# annnä Marketplace — SPEC (the open half of the store)

*One marketplace, two goods — **skins** and **templates** — on the same publish/browse/install rails. This file is the law of the goods, the rails, and the entitlement lane. The store's infrastructure is a **closed hosted service** outside this repo; only its seams appear here (`INTERFACES.md §1`). Everything in this file must make complete sense with that service absent. **Transaction terms are the closed service's and are not specified here** (§5).*

---

## §0. What the marketplace is

- **One marketplace, many document types** (carried ruling 2026-07-18). Skins are the shallow end (a pack + palette document); templates are the deep end (a bundle of shapes). Both flow through the same publish → browse → install rails; a new good is a new document type, never a new store.
- **Every payload is closed-grammar data, validated at the install door.** A marketplace document can rename, arrange, parameterize and skin; it can never express executable code, add lifecycle states, or alter engine semantics. **An installed item can never contain a program** — the worst case is a bad bundle, never an attack. Trust reads the format; revenue runs the store.
- **Template supply is owner-publish (FD-82).** Any signed-in owner may author a template through the console, save it for themselves, iterate, and publish it so others can install it. **Skins stay the admin pack pipeline.** This is capability, not gatekeeping: authorization gates (who may claim “Official PADI”, terms) may sit on top later (OR-28 / OR-29). They are not this sitting. `SCENARIOS.md` P2/P3. The admin pipeline for skins is `../assets/make-pack.mjs`.

## §1. The goods — two document formats

### §1.1 The skin pack document

The catalog form of a skin (`../app/DESIGN.md §Appearance` is the law of how a skin is *worn*):

| Field | What it is |
|---|---|
| `id` / `name` / `version` | Identity. A re-publish is a new version (§2). |
| `palette` | The approved token set — the shipped packs' `palette.json` shape **as it actually is: sixteen fields**, in the enumeration order the gate itself carries: `name` · `master` · `luminance` · `colorfulness` · `suggestedMode` · `dominants` · `semantic` · `accent` · `accentDeep` · `ambientDark` · `ambientLight` · `tintDarkAlpha` · `tintLightAlpha` · `brightestRegion` · `darkestRegion` · `veil`. **Every sub-shape is printed below the table.** *(Enumerated in full 2026-08-21 — the old cell named eight-ish and omitted `name`, `master`, and the two load-bearing measurements, so a schema built from it could not compute the veil and would refuse every real pack at §3's unknown-field door. The **veil** — the tint every glass surface is made of — **derives** per `../app/DESIGN.md §Appearance`, by mode from the pack's stored **`brightestRegion`** *(stored alongside `veil` itself, added 2026-08-22 — the V1 fix: the spike proved the old "continuous function of `luminance`" claim described a mechanism the packs could not feed, and a pack the build never saw needs the measurement stored to derive at install time)* plus 18% of its `DarkMuted`. **The install door also runs the derived AA floors** (`../app/DESIGN.md §Appearance`; a11y A12) — a pack that derives cleanly but fails contrast over its own regions refuses exactly as one missing a field does. **`darkestRegion` is stored beside that pair** *(added 2026-08-22, the same argument one field over: `../app/DESIGN.md`'s A1 urgency walk and A12 install floors solve against the pack's `brightestRegion` **and its darkest counterpart**, and a pack the build never saw needs both measurements stored to derive at install time — measured and written by the admin pipeline exactly as `brightestRegion` is, never a per-name table)*. *(2026-08-09: this was a two-value warm\|dark "glass temperature" switched on `suggestedMode`, and that rule is gone — `suggestedMode` still selects ink and density pair, never the veil.)* **The LQIP is not in this half (FD-31, ruled 2026-08-21):** a 24px inlined rendition of the licensed photograph is a rendition of the licensed photograph, so it lives in `derivatives` — **landed 2026-08-22**: the pipeline change shipped (`c49c1d2`) and all four packs' `palette.json` no longer carry it; the compliance note that stood here is discharged. |

| `preview` | **Palette-only** preview material — the gallery re-tints the owner's board from **swatches alone** *before* the account is entitled, without touching a licensed image or any rendition of one (FD-31). **Printed below.** |
| catalog metadata | Category, tags, featured flag, `popularity` (§6). |

### §1.2 The template bundle document (the "blueprint")

The transferable publication projection of a template is a **business-in-a-box** (personal cases included): the transferable *shape* of how someone runs bookable time — never their data. Carried law (prior build CONTRACTS §25), restated in full:

| Field | What it is |
|---|---|
| `id` / `name` / `version` / `manifest_version` | Identity and the authoring envelope. **`version` is content-addressed**: it increments when the document's content changes, never once per save call — which is what keeps `../engine/SPEC.md §1.7a`'s determinism guarantee ("the same session projects an **identical bundle** every time") true of the whole document and not only of its projected core. **`manifest_version` is the manifest-version stamp** *(field added 2026-08-29 — §3 has said since 2026-08-22 that the install door compares the catalog-manifest version a bundle was authored against, and the format carried no field for it to compare, so the door's rule was undecidable in fact)*: the app catalog-manifest version (`../app/SPEC.md §4.1`) the bundle was authored under, written by the save step **around** the projected set, so the projection itself stays the pure read §1.7a specifies. A re-publish is a new version (§2). |
| `domain` | The vocabulary: commitment-kinds with their typed fields ("dive course", "lesson"), display naming. Bounded by the same meta-schema as all generative UI (`../app/SPEC.md §4.1` — typed nodes from the closed list, a per-language `label` map, closed per-type prop lists). |
| `rule_shapes` | Entries from the engine's **closed rule menu** (`../engine/SPEC.md §3`) — with operands **blanked (the sentinel below) or set as the publisher's choices**. "Buffer between dives" is transferable wisdom; *their* 30 minutes is their setting. An off-menu rule shape is refused at the install door, upstream of the engine's own refusal. |
| `shared_shapes` | The outward faces: bookable-availability and booking-form shapes — the authoring side of the engine's Shared projection. **Printed below.** |
| `resource_shapes` | Boards to create: instructor roster slots, boat, pool, gear — **shapes only, no people**. **Printed below**, with its strips. |
| `kind_templates` | *(Field added 2026-08-21 — `KindTemplate` unblocked F5/Z1 in the engine while this table had no field for it to travel in, so the dive course was projectable in prose and refused at §3's unknown-field door in fact.)* Multi-day course shapes (`../engine/SPEC.md §1.12`), carried **role-only**: `{kind, sessions[{label, offset, duration, consumes[{board_role, quantity}], requires}], anchor_policy}`. **The hard fence binds this field with two named exclusions**: a session's `consumes` may carry **`board_role` only, never `board_ref`** (a concrete board on the publisher's account is their data), and the object travels **without `owner_org`** — both are stripped by the fence's selectable-set construction (`../engine/SPEC.md §1.7a`), not filtered after. |
| catalog metadata | Category, tags, featured flag, `popularity` (§6). |

**The wire grammar, printed** *(2026-08-29 — two fields were named with no shape a builder could implement and the blanking convention had no printed form, so the F4 and F5 seeds were writable only by guessing)*. Field names and their types; nothing here adds semantics the corpus has not ruled:

```
shared_shapes: [ {
    id, label,
    face     : "bookable-availability" | "booking-form",

    // bookable-availability — the three operands the "Free Time Available" seed blanks
    hours    : recurring-window | "blanked",
    duration : duration-operand | "blanked", // §3 duration range, with optional typed step/anchor
    buffer   : duration         | "blanked",

    // booking-form — a generative-UI schema, bounded by the app's meta-schema: typed
    // nodes from the closed list, per-language label map, closed per-type prop lists,
    // no code, no event handlers, no lifecycle
    form     : schema
} ]

resource_shapes: [ {
    role       : string,                 // "instructor", "boat", "pool", "gear" — a role, never a board
    kind       : string,                 // the board kind to stand up
    capacity   : unit-number | "blanked",
    attributes : [ { name, type } ]      // declared shape only, never a value about a person
} ]
// STRIPPED, by construction: `owner`. A concrete owner is the publisher's data. The strip is
// the projection's selectable-set construction, never a filter run afterwards — exactly as the
// kind_templates fence strips board_ref and owner_org.
```

**The blanked-operand sentinel, one printed form.** A duration operand uses the engine’s existing `duration` rule representation (`../engine/SPEC.md §3`): range alone or range with its optional typed step/anchor. A publisher-choice duration carries that complete validated operand; a blanked duration carries the sentinel for the whole operand, never a range that silently drops its increment. Private retained values are governed by §2 and are not this projection. A blanked operand travels as a **required-present key carrying the reserved value `"blanked"`** — never as an absent key. **Omission is malformed**, refused whole at the door with the failing entry named; only the sentinel means "the publisher left this one to the installer". That is what makes F2's and I3's refusal decidable at the door rather than a judgement about what a missing key was supposed to mean, and it is the printed form of `../engine/SPEC.md §1.7a`'s "operands are blanked either way".

**Bounding schema, field by field** (so F1's and F3's unrepresentability is checkable one field at a time): `domain` → the meta-schema at `../app/SPEC.md §4.1` · `rule_shapes` → the closed menu at `../engine/SPEC.md §3`, plus the sentinel above · `kind_templates` → `../engine/SPEC.md §1.12` · `shared_shapes` / `resource_shapes` → the structs printed above. **Every generative-UI schema among them — `domain`'s typed fields and each `shared_shapes[].form` — is bounded a second time by the transferable subset printed next**, which is the half of that meta-schema a bundle may carry.

**The transferable subset — what a travelling schema may carry, and this section is its one normative home (FR13)** *(2026-09-12 — `domain` and every `shared_shapes` `form` were bounded by the app's meta-schema and by nothing further, and that meta-schema's node carries `default?`, `bind` and a per-type `props` map; a `text-input` whose `default?` held the author's own contact detail therefore used only printed keys, validated against the printed grammar, and travelled unremarked — which made the hard fence below false in fact while every field of the document stayed legal. The fence said the fields do not exist; the defect was that they did, under a field the fence never named)*. A schema that travels — `domain`'s typed fields and every `shared_shapes[].form` — carries the **reusable structural half of `../app/SPEC.md §4.1`'s meta-schema and nothing else**:

- **Carried:** `type` from the closed list · `id` · the per-language `label` map · `children` · `required?` · a `bind` naming a field path **the installed copy will own** · `props` drawn from that type's closed prop list, carrying shape. A prop is shape only when the manifest's existing per-type entry marks it as portable and supplies its closed structural value shape; the value must be a bounded boolean, number, or manifest-enumerated structural value (or a list of those), never arbitrary text, a reference, or a value supplied by an instance.
- **Not carried, and not expressible in a bundle:** **`default?` in any form** — a default *value* is what one owner filled in, never the shape they authored; a **resolved reference** of any kind — a board, an account or organization, a party or principal, a contact, a token, a stored artifact; a **per-use value**; and a **`props` member carrying instance data rather than shape** — an option list naming a person, a prefilled address, an embedded credential. A prop is portable only where its type's closed list and its manifest-declared structural value shape admit it; arbitrary text, references and instance values are refused even when their wire type resembles a structural prop.
- **A schema node has no parameter carrier.** `default?` is absent from the transferable schema and is refused whatever value it holds, including the reserved value `"blanked"`; the blanked-operand sentinel above applies **only to `rule_shapes` operands**, where it is a required-present key. A value the installer must supply in a form is therefore blank in the travelling schema and is configured privately after install under §2/I1. **Publisher-choice rule operands are untouched by this subset**: an operand a publisher deliberately set is a closed-menu entry's value (`../engine/SPEC.md §3`), not a person's data, and stays permitted exactly as the `rule_shapes` row above states. "Their 30 minutes" was never the thing this subset excludes; *their* phone number is.
- **The subset binds at every depth.** A `group`'s `children`, a `row`'s children and those children's `props` are each the same subset. A nested node is not a hole in it, and neither is a node reached only through a `children` chain.

**Constructed first, re-checked second — and the ruled save optimization survives unchanged.** The projection's selectable set *builds* the subset (`../engine/SPEC.md §1.7a`): the excluded members are not in the readable set, so no filter has to be right for them to stay out — the same construction by which the `kind_templates` fence strips `board_ref` and `owner_org`. The publish and install doors then validate the same subset against the wire document, because a document that has crossed a trust boundary is checked and a projection that never left one is not. That is §2's ratified save sentence, intact and not narrowed here: **a valid projection need not re-run the door's F1/F2/F3 checks**, and install re-runs them because it crosses a boundary the save never crosses.

**`file-slot` cannot appear in a portable schema, and the refusal is whole.** The node and its former direct binding sit outside the active v1 manifest (`../app/SPEC.md §4.1`) under the owner/guest upload exclusion whose home is `../security/SPEC.md §4`; a bundle naming it is refused **entire, with the failing entry named** (`SCENARIOS.md` I3) — at the publish door and the install door alike, and in draft, saved, listed and forked documents equally. No fallback attachment control, accept-list-only variant or direct submission restores it through the portable format. This is the bundle-side face of the app's removal, never a second rule: the app's manifest and security's exclusion are the homes, and this sentence says only what the portable format does with them. **Structured forms and in-form consent stay expressible** — `signature` is an ordinary active field node capturing consent in the form, not an upload, and a `form` carrying it travels normally. Neither it nor an approved source form's identity, language or version is verification of a participant (`../app/SPEC.md §5`, and `../security/SPEC.md §4`, the home of that distinction).

**What this subset still does not fence, said plainly rather than implied.** The residual `../engine/SPEC.md §1.7a` records stands undiminished: a field's *name*, and the text of its `label` map, are shape the author chose, and "John's medication list" is caught by no mechanical rule stated here or there. Field names remain the publisher's review item under §2 (FD-1 residual, annotated at FD-82). This section narrows what a schema may *carry*; nothing in it reads what a name *means*, and no row below should be read as claiming otherwise.

**Authored vs publish-assigned, split** *(2026-08-21 — the flat table made G8 and I6 undecidable: if catalog metadata were required at authoring, no projected bundle could ever validate)*: the **authored set** is *what the engine projection emits, plus the save step's stamped envelope* — `domain`, `rule_shapes`, `shared_shapes`, `resource_shapes`, `kind_templates` from the projection (`../engine/SPEC.md §1.7a`), wrapped in `id`/`name`/`version`/`manifest_version` by the save step — and it is what G8/I6 validate against. The **publish-assigned set** — **`provenance`**, category, tags, featured, `popularity`, listing copy — is attached at §2's publish step by the **publishing owner**, with two members that are never the publisher's to set: **featured** is an admin merchandising flag and **`popularity`** is service-computed (§6). The publish-assigned set is **absent from an authored/saved bundle by definition**; the install door's unknown-field refusal checks against the full grammar, in which the publish-assigned fields are optional-at-authoring and present-at-catalog. The two that had no printed shape:

```
provenance : { publisher, published_at }   // who listed it, and when. HOW that publisher identity
                                           // is vouched is OR-28 — open, §7
listing    : { title, summary, detail }    // §2's "detailed information on what it is and what it
                                           // does"; rendered in the viewing owner's language with
                                           // English fallback (§6, the home of that rule)
```

**The publish order is the catalog's, not the hash's** *(2026-08-31, m-16)*: `version` is content-addressed identity and carries **no order**; "re-versioned" ordering (P7, unpublish/re-publish walks) reads the catalog's own **monotonic publish sequence**, assigned at publish — two facts, two fields, never conflated. **Three version species, never conflated:** the **seam API version** — the closed service's versioned API (`INTERFACES.md §1`); the **bundle document version** — `version` above, content-addressed; and the **catalog-manifest version** — the manifest-version stamp `manifest_version` carries and §3's door compares.

- **Hard fence — people and data never travel.** No counterparty, booking, history, ledger or personal-data record is *representable* in the format: the fields do not exist (poka-yoke, asserted as schema-level unrepresentability — `SCENARIOS.md` F3). **The fence covers the schema fields too, by the transferable subset above** — a `default?`, a resolved reference or a value-bearing prop is outside the subset at every depth, so a personal value has no legal carrier inside a travelling schema either. Read the two together; the field list alone was never the whole fence.
- **The format spans the seed catalog.** Smallest legal bundle: **"Free Time Available"** — one shared bookable-availability shape with blanked hours/duration/buffer (a teacher's bookings, a date, any meeting). Largest: the **dive-center** bundle — multi-resource shapes, course kinds, governed rules with blanked operands. Both must validate against one grammar (`SCENARIOS.md` F4/F5).
- **Relationship to onboarding starters — repointed under FD-102** *(2026-08-31: the app ships no domain starter; the neutral way-in is `../app/SPEC.md §8`'s)*. The separateness law **survives for any future starter** under FR38's founder-built carve, and explicit throwaway development fixtures stand: an app-local stored template remains **deliberately a separate system** — same spirit, different artifact, never merged, and never replaceable by a marketplace bundle; their home, including which starters exist, is `../app/SPEC.md §8` (FR13, and the second list that used to stand here had already drifted from it).
- **Divergence from the prior bundle, recorded** (the supersessions discipline): the prior ruling's bundle was "domain schema + booking templates + rule shapes." `shared_shapes` and `resource_shapes` are **deliberate additions** — this architecture makes the outward faces and the resource boards first-class, so the bundle carries their shapes too.

## §2. Publish (owner-publish for templates, FD-82)

**Author through the console → save for the owner → iterate → publish to the catalog.** The **Author** step is not hand-writing a document. A signed-in owner tells the agent what the template must be able to do; a successful catalog lookup with no suitable result allows neutral from-scratch authoring, while an unavailable lookup stays explicitly unknown and permits retry or user-chosen authoring. No template is invented as a retrieved result. The same harness tools that shape any board (generative-UI + rule writes + `CRUD_Shared`/`CRUD_SOP`; `../harness/SPEC.md` §5/§6, `../harness/SCENARIOS.md` G6) produce the kinds, rule shapes and shared/resource shapes. That output is saved as an **owner-private configured definition beside its §1.2 publication projection** in §3’s existing account document — iterable, **not a catalog listing**. **Publish** is a later owner act: the saved bundle is listed so others can install it, carrying detailed information on what it is and what it does (the publish-assigned set: provenance, category, tags, listing copy). This is the **authoring-and-publish law's one normative home** (FR13): a bundle is **never hand-written by a developer**; developers never author domain templates (FR38 authorship, unchanged). Skins additionally run the pack pipeline (`../assets/make-pack.mjs`) and remain **admin-only**.

- **Save is not publish.** A saved bundle lives on the owner's account. Catalog listing happens only when they press publish (`SCENARIOS.md` P3).
- **The save law — and §2 is its one normative home (FR13)** *(2026-08-29: the projection's side and the authoring side each described a save, and neither said what the save validates or where the document lands)*. The ratified sentence, in full:

  > Save skips the door's F1/F2/F3 checks — deliberately: the §1.7a projection is fenced by construction and its source rules are closed-menu-constrained at write time (an off-menu type is unstorable), so the checks are a structural no-op on a save; install re-runs them because it crosses a trust/time boundary the save never crosses. The PROJECTION, not the door, guarantees the §1.2 sentinel on every emitted operand — a mid-authoring draft's unset operand included ("operands blanked" means the sentinel on the wire).

  The quoted ratified paragraph describes the **structural projection only**, not validation of private defaults or proof that a save persisted. The projection named there is `../engine/SPEC.md §1.7a`. The configured definition and projected document **land in §3's app-owned document store, through the same write path an install's fork lands through**, provenance **`createdVia: save`**. **No new seam verb, and no second store path** — a saved definition and an installed fork share the account-document envelope, with origin distinguished by provenance. `../harness/SPEC.md §6` and `../engine/SPEC.md §1.7a` specify the projection; the save itself is law here.
- **Private definition and fresh use.** The existing account document holds owner identity, stable definition id, revision, manifest stamp, provenance, lifecycle (`draft`, `usable`, `retired`), a private configured-definition payload and its separately constructed §1.2 publication projection at that revision. Revision identifies persisted definition content; it is neither a per-use request id nor the projection’s content-addressed `version`. Retain prior revision payloads needed by bound uses/links and history in this same document store; replacement advances the current pointer without overwriting those payloads. The private payload contains the authored closed-grammar schema, typed rule operands and validated defaults, their scope and explicit answers/pins. Preserve the whole chosen duration range and optional typed step/anchor (`../engine/SPEC.md §3`), windows, buffers and other supported settings. An explicit blank stays blank. Values come from accepted authoring input and authorized stored structure, never reconstructed from display numbers or the blanked projection. An incomplete definition may be saved as `draft` with unresolved fields identified and disabled policy retained; it cannot present unresolved settings as usable.
- **Validation and use binding.** Save validates the private schema and supplied defaults through the existing catalog/typed-rule checks and ordinary harness/engine validation, including unresolved operands and scope; it does not skip these checks merely because projection F1/F2/F3 checks are redundant. After confirmed persistence it immediately opens one fresh use, bound to `{owner, definition id, definition revision}` with its own request identity and editable per-use blanks, without a separate owner guest-page-preview gate. A saved draft opens for completion with unresolved fields visible; booking still requires ordinary admission. Opening another use creates another request identity. Reopening/retrying the same use preserves its identity; a save retry recovers the originally opened use, not another one. Saving/opening does not itself book, mint access, send, publish or create a Grant. Use-specific values and any later booking/link references belong to that use’s existing request/Shared lifecycle, not to definition defaults.
- **People and choices have explicit scope.** Reuse across different people is the ordinary path, with Student/name/contact or equivalent participant inputs blank per use; no initial reuse questionnaire. Incidental participants, contacts, booking-specific links, credentials and live Grants never enter defaults, copies or publication. A unique identifying value deliberately entered while editing a definition instead triggers clarification of whether it belongs to this use or the private definition, only if the scope is unresolved. Keep and reuse the answer; an explicitly authored named private value is permitted with its prefill scope visible, never silently erased or absolutely banned. An explicit attendance choice is separate from reuse across people. A copy preserves intentionally authored defaults and their scope, but a scope referring to the original offering (including quota scope) needs its user-owned resolution before use; a new identity never grants a fresh allowance. Reminder configuration can remain authored data; its live authority and recipient resolution must be obtained under the existing harness floor, never cloned.
- **Definition edit or use edit.** A persistent definition edit, even when initiated from an open use, asks **Replace existing** or **Save as new** once for that candidate. Store the chosen branch with the accepted shared draft’s ref/revision (`../harness/INTERFACES.md §3.1`); resume reuses it unless the user changes that choice. Replace retains definition identity and advances the revision only after validation and any required current-booking compatibility/resolution. A blocked candidate is addressable and resumable with current and proposed settings distinct; the current definition stays effective until application succeeds. Save as new allocates an independent definition identity and opens its fresh use; original revisions, links, uses and bookings remain attached to the original. It copies only intentionally authored private configuration, never the active use’s participants, credentials or live Grants. Ordinary per-use Student/date/field edits and removal of an uncommitted draft row do not ask this definition-replacement question. Existing uses retain their bound revision; moving one to a later definition is an explicit checked act, never a silent retarget. Booked terms and history retain their own engine lifecycle.
- **Save readback is evidence of persistence.** Before reporting saved, the §3 producer durably records the definition identity/revision and write identity and reads back that result. Show persisted revision separately from an unsaved edit, a pending save and an unknown outcome. An acknowledged refusal leaves the edit unsaved; a lost acknowledgement is unknown until recovered by that same write identity. No optimistic “saved” label, duplicate identity or repeat Replace/Save as new question may substitute for recovery. Closing an unsaved edit discards only that edit under the shared draft contract; a pending or unknown save must be resolved before claiming it was discarded.
- **Publish uses only the saved revision’s data-free structural projection**, never its private configured payload. Private named defaults and per-use values are not selectable; blank private operands unless independently authored as non-personal publisher choices in the projection. Publisher-choice labels remain the disclosed name-review residual below. **Publish re-runs the authored-set validation the install door runs — as a courtesy, never as the law.** The door stays where validity is decided (§3), and running the same checks at publish means nothing invalid is ever listed in the first place, so the refusal an installer would have met arrives at the publisher instead.
- **A saved bundle is deletable by its owner, and deleting it never orphans an existing listing.** Removal retires its active saved entry; it is not erasure of referenced revisions or cancellation of bookings. First enumerate the actual live links, empty and populated uses, pending/unknown operations and bookings, disclose effects and obtain required user choices. Recheck the definition revision and complete dependency set at application, including references added during approval; a changed set refuses the stale retirement without partial cleanup. The unused-copy case may remove its disclosed empty use with the entry. Populated uses and live links require their own resolved lifecycle choices; resolve unknown commit outcomes first, and use ordinary booking cancellation for committed bookings. Retain the revision needed by surviving uses/links and booked terms/history; no hidden broken link, booking cascade or assumption that every template is empty. A listing is the catalog’s own document: retirement leaves everything already published and every installed copy unchanged. Public unpublish stays a separate owner act. Gated at P6.
- **Any owner may publish a template they authored** (FD-82). No authorization gate on *who* in this sitting. Future gates may sit on top (OR-28 vouched “official” class; OR-29 terms). Do not invent those gates here.
- A re-publish is a **new version**; the catalog lists the newest.
- **Unpublish removes the listing only.** Installed copies are never touched — fork isolation (§3) makes this safe by construction: *unpublish → installed copies continue to work* (`SCENARIOS.md` P1).
- **No extract-from-board.** Publish lists an authored, data-free §1.2 shape. Extracting a populated board is still refused (engine no-export; `../engine/SPEC.md` §1.7a). Field names remain the publisher's; there is no mechanical fence on “John's medication list” now that review is not admin-only (FD-1 residual, annotated).

## §3. Install

Browse → preview → install. **Install = snapshot fork with provenance** (`createdVia: install`, source id + version) — **no live upstream link, no update subscription. The installer owns their copy.**

**Account-document producer and internal path.** The existing **app account-document adapter**, backed by the app-owned document store already used for template forks, produces private save and install persistence under §2’s save law. It uses app-owned records on the existing reactive backend (`../app/INTERFACES.md §2`), distinct from engine domain truth and from device skin files; no second database or engine marketplace table is introduced. Its internal save/read/revise/remove path is callable by the authenticated app controller whether or not a canvas is rendered. Existing owner-input and draft/readback payloads carry the requested operation and selected identity; `render` merely presents results and never causes persistence. This is internal application plumbing, not a new harness tool, `AppSeam` method, public verb or `display_settings` member. Headless eligible owner operations use this same adapter, with the same authenticated principal and checks; caller-supplied owner ids are never authority. The adapter supplies authorized document content to the existing owner-input/context path, tagged by provenance; it does not add an engine `calculate` document read or let the model query storage directly.

Authenticate before enumeration or lookup; bind every read, save, revision, copy and retirement to the authenticated account and recheck authority when applying. A wrong account cannot enumerate, read or mutate another account’s definition, guess its existence from differentiated errors, or recover its write receipt. Return only an authorized account slice. An owner’s authorized session on another device reads the same persisted identity/revision; local form state and HTTP caches are not the durable account store.

A submitted replacement kept pending for compatibility resolution retains its candidate fields and branch with the existing document’s operation record, separately from the effective definition revision; this is not persistence of every unsaved keystroke. Resume binds the retained candidate to the current shared draft and revalidates, without replaying the branch question. For each intended mutation, durably retain a stable account-scoped write identity and payload fingerprint before dispatch, with the expected definition revision (or create intent for a new identity), accepted draft ref/revision and scope. The adapter atomically compares the expected revision, writes the document and its attributed result/receipt, or refuses without overwrite. Concurrent edits from the same revision cannot both replace it. Identical retries recover the original identity/revision and correlated fresh-use identity, even after lost acknowledgement or reload; reuse of a write identity for different contents refuses. A separate deliberate new save/copy receives a new write identity. Recovery reads precede retry and remain available for removal receipts. No successful revision is reported from a projection result alone.

The adapter also serializes attachment of app-owned use/link references with retirement’s dependency check. Opening/issuing a use or link, or changing a use’s dependent state (including submitting an already-open empty use for booking), must reserve/advance its app-owned reference revision through this same path before the existing harness operation proceeds; unresolved in-flight work is a dependency, not absence. The existing app/harness controller orchestrates this check around the ordinary operation; the engine receives no document identity or marketplace-specific field. At retirement’s applying point, compare the reviewed reference set and current revisions and refuse any race or unresolved result; a retired identity cannot accept a new reference. Existing domain changes still use ordinary harness operations and their engine rechecks, never direct app writes. If those operations are needed, finish/read back the user-selected resolutions before retrying retirement; do not claim one transaction across a catalog call, an engine write and the document store. Already completed independent acts are reported truthfully. The backend’s internal document receipt and reference checks are app-owned bookkeeping, not new engine primitives.

- **Skins:** install = entitlement grant (through the seam's `entitlements.grant`, granted by the closed service, §5 — `INTERFACES.md §1`) + pack fetch. The skin joins the owner's gallery and faves like any shipped skin. **The fetched pack persists on the entitled device, in an app-managed store outside the HTTP cache** *(named 2026-08-21 — E4 forbids a cache header outliving the signature, so a builder using the HTTP cache as the "device copy" would satisfy E4 and break S4/S6 on the first eviction; the persistent copy is the app's own storage, written after fetch, and E4 governs only the delivery response)* — §4's short-lived URLs govern *delivery*, never the device's private copy — which is what lets a store skin satisfy the no-flash and outage laws (`../app/SCENARIOS.md` S4/S6). For skins, the fork-ownership law reads: the entitlement plus the device copy *are* the installer's copy; unpublish removes the listing, never the entitlement or the copy. **Owner-initiated removal** *(2026-08-29 — install had an inverse for templates (uninstall) and none for skins, so an owner who wanted a skin off their device had no specified act)*: the owner may remove an installed skin — it **deactivates**, its **fave slot clears**, and the **device copy is deleted**. **The entitlement survives**, so a re-fetch re-installs it with no new grant. This is the exact **inverse of FR14's split** (§4): there the entitlement ends and the copy stays; here the copy goes and the entitlement stays.
- **Templates:** the install reads the full document through **`catalog.get`** (`INTERFACES.md §1`), and the bundle is **validated whole at the door** — an unknown field, unknown type, or off-menu rule shape refuses the entire install with the failing entry named; there is no partial install (`SCENARIOS.md` I3). **A bundle records the catalog-manifest version it was authored against, and the door compares** *(2026-08-22 — `../app/SPEC.md §4.1`'s manifest now carries one; a bundle authored under a newer manifest than the client's refuses with the versions named, the same honest refusal as an unknown field)*. **Validate, then grant — in that order** *(2026-08-29 — this narrative named no grant at all for templates while `INTERFACES.md §1` calls `entitlements.grant` "the install's grant" for both goods; with the order unstated a builder could grant on the install request and then refuse the document, leaving an entitlement to nothing)*: **`entitlements.grant`** runs only once the door has passed the bundle, so **a refused install never brings an entitlement into existence** and there is never one to withdraw afterwards. **The validated fork lands in an app-owned document store — the sibling of the skins' app-managed store above — owned by the installer** *(named 2026-08-22, the mirror of the skins' named home: every other candidate is explicitly closed — no marketplace table exists in engine truth (`INTERFACES.md §4`) and the app's starter store is deliberately a separate system (§1.2) — so this store is what serves the fork's visibility and resumability below and what I5's uninstall removes)*. Then the installer's **own agent** walks the blanked parameters through the normal **propose → confirm** elicitation — the proposal card **is** the preview, not a separate stage — *their* buffer, *their* prices, *their* hours — so **every resulting domain write is an ordinary harness-mediated write**; the fork itself persists through the internal account-document path above. There is no bulk silent import, and the floor is untouched: installing is authoring (`INTERFACES.md §3`). **The walk is a session under the authoring twin's law** *(2026-08-21 — the T2 session law, harness G5; the walk had no session state, and §3's order of operations lands the fork first, so an abandoned dive-center walk otherwise stranded a forked source plus half-confirmed rules in a state no scenario described)*: save/resume/abandon; partially-confirmed parameters persist as `draft` (disabled) rules; an abandoned walk leaves the fork plus its drafts — visible, resumable, and removable by ordinary uninstall (I5's path covers the partial case). Bundle-carried free text (naming, provenance prose) enters the installer's context tagged `document` and takes the quarantined read (`../security/SPEC.md §5`, the install door's stamp).
- **Uninstall keeps the past.** Under §2’s checked retirement law, uninstalling a template removes the active source document **and any unreferenced `draft` (disabled) rules the walk left behind**, through their ordinary lifecycle path *(corrected 2026-08-29 — "the source document only" contradicted the partial-walk cleanup this same section specifies and I8 asserts, which has drafts to remove; I5 cites this sentence, so the contradiction was load-bearing)*; rules and commitments **already confirmed** stand, under changing-the-rules-never-rewrites-the-past.

## §4. Entitlements & degradation

**Grammar evolution — one law over both goods** *(2026-08-22 as the pack-side mirror of `../engine/SPEC.md §1.10`'s evolution rule — the palette grammar has already grown stored fields once, and install is a fork with no upstream link; **widened to both goods 2026-08-29**, because an installed template fork is the same situation stated for packs alone: a fork meeting a client whose grammar has moved on)*. **Both marketplace grammars are additive-only with declared defaults** — no field is removed or re-typed, every already-shipped shape stays readable, and a change that cannot be expressed additively is a spec change with its own ruling. That is the engine's rule for its own store, applied to the two documents this section governs.

Degradation is then stated **per good**, because the two are not alike:

- **A pack the grammar has moved past degrades to the shipped floor by this section's existing mechanism**, until it is re-derived (where the new fields are derivable from what it stores) or re-installed; it is never silently broken and never silently un-installed. The surface stays honest in this section's own register — the gallery says the skin needs re-fetching, **never a stale store action, never an error wall**. Gated at E8.
- **An installed template fork stays readable and is upcast on read** — the declared defaults fill what the fork predates — and is **never refused retroactively**. A fork the grammar has moved past **produces no detection event at all**: it keeps working, and nothing surfaces, because nothing is wrong.

**The detection identity, and the moment it is checked — packs only** *(scoped explicitly 2026-08-29; the reader could not tell whether the template fork was subject to it, and it is not)*: detection is **field absence measured against the current grammar** — a pack lacking a field the live grammar declares — checked when the pack is read for use, at the same two moments §4's entitlement checks occur (skin activation, app open). Nothing in this paragraph reaches a template fork.

- **Per-account entitlements**, held by the closed service. Licensed images are served only via **short-lived signed URLs** to entitled accounts; **nothing licensed — as a URL or as inlined data — appears in any public repo, client bundle, long-lived URL, or unentitled-reachable document** (`SCENARIOS.md` E4, content-based since FD-31). The signed-URL discipline is an **analogue of** the capability-token law, governed separately *(reworded 2026-08-21 — the old "an instance of" filed it into `../security/SPEC.md §3`'s closed table, which has no row for it and whose binding rules it fails on every axis: stateless, no stored digest, no revocation latch, and minted by the closed service rather than annnä — the reversal §3.1 exists to stop)*; E4 remains its scenario.
- **Degradation law (carried):** service unreachable → the shipped four + Plain always, plus any installed skin whose pack is on-device (§3), at full function; **every installed template keeps working** (installed = local forked data); store shelves show an honest "store unreachable" — never stale store actions, never an error wall (`../app/SCENARIOS.md` S6, `SCENARIOS.md` E2/E3).

- **Revocation (FR14, ruled 2026-08-06).** An entitlement can be **withdrawn by the closed service**. Why it was withdrawn is out of scope (§5) — the open half sees only the state change, and the law is one rule with no special cases:

  **A withdrawn entitlement takes effect at the next entitlement check.** The skin **deactivates**, its **fave slot clears**, and appearance falls back to the shipped floor (§0's four + Plain). Checks occur at **skin activation** and at **app open**.

  *This does not contradict §3's device-copy persistence, and the distinction is the whole point:* §3 says **unpublish** never removes the entitlement or the device copy — unpublish is a *catalog* event. Withdrawal is an *entitlement* event. **Owner-removal is the third, a *device* event** *(2026-08-31, F-25 — the pair list was a pair while three event classes exist)*: an owner removing an installed pack deletes the device copy and touches neither catalog nor entitlement; re-activation walks the entitlement check as any activation does (`SCENARIOS.md` I10). Under FR14 the device copy still persists on disk; what changes is that **the entitlement no longer authorizes activation**. The pack is not deleted, hunted down, or remotely wiped.

  *Interaction with the degradation law, stated so a builder does not have to guess:* offline, **no check can occur**, so the last-known entitlement stands and the skin keeps rendering. Revocation is therefore never a flash, never an error, and never an outage-triggered downgrade — it lands on the next successful check, which is exactly the behavior S4/S6 require.

  **The template side of the same one rule** *(2026-08-29 — FR14 was written over skins and read as if it spanned both goods, leaving what a withdrawn template entitlement does to an installed fork unstated)*: a withdrawn **template** entitlement **never touches the installed fork**. The fork is local forked data the installer owns (§3) — no rule is disabled, no commitment moves, nothing on the board changes. What withdrawal ends is **re-fetch and re-install standing**: the account can no longer pull that bundle from the catalog again. FR14's "one rule, no special cases" now genuinely spans both goods — in each, what withdrawal ends is the *authorization*, never the copy. Gated at E9.

## §5. The closed-service lane

- **Store transactions live entirely inside the closed service.** What the store transacts, and on what terms, are properties of that service and are **deliberately not specified in this repo** — no rails, no keys, no math, no stated terms. This repo's readers get the open half; the terms are not part of it.
- **The lane distinction is a safety law, not a commercial one.** The product's money law — *money is tracked, never moved* — governs value **between users on boards**. A store transaction is a **different lane** and never touches a board's ledger records (indexed in §8's invariants ledger below). **Points are never money** — stands regardless of what the store transacts.
- **Skins-as-purchasable is deferred, and this is its readiness home** *(2026-08-31, F-28 — the deferral had no SPEC sentence)*: store skins become **purchasable** only when the closed-service lane opens — a readiness condition of this section, never a date — and until then entitlements are granted by the admin path alone; the four sites that restate the deferral point here.
- **Entitlement, not transaction, is what this repo models.** The open half sees exactly one fact: whether an account is entitled to an item (§4). How an entitlement was acquired, and how it ends, are the closed service's business — the open half reacts to the entitlement state and nothing else. That boundary is what keeps §4's revocation law free of any transaction detail.
