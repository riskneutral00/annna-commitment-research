## A — Atomic commit & races
- **A1 [race, one winner]** Two commits race for the last unit of capacity. Exactly one succeeds; the other returns `{conflict, reason, alternatives}` listing still-open times. *(Sofia's 3:00; Situation-D's last Friday slot; Situation-C's last boat seats.)*
- **A2 [all checks, one transaction]** A commit that passes capacity but violates a buffer gap against its *following* neighbor fails atomically — nothing partial is stored.
- **A3 [governing wipe rejected]** A lower-authority diff whose effect would disable a governing rule does not apply; the governing rule remains in force. *(Mirror of harness D-series.)*
- **A4 [write-id idempotency — §6.6]** A commit applies; the identical write id is re-committed: the **original result** returns and nothing applies twice. The same id arrives with a **different payload**: refused (`{conflict, reason: write-id-reuse}`), neither payload honored. A commit **fails**; replaying its id returns the same failure. A **foreign tenant** replays the id: nothing matches, nothing returns — the index is `(owner_org, credential)`-scoped. *(The engine half of harness K4.)*
- **A5 [re-widening cannot double-book — §6.7]** A rental ends early (`actual_end` 14:00), the freed 14:00–17:00 is re-let, then a diff corrects `actual_end` back to 16:00: the write returns `{conflict, reason, alternatives}` and **parks for a human**; the store never holds two concurrent occupants of a capacity-1 board. The same correction with the slot still free applies as an ordinary diff.

## B — Latches
- **B1 [no un-expire]** A hold lapses (`expired_at` set by the virtual clock); the signature arrives late. Evidence is recorded; status stays `expired`; the unit is never re-held. *(Situation-B's lapsed hold.)*
- **B2 [latch wins]** A cancelled-but-otherwise-complete commitment reports `cancelled`, not `completed`.
- **B3 [no clearing write]** Any write attempting to null a set latch is rejected by the store.
- **B4 [escalation stored, terminal write-once]** An `Escalation` (`../harness/SPEC.md §3.9`; stored per SPEC §1.13) is written, its `ladder_state` advanced across two virtual-clock firings (rung 1 → rung 2), then its status latched `timed_out_parked`. A later write attempting to reopen it (revert to `open`) is **rejected by the store**, and the co-occurring `needs_human` park is clearable only by a human (B3's discipline applied to the escalation). Assert the object **persists across firings** (read back from the store, not from harness memory) and that **no escalation-specific entry point** is called — only `commit`/`calculate`. *(The engine half of `../harness/SCENARIOS.md D12–D17; §3.9`.)*

- **B5 [no delete entry point — §1.10]** The engine's callable surface contains **no operation whose effect removes a stored row** — asserted structurally as an absence over the entry-point set (the K2 pattern applied to deletion), plus one behavioral half: cancelling, revoking, expiring, and withdrawing a bare draft (§1.4) each leave the row readable in history.

- **B6 [a historic shape stays readable — §1.10]** *(added 2026-08-29 — §1.10's additive-only law had no scenario, no `§10` row and no build step, in an append-only store where the rows it governs are permanent by law, so a violation is not recoverable by a later fix.)* *Given* rows written under an object shape, *when* the shape gains a field with a declared default, *then* every historic row **reads back through the new shape** with the declared default supplied **on read** — and the stored bytes of those rows are asserted **unchanged**, because *"upcast on read, never rewrite"* is falsified by a migration that quietly succeeds. And a shape change that **removes or re-types** a field is **refused at write as a storage fact** — asserted as refusal, the G8 pattern, not as a validation message and not as a migration that runs.

- **B7 [a restore conflicts loudly and cannot resurrect a latch — §9, §6.2]** *(added 2026-08-29 — `§10` carried the restore row as the one ledger entry whose construction site pointed outside the package, while no engine scenario mentioned a restore and no BUILD step named one.)* Two arms, asserted in one run. **Conflict arm:** a version restored over a slot that has since been **re-let** returns the conflict set as a **parked owner decision, per row** (`needs_human`, §1.3) — assert **per-row granularity**, not one merged park, and assert **nothing applied silently**. **Latch arm:** restoring a **pre-cancellation** version of a cancelled commitment is **refused**, asserted against the **full version chain** with the latch set on a version *other than* the one being restored — a check that reads only the restored version passes this scenario wrongly, which is the whole reason the arm is written this way. And assert the boundary §9 draws — *"A restore recovers structure; it never re-runs the past"* — as the absence of any replayed terminal event. *(The restore operation's own home is `../security/SPEC.md §8`; this is the engine law §9 states about it.)*

- **B8 [the conversion link is engine-minted and adds no read power — §1.1]** *(added 2026-08-29 — FD-46/FD-51's party↔principal link was defined in `SPEC.md §1.1` with engine-enforced semantics, absent from Step 1's object roster, and gated only by `../security/SCENARIOS.md` N6 in another package.)* **The structural half (Step 1):** **no caller-constructable entry point mints a link** — asserted as an absence over the entry-point set, the B5 pattern; and a link naming two tenants is **engine-authored or it does not exist** (I4's discipline applied to identity — the mint act itself is the security layer's claim, `../security/SPEC.md §2`). **The read-union half (Step 4):** the link's assembled starting history is **exactly** the union of what the linked party's booking-bound tokens could already read — asserted as **set equality**, never as a sample — and drawn *"over unrevoked, unexpired tokens only"*: a **revoked** token contributes nothing and an **expired** one contributes nothing, each asserted in the same run, so a build that assembles over the whole token history fails here. **And it re-homes nothing:** every carried record keeps its owning tenant after conversion, asserted on each record's stored `owner_org`. *(The engine half of `../security/SCENARIOS.md` N6 — the two must agree or conversion means different things on the two sides of the seam.)*

## Q — Quota & balance
- **Q1 [the 11th hour]** A customer at 10h/month: `calculate` availability excludes any slot that would exceed the rate; `commit` refuses if forced. *(Sofia's cap.)*
- **Q2 [balance pack]** A 10-dive/3-month pack: draws decrement; the 11th draw and the post-expiry draw both refuse. *(Situation-C's dive pack.)*
- **Q3 [window edge]** A quota window spanning the materialization horizon computes identically before and after horizon extension.
- **Q4 [cancel restores the draw]** A booked half-hour drawing against a per-customer quota is cancelled: the half-hour **returns to the window's allowance** in the same window, and a rebook draws it again normally — the money credit (K1) and the restored hours ride onto the rebook together. *(Situation-A's cancellation-credit beat — K1 covered the money half by name while the quota half had nothing.)*
- **Q5 [the operator's day ceiling]** *(Situation C's "capacity — how many students the center runs in a single day"; added 2026-08-22; reworded 2026-08-22 — the row cited G7(b) for a board-targeted quota `SPEC.md §3` does not admit.)* An owner-scoped count-denominated `quota` over a day window targeting the course kind (§3's quota row: kind and audience are its targets) sits at its cap: `resolve` for one more course that day returns the structured decline naming the quota — **even though every resource it would draw on (instructor, pool, gear) is free**. The ceiling binds above the resources; cancelling one of the day's courses restores the count and the next resolve places (Q4's law).

## T — Travel & gaps
- **T1 [unreachable excluded]** Adjacent placements at two places: any candidate violating `gap ≥ travel(a,b,at)` is absent from availability and from `resolve` output. *(Situation-D: 10:00 across town after a 9:00–10:00 visit is never offered.)*
- **T2 [override beats computed]** A declared travel rule (route + time-of-day scoped) contradicts the provider's number; the declared value governs every computation touching that route/time. *(The bridge at rush hour.)*
- **T3 [fail closed]** The travel stub returns `unavailable`: the gap is unknown; the slot is not offered, the move not proposed; the decline carries the reason.
- **T4 [constant buffer]** A constant-operand `buffer` rule evaluates exactly as the classic buffer (Sofia's 10-before/15-after run) — and the harness's stored shape, `Rule{type: buffer, operand: 5min}` (harness B1), stores and evaluates **unchanged** on this menu.

- **T5 [a buffer operand edit governs forward only — FD-79]** *(added 2026-08-29 — the founder ruling landed in `SPEC.md §3`'s buffer row with no acceptance row anywhere: T4 covers constant-buffer math only, no BUILD step named it, and the coverage map omitted it. This is the class the corpus named on R1 — the FD-15 class.)* *Given* a committed placement whose `buffer` window is **currently running** off it, *when* the `buffer` rule's operand is edited — **both directions in one run, lengthened and shortened** — *then* the running window **neither shortens nor lengthens**, asserted on the gap the running placement enforces before and after the edit; and the **next** commit is governed by the **new** operand. And assert the sibling that makes the ruling non-vacuous: a placement committed *after* the edit and adjacent to the pre-edit one is checked against the **new** operand on its own side and the **old** window on the neighbour's — the two bindings coexisting without either being retroactive. *(FD-79's home is `SPEC.md §3`'s buffer row; the harness half is `../harness/SCENARIOS.md` F6.)*

## M — Recurrence & materialization
- **M1 [materialize]** A weekly pattern materializes real instances over the horizon; each has its own id and latches.
- **M2 [edit one]** Cancelling one instance latches that instance only; siblings and pattern untouched.
- **M3 [forward-only pattern edit]** Pattern shifts Monday→Tuesday: instances carrying state (a latch, an attached party, precondition evidence) keep their day; bare drafts regenerate on Tuesday — and the superseded Monday drafts are **withdrawn** (§1.4's named disposition): capacity released, absent from every projection, rows kept in history with the `superseded_by_generation` event.
- **M4 [beyond horizon]** A booking request past the horizon materializes only the requested window, then books normally.
- **M7 [materialization cannot double-book — §9]** A one-off books week 12 (beyond the horizon, via M4's on-demand path); a pattern covering that slot is then created; the rolling job extends the horizon to week 12: the pattern instance materializes as a **conflicted bare draft** — drawing no capacity, absent from availability, carrying its structured conflict record readable through `calculate`'s stored-object member — and the capacity invariant holds throughout. Nothing is silently dropped: the conflict record is exactly what the harness's next firing surfaces.
- **M5 [DST gap]** A daily pattern at a local time erased by spring-forward (zone with DST): that day's instance materializes at the gap's first existing instant; every other day is unchanged; no day yields zero instances. *(Law: SPEC §9.)*
- **M6 [DST duplicate]** The same pattern crossing fall-back: the duplicated local time materializes exactly one instance, at the earlier-UTC occurrence, and a duration spanning the transition keeps its true elapsed length. *(Law: SPEC §9.)*

- **M8 [an `except` date over a stateful instance is registered, not stranded — §1.4, §1.15]** *(added 2026-08-29 — §1.4's `except` path had no scenario at all: M3 covers the day-shift path only, so the registered form ET-4 states was executed by nothing.)* *Given* a pattern with a materialized instance **carrying state** — a latch, an attached party, or precondition evidence — on date D, and a board with **no other scheduled firing before the horizon edge** (the condition §9 names as the one that made the silent drop possible), *when* `except: [D]` is added to the pattern, *then*: a **`TriggerRegistration` (§1.15) exists at D's instant**, asserted on the **stored registration** and never inferred from a later firing; stepping the virtual clock to D **fires it** and the instance surfaces as an ordinary parked question (`needs_human`, §1.3); the stateful instance is **not withdrawn** — it survives with its state; and any **bare** draft on D **is** withdrawn under §1.4's named disposition (M3's law: capacity released, absent from every projection, the row kept in history with the `superseded_by_generation` event) — the two dispositions asserted **side by side**, so they cannot be conflated. Assert the firing arrives as the **ordinary clock source** and that **no new trigger kind appears** (N1's law: the trigger vocabulary widens by nothing).

## P — Place-only resolve & projections
- **P1 [placement]** `resolve` returns a placement satisfying every board and rule it touches.
- **P2 [honest decline]** No placement exists: structured decline naming the refusing constraint class — never a forced fit. *(Situation-B's "no bike"; Situation-E's safe park.)*
- **P3 [site-day projection]** A `location-window` rule (Eastside only Mon/Wed): availability projections offer the day's place only. *(Debra's link; Situation-C's boat route rotation — which site the boat runs which day is the same rule.)*
- **P4 [domain refusal]** An `attribute-domain` violation (address outside service area) refuses at intake with the honest no.
- **P5 [unknown is not free — §1.2]** A proxy board with `empty_means: unknown` and no confirmations: every availability computation over it returns **nothing** — emptiness never reads as free; a confirmed window then appears, and only it is offered. *(The §1.2 law had no scenario; T3/V4 cover only the travel half of unknown-fails-closed.)*
- **P6 [the duration floor excludes at projection — and the ceiling refuses]** A kind under `duration: 30–120 min`: availability projections offer no start that could only hold a sub-minimum booking, and a forced sub-minimum commit refuses naming the rule. **And the ceiling** *(2026-08-22 — the operand's upper bound had no assertion in either suite)*: a forced over-maximum commit refuses naming the same rule, and no projection offers a span longer than the maximum as a single bookable duration — floor and ceiling are one operand, asserted at both ends. *(The engine half of harness B9 — Situation-A's minimum-duration beat and her 120-minute maximum; the commit half closes at Step 5 with the other commit-side laws.)*

- **P7 [the fallback engages for two distinct causes — and the causes stay distinguishable]** *(Situation C's flagship beat: the house boat bumped once for seats, once for route — added 2026-08-22.)* Given a kind carrying a ranked `fallback` chain (house boat → backup) and `location-window` route rules on both boards: **(a)** a goal that exceeds the top entry's remaining capacity places on the backup; **(b)** a goal whose site the top entry's window doesn't cover that day places on the backup — two placements, two different obstructions, no forced fit. And the causes are never collapsed: with the backup *also* unable to serve, run (a)'s structured decline carries the **capacity** class and run (b)'s carries **`location-window`** — asserted as different refusing constraint classes (V4's discipline applied to the fallback chain); one merged reason fails this scenario.
- **P8 [contention is deterministic, bounded, and parks honestly]** *(added 2026-08-22 — `SPEC.md §7`'s contention law had no row, while printed gate names elsewhere referred to races this family did not contain.)* Two goals firing simultaneously over the same free window: arbitration orders them **deterministically** (arrival, then stable-id tiebreak — the identical order on replay); re-solve rounds are **bounded**; and a goal that survives no round returns a **structured decline for the harness loop** naming the contention — never a stall, never a silent drop.
- **P9 [a mid-series rate edit asks its owner, and nothing re-rates silently]** *(added 2026-08-23 — FD-75 closed OR-41 as an owner ask, not a founder ruling.)* Given a standing series with materialized instances behind it and not-yet-materialized instances ahead, when the owner edits the series' `pricing` operand: already-materialized instances are untouched (§1.5's bind-at-booking, asserted unchanged); the edit writes a **`PendingDecision`** naming exactly the two choices (keep the series' founding rate / re-rate as instances materialize, from the edit forward) — asserted engine-named, unrenamed on the surface (P2's discipline); **until the answer lands, an instance materializing takes the prior rate** — asserted no silent re-rate; and each stored answer governs that series' subsequent materializations. No third choice and no default exist (asserted as absence).

- **P10 [the same store state returns the same *values*, not merely the same verdicts — §0]** *(added 2026-08-29 — §0's foundational claim was asserted engine-side only twice and narrowly (Y1 for one typed value, P8 for arbitration order), `BUILD.md`'s "determinism is a test" guardrail named no test and no step, and the one repo-level gate is recorded at `../deployment/SPEC.md §7a` row 5 as comparing **test names and statuses, not content** — so a scenario returning a different placement on replay while still passing is invisible to it.)* One run, **replayed at the identical supplied reference instant**, over the three sites §5/§7 name as the clock-leak points: a placement crossing a **travel-cache TTL boundary**, a **contended** window (P8's Given), and a window materialized by the **horizon job**. Assert the returned **values** are identical across the two runs — the placement's instants, the proposal's `moves[]` order, and the availability set's members, each compared by value. State the assertion's own floor: **a pass/fail comparison does not satisfy this scenario**, because the repo-level determinism gate compares names and statuses only; that recorded narrowing is precisely why this assertion has to be value-level here.

## X — Reshuffle proposals
- **X1 [direction honored]** Same trigger, `toward-start` vs `toward-end`: two different proposals, each improving in its stated direction only.
- **X2 [pin pre-filtered]** A pinned party's placements never appear in `moves` — they appear in `untouched` with reason `pin`. *(Harold is never even suggested.)*
- **X3 [stale proposal]** The board changes after a proposal is computed; apply-proposal re-validates and returns `{conflict}` — no partial application.
- **X4 [declined move]** One move's confirmation is `declined`: apply refuses; the board is unchanged; nothing was moved piecemeal.
- **X5 [freed fail-closed]** The proposal's freed window is unbookable while its decision is `pending`; `keep-blocked` keeps it so; `reopen` restores it to projections. *(The afternoon that stays hers.)*
- **X6 [confirmations required]** Apply-proposal with any `pending` confirmation refuses.
- **X7 [bound respected]** A compaction needing 4 moves returns the best ≤3-move proposal or a decline — never an unbounded search. *(The printed v1 bound.)*

## K — Money marks

- **K2 [marks latched]** `paid/settled` marks carry `{by, at}`; no engine operation moves value (no such entry point exists to call).
- **K3 [no-show is never engine-declared]** A commitment whose scheduled start has passed with no check-in: the engine surfaces **the fact** and **never writes a `no-show` mark of its own** — assert the absence, on the stored record, after the clock has advanced well past the start. The mark appears only from an owner act, attributed `{by, at}`; what it then costs is the commitment's no-show policy, **bound at booking** (SPEC §1.5), so a policy edited after booking does not change this instance's owed amount. *(SPEC §1.9, founder-ruled 2026-08-07 #5 — the ruling had no acceptance criterion until now.)*

- **K4 [the mark latches the money state — FD-30]** The owner marks `no-show` on a commitment whose bound policy is deposit-forfeit; the counterparty then self-cancels on a valid token: status reflects the cancel, and `owed` **still derives the forfeit from the mark** — the record never reads $0. Marks first, then state; a derived value never un-derives a recorded human judgment.

- **K5 [cross-owner money is one record on both boards]** *(Situation C's freelancer day rate — "what Hug owes Matthew"; §1.9 × §7.1; added 2026-08-22.)* A §7.1 share-seam commitment carrying `priced` at the supplier's stated day rate: `owed` derives **identically on both boards** — one record, no mirrored copy to diff (I1's law applied to money) — and the K-family laws hold across the tenant line: marks latch `{by, at}` whichever side sets them, a `settled` set by one side is the same mark the other side reads, and no engine operation moves value. Assert the boundary too: neither side's **other** ledger entries become reachable — the shared commitment's own marks are details of the record both parties stand on, never a rung over the counterparty's ledger (I3 unchanged, N5's assertion pattern).

- **K6 [`held` is unsettable until its trigger is ruled — §1.9]** *(added 2026-08-29 — §1.9's poka-yoke was written specifically to stop the obvious wrong build, "the obvious wiring is the natural build and nothing else gated against it", and had no `§10` row, no scenario and no Verify line: a builder who wired hold-creation to `held` passed this whole suite.)* A write setting the **`held`** mark **on any path that can reach a money mark** is **refused** — asserted as a refusal, the G8 pattern, never as a validation message, and asserted over the whole set of reaching paths rather than one of them. ## G — Consistency & coverage
- **G1 [governing conflict]** A rule clashing with a governing rule: hard stop, write refused.
- **G2 [own conflict]** A rule clashing with the owner's own rule: returned for the override-with-reason path — not silently applied, not hard-stopped.
- **G3 [latent]** A ruleset hitting §3's `buffer × location-window` latent row (the buffer exceeds every gap between allowed windows): the alert returns naming the row, nothing is blocked, the ruleset stores. *(Rewritten 2026-08-21 — the old Given named "an SOP-internal latent inconsistency," an artifact the engine does not store; SOPs are harness-side.)*
- **G4 [coverage structural]** `check_coverage` flags a missing required attribute; it makes no semantic-completeness claim.
- **G5 [unsatisfiable outranks authority]** A pair marked ***unsatisfiable*** in §3's clash table — run it for a time-denominated `duration × quota` and for `duration × location-window`, both authored at **individual** authority — is **refused at write** and is **not** returned on the override-with-reason path. Assert the override path is unreachable for these, and that the refusal carries the naming message. *(The G2 own-rule case proves the opposite routing for a genuinely overridable pair; G5 is the line between them. The old second exemplar, `dependency × pin`, died with the pin disambiguation — a pin no longer touches bookability.)*
- **G6 [the refusal names the fix]** Every unsatisfiable refusal carries both offending operands and the remedy — never a bare "invalid ruleset." *(SPEC §8; the `../model/SPEC.md §6` decline voice, enforced engine-side so it holds with no model in the loop.)*
- **G7 [the class does not over-apply]** Three rulesets that **look** unsatisfiable and are not, each asserted **storable** — written as positive tests because an over-broad `unsatisfiable` fails by refusing something valid, which no refusal-side assertion can catch: **(a)** a composition whose draw exceeds capacity only for *larger* bookings (`capacity × dependency` above its minimum) stores, and oversized bookings refuse at commit per A1; **(b)** a **count-denominated** `quota` ("max 3 lessons a day") beside a `duration` rule stores — the pair shares no evaluated quantity (§3's unit guard); **(c)** a ranked `fallback` chain whose top choice is `pin`ned stores and resolves normally — a pin constrains moving, never booking. *(Re-cut 2026-08-21 from the single pin case to the three survivable look-alikes.)*

- **G8 [off-menu unstorable — §1.4, §1.5]** An off-menu rule `type` and an off-menu recurrence `shape` are each **refused at write as a storage fact** — asserted as refusal, not as a validation message; nothing off-menu is ever reachable at evaluation because it was never storable. *(Both laws were stated twice and tested nowhere; the rule-type half closes at Step 3, the recurrence half at Step 6.)*

## I — The cross-owner share (SPEC §7.1)
*Parity family: `../harness/SCENARIOS.md` I1 asserts the harness half (the path is the ordinary loop, no separate harness invoked); these assert the engine half.*
- **I1 [engine parity with harness I1]** Two on-app owners, one books the other: `resolve` (over the counterparty's exposed availability) + accept + `commit(offer_ref)` yield **one creator-owned commitment standing on both boards in one transaction** — no mirrored second record exists to diff. **No function outside the §1 seam set is called** — asserted as a walk of the contract, which is what makes the swap law survive this feature. *(The engine-side mirror of harness I1 — the two must agree or the swap is a lie.)*
- **I2 [both boards or neither]** The counterparty's board fails a check at commit time (a buffer violated by a placement made since the offer): **the commitment appears on neither board**; `{conflict, reason}` returns — reason and alternatives bounded to the exposed availability (§7.1 item 3: the initiator learns *taken*, never *why*); the **offer ends** and the terminal state is a **recorded attributed event**, not a status value (I7's record). *Assert the commitment's status reads as one of `../harness/SPEC.md §3.4`'s values — the terminal event releases the hold, so the `offered` condition no longer derives (§3.4's conflict-case rule) and no latch was set — and that **no fourth value** appears for the conflict; a run that invents one fails this scenario.*
- **I3 [no read power added]** Throughout an offer, every value the initiator's side can observe about the counterparty is derivable from the `availability` grant (the published Shared projection). No commitment, rule, party, name, or money mark of the counterparty is reachable without a higher rung they granted — asserted as a walk of what the seam returns, not a runtime sample. *(The S1 board-blind guarantee, re-asserted across the tenant line.)*
- **I4 [caller cannot author a crossing]** A caller-supplied structure naming a second tenant is a type error; a **ShareGrant** is engine-minted or it does not exist *(qualified 2026-08-21: the §1.6 authorization Grant is harness-elicited under FD-24 and is not this edge — the unqualified sentence conflated the two shapes §7.1 separates)*. Asserted structurally against the contract — there is no entry point to call.
- **I5 [silence never binds]** An offer that is never answered reaches `expired` on the virtual clock when its hold runs out: the commitment stands on no counterparty board, a recorded terminal event on both.
- **I6 [the hold is the creator's setting]** While an offer sits `offered`, the targeted window is **held for the offer's `hold` duration** (default 5 minutes; creator-set 0–24 h) and then freed. With `hold: 0` the window stays bookable and the first commit wins. A racer against a zero-hold or expired offer loses with `{conflict, reason, alternatives}`, alternatives drawn from **exposed availability**, never the board.
- **I7 [terminal states recorded both sides]** Decline (with its structured reason), expiry, and conflict each write an attributed `{who, basis, when}` event to **both** boards and place the commitment on neither. *(`../security/SPEC.md §9` N3, made testable.)*
- **I8 [a live unanswered offer cannot commit — §6.5 b]** The initiator calls `commit(offer_ref)` while the offer sits `offered` with no stored accept: the commit **refuses** — the accept-gate is checked, not vacuously satisfied through an empty `moves[]`. *(Before 2026-08-21 the accept requirement lived only in §7.1 prose and the moves-check was vacuously true for every offer; I5 tested silence via expiry only.)*
- **I9 [the offer's zone is the initiator's]** *(Carved from Y1 2026-08-22 — the arm's Given needs this family's Step 8 machinery, which Y1's row cannot cite.)* A §7.1 cross-owner offer resolves its time phrase in the **initiator's** board's declared home zone (`SPEC.md §1.2`'s goal-zone rule), while the counterparty's page displays the same instants in their own zone — one stored truth, two zone renderings, asserted side by side.

## W — Multi-day decomposition (SPEC §7)
*(Letter `W`, not `D` — this file cross-references the **harness** D-family, the floor, and two D-series would be unreadable.)*
- **W1 [per-day calls]** A four-day course resolves as four single-day `resolve` calls composed by an Order — no multi-day search exists to call. *(Situation C's flagship.)*
- **W2 [partial placement survives]** Day 3 declines; days 1–2 handles remain valid and independently committable. Nothing is rolled back, because nothing was written.
- **W3 [which days placed]** The result names, per day, a placement or a decline carrying its refusing constraint class — never a bare partial.
- **W4 [all-or-nothing is the caller's]** The same day set committed as one Order applies atomically: a day-4 failure leaves days 1–3 uncommitted. Committed individually, they stand independently. Both paths exist; the engine picks neither.
- **W5 [template expands to ordinary objects]** A four-day `KindTemplate` (SPEC §1.12) instantiates to four Commitments under one Order, sequenced by `depends_on` per `requires`. **No object type exists in the result that a hand-authored course would not produce** — asserted structurally. *(F7's resolution, made testable.)* This is *expansion*-equivalence (template → objects). Its **authoring**-equivalence twin — an agent-authored *bundle* ≡ a hand-authored one — is FR38's instance and lives in `../marketplace/SCENARIOS.md` I6, because the engine is deliberately not marketplace-aware (`INTERFACES.md`); FR38's "W5 (agent-authored ≡ hand-authored)" citation points back to the principle stated here.
- **W6 [relative offsets]** The same template expanded against two different anchor days produces correctly-dated session sets, with no stored absolute time anywhere in the template.
- **W7 [role binds at expansion]** A template naming a `board_role` ("a boat") binds to a concrete board at expansion; the template is unchanged and re-expands against a different fleet.
- **W8 [template edit is forward-only]** Editing a template leaves already-expanded courses untouched — mirror of M3's pattern-edit law.
- **W9 [a spanning consumption rides the course]** *(Situation C's "tagged once, theirs for the whole course"; added 2026-08-22.)* An Order combining per-day session commitments with each member's gear as **one commitment spanning the course days on one unit** — the Situation-B rental shape, no object type W5's law forbids — behaves as the story requires: no day re-draws from stock, the unit never re-enters availability mid-course, and cancelling through the Order path (W4) frees the whole span at once. Asserted structurally: per member, one consumption row spanning four days — never four daily draws.

## V — Travel envelope (SPEC §5)
- **V1 [ceiling]** A placement whose candidate set would need more than the fetch ceiling makes no further fetches: remaining legs are unknown and fail closed. The search declines; it never stalls.
- **V2 [dedup + batch]** Many candidate instants over the same place-pair and time-bucket produce **one** provider request; the scripted provider's call count is asserted.
- **V3 [cache hit beats fetch]** A second placement over a cached `(place_a, place_b, bucket)` makes no provider call and returns the identical duration.
- **V4 [the two declines are distinguishable]** A day that is genuinely full returns `no-feasible-placement`; a day the provider failed on returns `travel-unknown`. Asserted as different structured reasons — collapsing them fails this scenario.
- **V5 [a cold day warms, and says so]** *(added 2026-08-22 — SPEC §5's warm-then-re-offer: without it, every board's first location-aware placement declined by construction.)* A cold-cache Situation-D day whose candidate set exceeds the fetch ceiling: the decline's unknown legs carry `travel-unknown` with `detail.cause: ceiling` — distinguishable from a provider outage's `detail.cause: provider-failed`, V4's discipline one level down, with the closed reason set unwidened — the cut triples are resolved by the background warm-up, its completion fires the clock source, and the follow-up resolve **places** with no fresh provider calls beyond the warmed cache (V3's assertion closes the loop). A flat decline with no warming path fails this scenario.

- **V6 [a commit makes zero provider calls — §6.1]** *(added 2026-08-29 — §6.1's named hard law had no `§10` row, no Verify line and no scenario, while V2 already proved the assertion is cheap.)* *Given* a commit whose travel-computed `buffer` gap **misses** the cache, *then*: the scripted provider's call count is **zero** (V2's assertion pattern); the gap is `unknown` and the commit **fails closed** — the placement is refused, never accepted on an assumed gap; and **no cache fact is written** by the failed commit, asserted on the stored cache, which is the half that makes a failed commit side-effect-free. Assert the contrast **in the same run**: the identical placement through `calculate`/`resolve` **does** fetch, because §5's fresh-fetch rung belongs to the read path — a build that simply never fetches anywhere passes the first half and fails this one.

## N — The trigger registry (SPEC §1.15; the bridge at `INTERFACES.md §2.2`)
*(Family added 2026-08-22 — §1.15 existed with no scenario, no build home, and no stated bridge to the harness clock; V5's warm-up, the hold clocks, the horizon job, and the FD-53 age-out all ride it.)*
- **N1 [armed, fired, ordinary]** A stored `TriggerRegistration`'s `fire_at` arrives (virtual clock): the substrate trigger fires and surfaces as the harness's **ordinary clock source** — the firing carries the registered ref, and the trigger vocabulary widens by nothing (`../harness/SPEC.md §4` stays six sources).
- **N2 [re-register replaces]** Re-registering the same purpose with a new `fire_at` replaces the arming: exactly one firing, at the new instant, never two.
- **N3 [withdrawn or orphaned, inert]** A registration withdrawn through its `scheduler_handle` fires nothing; a firing that finds its registration gone (removed between arming and fire) commits nothing and parks nothing — inert by law (`SPEC.md §1.15`: nothing evaluates against a registration). *(The commits-nothing arm closes at Step 5, when `commit` exists to be wrongly reached.)*

## O — Minimum occupancy (SPEC §3 `min-occupancy`)
- **O1 [early booking never blocked]** The first booking on a boat with `min-occupancy: 4` commits normally. Being below the minimum is never a reason to refuse a booking.
- **O2 [clock trigger, owner decision]** At `start − decide_by` with 2 of 4 seats confirmed, the engine **writes the `needs_human` park and a `PendingDecision` (SPEC §1.14)** and stops there; the harness's trigger loop reads it and the run **parks for a human**. The engine cancels nothing and notifies no customer on its own. *Assert the record is a `PendingDecision` carrying its three engine-named choices (run under minimum / cancel / extend the window), readable through `calculate` with no new seam verb, and that **no engine path writes `chosen`** — a run in which the engine picks, defaults, or times out into a choice fails this scenario.*
- **O3 [minimum met, silence]** At the trigger instant with 4 of 4 confirmed, nothing fires and nothing is surfaced.
- **O4 [unsailable clash]** `min-occupancy.min` greater than the board's `capacity.N` classifies **unsatisfiable** at `check_consistency` (SPEC §8 item 4) and is **refused at write even though both rules are the shop's own** — not offered on the override-with-reason path, because no override could make the boat sailable. The refusal names the fix. Discovered at authoring, never at sea.

## Y — Typed values (SPEC §2)
- **Y1 [instant resolution — FD-27; propose-then-verify per FD-57]** `typed_value` resolves a raw time phrase — arriving as `{phrase, proposed}`, the model's proposed structured value beside the raw words — to an `instant`/`interval` against a `type_spec` carrying `{zone, reference_instant, locale}` (§2's resolution-context rule), **by verification: the proposal re-rendered into the locale and zone must match the phrase's components, asserted as a round-trip** — a proposal that renders to a *different* Thursday, hour, or period is refused as a `typed_value` error, never accepted on plausibility: *"Thursday 3–4pm"* (`locale: en`) with zone `Asia/Bangkok` and a Tuesday reference yields that week's Thursday 15:00–16:00 as zone-resolved instants; the identical inputs yield the identical result on replay; the Thai phrasing **"บ่ายสามถึงบ่ายสี่วันพฤหัสนี้"** (`locale: th`) and the zh-TW phrasing **"這週四下午三點到四點"** (`locale: zh-TW`) of the same time resolve to the **same instants** *(operands printed 2026-08-21 — an equivalence asserted over unprinted inputs has nothing to code against)*; a phrase resolution cannot settle (*"sometime soon"*) returns a `typed_value` **error**, never a guess — and nothing in this path reads wall time. **And the two-zone case** *(2026-08-22, §1.2's goal-zone rule)*: a goal whose `consumes` spans two boards with different declared home zones resolves the phrase in the zone of the first-consumed board under the goal's declared ordering — assert that choice *(the §7.1 cross-owner arm is carved to I9, 2026-08-22 — its Given needs Step 8's share machinery; this row stays whole)*. *(The engine half of the thin-agent time law: the model passes the phrase raw, `../model/SPEC.md §5`.)*
- **Y2 [a literal cannot sit in a handle-typed position — §2, §4]** A write whose handle-typed field carries a raw literal (a display-facet string re-entered, a fabricated id) is a **type error** before any math runs — the structural half of thin-agent, asserted directly. *(I4 covers only the tenant-crossing case; the general law had no scenario.)*
