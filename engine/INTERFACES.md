# annnä Engine — INTERFACES (the seams)

*Three seams: **upward** (satisfy the contract the harness already pinned — `../harness/INTERFACES.md §1`, verbatim), **downward** (what the engine itself depends on: a travel source and a storage substrate), and the **sideways display-projection seam** (§2a) — the five `SPEC.md §0` projections, three pushed by subscription and two read on demand *(re-counted 2026-08-28 with §1.7c, FD-85)*, which the app renders verbatim, never computing a time, gap, or availability itself *(header re-cut 2026-08-22: it previously named only "a handle's display facet", the pre-§2a shape)*. **Affected-commitment compatibility uses the existing verbs.** `SPEC.md §8`'s second result rides the **existing** `§1.3 check_consistency` return as its **third member, `compatibility`**, beside `conflicts`/`latent` — no new seam verb, no fourth `check_coverage` kind and no extra call before a write. It is `Compatibility | null`: `null` for a call that declares no candidate, and `null` is never clear (only an empty `blockers[]` is). It is declared by the **optional second argument** and never inferred from the first: the caller passes a `CandidateDeclaration` carrying the proposed rules' identities and the one `effective_scope`, while the first argument keeps carrying the proposed rule content unchanged; a call without that argument is the legacy noncandidate request, and a present declaration missing `rules`, a `revision`, `effective_scope`, or disagreeing with the first argument about which rules are proposed, refuses the whole call rather than degrading to `null`. Its members are **computed** from that declaration's `rules` — one entry per rule the submission proposes, each `rule_ref` with its expected `revision`, under one `effective_scope` — and the stored commitments: which records block that candidate, which of its **own** member rules each record fails with the complete `SPEC.md §3` operand, the engine-named resolutions and the `store_version` the verdict was computed against. **The harness supplies none of them as a call parameter** — no blocker list, no exemption, no grandfathering flag and no authored resolution — and a consumer that treats an empty `blockers[]` from an earlier call as still true at apply is reading a verdict past its `validated_at`, which `SPEC.md §6` refuses at the write. **`commit` gains no declaration member either** *(2026-09-12)*: the write-path recheck at `SPEC.md §6` item 1 forms the `CandidateDeclaration` from the rule diff it is applying — that diff's own rule refs, the expected revisions the write already re-validates (`new` for a created rule) and the proposed rules' declared scope — and calls **this same verb** with it, so the `../harness/INTERFACES.md §1.2` `commit` input shape is unchanged and no candidate, blocker, exemption or scope parameter crosses the seam on a write any more than on a read. Every commit carrying a rule diff enters that recheck, including one that only creates or enables a rule; a diff covering no live or future commitment is not skipped, it comes back with an empty `blockers[]`. **Neither the candidate nor this verdict is engine-stored** *(2026-09-12)*: the engine mints no candidate id and writes nothing for a refused apply beyond §6 item 6's existing apply record, so there is **no** new `§1.1` read payload and no candidate read verb here. The retained candidate lives at its existing home, the app account-document adapter's operation record (`../marketplace/SPEC.md §3`), with the settled definition-branch answer beside it on the harness's own draft carrier (`../harness/INTERFACES.md §3.1`); resuming means re-calling this verb over what that record retains, not reading a stored verdict back.

## §2. Downward — what the engine depends on

### §2.1 The travel source (external compute)
```
travel({origin, destination, mode, timing: {kind: arrive-by | depart-at, instant, zone},
        reference_instant}) -> estimate | unavailable
estimate = {request_identity, duration, departure, arrival,
            source: {provider, adapter_revision, obtained_at, valid_until}, freshness}
```
- Derived from `SPEC.md §5`: origin/destination are ordered typed places with selected revisions; duration and dated instants are engine-typed. Only the engine calls the provider and validates its result. Harness/app consume its Handle and display facet, never provider numbers as write literals. Unavailable remains an explicit result under the existing envelope, with no fabricated duration/departure.
- Precedence and fail-closed behavior: `SPEC.md §5`. Provider identity is config (BUILD), like a model binding — swappable without spec change.
- **Stub:** script the full request identity and source/freshness fields from `SPEC.md §5`, plus explicit unavailable/unsupported responses; count both distinct identities and batched calls. Inject the reference clock, different modes, same-bucket different instants, arrive-by/depart-at, different dates/zones, changed place/provider revisions and expiry boundaries. Every SCENARIOS run uses the stub. These controls prove adapter/cache behavior only; serving capability is owed at BUILD Step 4.

### §2.2 The storage substrate
Tech-neutral requirements (candidates named in `BUILD.md` only):
- **Atomic multi-object transactions** (one commit = one transaction, `SPEC.md §6.1`), including the chosen coordinated rule diff under §8; member authorization, resulting-set validation and all attributed rule writes succeed together or none do. Store/read complete `Rule.operand` shapes under §3, preserving the legacy leaf and duration aggregate through versioned readback.
- **Recoverable firing ownership** (`SPEC.md §1.17`; behavior `../harness/SPEC.md §4a`): arbitrate current ownership, invalidation and recovery in the existing store, check ownership inside each new work/loop transaction, and couple pre-birth release with one attributed loss record. Preserve post-birth interrupted continuations, scoped apply-result replay and already-authorized receipt writes. The harness-facing adapter must use this authoritative state to fence actual dispatch, reach running work with existing stop controls and release requests at durable asks. No new service or seam verb; lease/heartbeat or proved-equivalent mechanics remain adapter design, with injected-time/two-worker proof at `BUILD.md` Steps 5/9 and the harness Steps 5/8.
- **Append-only writes** with attribution (diffs, `SPEC.md §1.10`); no delete primitive exposed above the substrate.
- **Per-object version chains** for point-in-time reads and handle staleness checks (`store_version`).
- A **clock trigger** facility for holds and horizon extension (virtual/steppable clock in tests). **The trigger-registry bridge lives here** *(2026-08-22 — seam law at the seam)*: a `SPEC.md §1.15` TriggerRegistration's `fire_at` is armed on this facility, and the substrate's firing surfaces **as the source its kind maps to** *(the kind-routed mapping, 2026-08-31)*: `offer-hold` → the `hold-expiry` source · `reminder` → the ordinary `clock` source · `ask-age-out` → the ordinary `clock` source · `escalation-deadline` → the ordinary `clock` source — and a registration carrying **no harness `kind`** (the engine-internal writers: `min-occupancy`, the conflicted-draft instant, the `except`-stranded instance (including a stop boundary under §1.4), the horizon job and V5's warm-up) surfaces as the harness's **ordinary clock source** exactly as before (`../harness/SPEC.md §4`'s source roster unchanged by this clock mapping — the mapping selects among existing members, and the harness never learns a NEW trigger kind); `scheduler_handle` is the substrate's cancellation token, a withdrawn registration cancels its arming, and a firing whose registration is gone makes **no business-state write, park, or ask; it appends only its own attributed no-op record**, identified by the firing registration and §1.10's history (`SCENARIOS.md` N1–N3). Reminder registrations carry the booking/policy revisions and grant reference from `SPEC.md §1.15`; that home owns transactional replacement, withdrawal and replay. Escalation creation/advance is the harness writer for the proposed escalation kind (`../harness/SPEC.md §3.13`; notice at `../harness/INTERFACES.md §7.2`), separate from those internal writers. Its rung/total identity remains stored, reached through the callback ref; cancellation, stale-rung rejection and the independent total cutoff follow that home, regardless of listener ordering. The clock callback carries the existing registration ref, through which current state is reread; it never supplies an independent authorization snapshot. Unused-pass custody/cleanup follows `../security/SPEC.md §3` on its existing internal storage path; it is not a TriggerRegistration writer or a new scheduler/harness event.
- **Reactive push to subscribers** *(founder-ruled 2026-08-06; numbered **FD-90** on 2026-08-29 — the ruling is unchanged, the label is what lets a restatement cite it)* — when a committed write changes a published display projection (§0's sole-client carve), subscribers are pushed the new value; the app never polls for it. This is a **hard criterion, not a preference**, and it is the one a reader is most likely to skip: a store can satisfy every row above and still be non-reactive, at which point `../app/INTERFACES.md`'s live board and app scenario Z3 ("board updates live") quietly become a polling loop nobody specified. The ruling exists precisely so a non-reactive substrate cannot be picked by accident.

## §2a. Sideways — the display-projection seam *(2026-08-22 — the header above promised three seams and the body specified two; this is the one the app builds its home screen on)*

The **five** projections `SPEC.md §0` enumerates — the guest Shared projection, the owner's live board view, the FR38 template-bundle projection, the FD-34 candidate-shape ghost, and the **effective-policy projection** (`SPEC.md §1.7c`) — are this seam's whole surface; **a sixth is a spec change with its own ruling**, exactly as a sixth seam verb would be. *(The sentence required a ruling for a fifth projection and has one — **FD-85 (PROPOSED)**, 2026-08-28, whose home is `SPEC.md §1.7c` — and it stays true unchanged for the next one. The ruling is the founder's to ratify or strike; until he does it gates the build as written, FD-91.)* **Two transports, one fenced family** *(sentence added 2026-08-22 — `SPEC.md §1.7a` and this section previously read as giving the bundle both; re-counted 2026-08-28 with §1.7c)*: the guest Shared projection, the owner's live board view **and the effective-policy projection** are **subscription** members (§2.2's reactive push, the rules below — three of them); the template-bundle projection and the candidate-shape ghost are **read-on-demand** members — the bundle invoked as an internal `calculate`-class read (`SPEC.md §1.7a`), the ghost computed when the store surface asks and never stored *(the caller's home is `SPEC.md §5` item 7 — the ghost is a member of the closed query taxonomy, read through the harness like every declared shape; this sentence is transport only and cites that home, per FR13)*. Three pushed, two read on demand. The bundle read is only the data-free publication projection; private configured definitions and their revisions persist through the app account-document adapter (`../marketplace/SPEC.md §§2–3`), never a new engine read/write, table or projection. A publisher-choice duration carries the full typed range/step/anchor under `SPEC.md §§1.7a/3`; private retained operands cannot be recovered from a blanked snapshot.

- **A board subscription carries its queried window `{from, to}`** *(2026-08-31 — the member `../app/SCENARIOS.md` C6 gates on, printed seam-side at last)*: a request names its window, bounded exactly as `SPEC.md §5` rules; a window reaching past the loaded horizon **is** §9's beyond-horizon request. §5 declares the tenant-scoped preparation writes under §1.4 before cache-only projection computation; unloaded time is unknown, never free. This direct subscription creates no harness firing; its completed chunks survive cancellation/crash with engine history under §5. Harness-requested preparation instead requires `../harness/SPEC.md §3.14(b)`'s durable birth and current claim, through the existing seam. The same window/reference-instant replay with unchanged stored inputs — including tenant authorization, Pattern definitions and generations, existing instances, terminal history, dated exceptions and relevant trigger registrations/cache facts — creates no further rows, history, registrations or cache facts; a matching window and reference instant with changed inputs, especially a changed Pattern or generation, is a new request, not the same replay.
- **Every pushed value carries `{store_version, projection_id}`.** The app **discards any payload whose `store_version` is older than what it already holds** — one rule that kills the merge ambiguity in both directions, because the board has two content sources: `render(board, payload)` from the harness sets the *surface*, the projection sets the *contents* (`../app/SPEC.md §1` carries the same sentence). A `render` payload computed at version N arriving after a push at N+1 does not repaint the board backward. Owner projections additionally carry `applied_revisions[]` with the exact `{applied_ref, committed_revision}` associations from `SPEC.md §5`, including the coalesced/recovered-write case. The commit producer returns that same pair through the existing harness seam (§1); neither a newer global version nor the same object ref alone establishes it. The app consumes the association under `../app/SPEC.md §2`, while the existing privacy/selectability fences remain unchanged.
- **A subscription carries `unavailable` as a member.** A subscription that goes quiet is a *state*, never an empty board — the app renders *stale, reconnecting* (`../app/SPEC.md §1.1`'s never-lies-about-progress law reaches here). A handle's `expires` governs commit redemption (`SPEC.md §4`), not display; a displayed facet does not blank on expiry, it re-reads.
- **A projection stub ships with the engine's stub** so the app suite can exercise subscription, push, staleness-discard and the `unavailable` member without a live store — the same stub discipline §4 applies to everything else. At the existing harness tool/loop and app board/swap BUILD gates, extend the stateful commit/projection doubles together to supply and replay the §5 associations, including out-of-order, unrelated and same-object updates.
