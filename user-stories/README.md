# User Stories (the situations the product must satisfy)

This folder holds the **real, end-to-end stories of how people actually use annnä.** It is the product's **falsification-probe corpus** — what every scenario must derive from and be refutable against. **The requirements register is [`PRD.md`](../PRD.md)'s `RQ-##` series (FD-35, ruled 2026-08-21)** — this file previously called itself "the requirements source-of-truth" while `AGENTS.md` gave that to the PRD, two SPEC-tier files with no tiebreak; the split is now: requirements live in the PRD, and the Situations are the probes that test them. A Situation beat with no covering scenario is a derivation defect; an RQ no Situation exercises is a probe gap — both directions now have a name. It is deliberately *not* the tests: the per-layer acceptance suites (each layer's `SCENARIOS.md`, and the model's `EVALS.md`) are **derived from these stories**, and [`TDD.md`](../TDD.md) states what kind of executable test each criterion becomes. Stories first, tests after — both now written.

**What these files are:** the full narrative of how each kind of user works with annnä, plus the **situations** that matter — both the things that **must work** and the things that **must be refused** (poka-yoke tested from the outside).

**Why these stories exist:** each Situation explains **how somebody works in real life today, without the app** — the phones, paper, memory, and message tag of its current-reality run — against **how that same person will use annnä to improve their life**, told top to bottom (set up → publish → book → change → settle). **The gap between those two tellings is the product**, and the edge runs around them mark its boundaries: what must work, what must be refused, and (in Situation C) the realistic middle where only part of the world is on the app yet. All of it exists **to help design the parts of this application** — the **harness**, the **model**, the **engine**, and the **app** — each layer *derived* from what these stories require rather than invented and justified afterward. *(Mechanisms that run the other way — designed first, story owed — are not papered over: each is named in the **invented-and-justified register** below, with its justification and the beat it owes.)*

**What these files are NOT:**
- **Not tests.** We describe the *situations* a test would need to cover; the executable tests are not written here. What kind of test each criterion becomes is decided in [`TDD.md`](../TDD.md).
- **Not decomposed here.** The per-layer decomposition of these stories lives in each layer's own `SCENARIOS.md`, not in this folder.
- **Not v1-scoped.** The stories tell the **end-state product**. **Five named gaps** *(1–2 founder-ruled 2026-08-06; 3–4 added 2026-08-22, the epics-audit residue sitting; 5 added the same day, the fork sitting FD-60 — both preambles in `../RULINGS.md`)*:
  1. Wherever a story shows annnä itself sending over WeChat / Messenger / SMS or buzzing a phone (Situations A, C, D), v1 delivers that same moment as **email sent by the app, or the owner tapping Generate Link and pasting into that channel themselves** (`../app/SPEC.md §6/§9`). The depicted auto-sends are later additions behind the same seam — only the *who presses send* differs in v1.
  2. Wherever a story shows annnä **referring a customer out to a center it holds no prior relationship with** — the agent handing a stranger a customer and passing their data (Situation C's German / Drysuit hand-offs through the agent) — that **referral flow is deferred post-v1** (`../engine/SPEC.md §7.1`). What v1 *does* reach is every supplier **already on annnä**, across account lines, through the **share seam** (one creator-owned commitment reaching boards annnä already holds an availability grant from — `../engine/SPEC.md §7.1`) — so v1 is **not single-tenant**; only the reach to *strangers* is deferred.

  3. Wherever a story shows the **app chrome running in the owner's language** (Ploy's and TingTing's "app language Thai; the app runs in that one language throughout"), v1 chrome is **English** — a deliberate scope line (`../app/DESIGN.md §Language`). What *is* in the owner's language at v1: FR32's catalog surface, and every guest-facing surface per FR15's stored ranked set. The depicted localized chrome is a later addition. **And the guest-language copy is hand-authored, not translated (FD-56, 2026-08-22):** where TingTing's story reads as translations appearing, v1's mechanism is the owner authoring each ranked language's copy themselves through the ordinary seam (`../app/SPEC.md §5`'s production path) — no model translation call exists, and a fifth model call would be a spec change with its own ruling. The story beat is end-state; the authoring cost is v1's, said out loud.
  4. Wherever a story shows **bulk or non-calendar import** — Sofia's Flow cycle-tracker, TingTing's spreadsheets and contacts — v1 imports **calendar data only**, from the FR36/FD-37 provider set (`../app/SPEC.md §9`, built at `../app/BUILD.md` Step 6a). Non-calendar import has no ruling and no mechanism: it is a named gap, not an implied feature.

  5. Wherever a story shows **the whole week placed in one pass against a live view of the whole market** (Situation C's situation-1 and its README ceiling paragraph), that omniscient single pass is the **demonstration's ceiling, not the shipped mechanism** (FD-60, 2026-08-22): the engine places per goal — chained per-day greedy first-fit with honest structured declines (`../engine/SPEC.md §7`) — and the honest v1 run narrates declines and asks the owner at each dead end. A global multi-goal optimization pass has no ruling and no mechanism: a named gap, not an implied feature.

  As with all five gaps, the stories stay true as written; only the *reach*, the *who presses send*, the chrome language, the import span, and the placement's omniscience differ in v1.

## How to read
**Every use case is a `Situations/Situation-<slug>/` folder** — read that folder's README first, like a storybook. The folder shape is the same whether the use case is a **single protagonist** (Situation-A, Sofia) or a **market of many stakeholders** (Situation-C, the dive): a `README.md` storybook, the **setup stories** (how each actor sets up — `resource-*.md` / `operator-*.md` / a protagonist's own telling, plus `customer.md`), and the numbered **situation runs** (`situation-1.md …`, each a floor / ceiling / probe with a stated purpose). `_briefs/` holds the probe-elicitation briefs — the input a Situation folder is built from, kept for provenance, **never authoritative once the Situation lands.** Two kinds live there and `_briefs/README.md` explains the difference: one was written *after* its sitting as the record of one, and the rest were written *before* any sitting, from the coverage debt, so their lists are questions to ask rather than answers. A brief that answers its own questions has become a script, which the provenance vocabulary below already names as the thing that cannot count as coverage.

[`COVERAGE.md`](COVERAGE.md) is the folder's coverage index: every Situation beat against the layer that owes it, plus the exhaustive audit of every bolded phrase in every story file and what disposes it. Read it to find out whether a beat is covered, owed, deferred, unruled or deliberately empty — and read it before concluding that a layer has no obligation on something.

## Principles that apply here
- **Use cases are falsification probes, never design targets.** Capturing them as stories and tests is exactly right; designing a layer *to* one of them is not (the meta-principle). If a story breaks the model, it reveals a missing *general* primitive.
- **The Situations are the founder's proof scripts, not dev deliverables (FR37/FR38).** Each is **acceptance evidence for the founder's own admin runs**: he validates a domain design by building it *as a user* through the app, proving any user could — so **no founder ruling is owed on domain content** (FR37, `../RULINGS.md`), and **Claude/developers never implement a domain design as a deliverable** (FR38). The mechanisms these stories surfaced — template expansion, min-occupancy, holds, grants, precondition-parks — stay **platform law** under *keep the mechanisms, strip the authorship*; the domain content they carry is user-built proof. The stories are **never deleted**. This sharpens the probes-not-targets line above, it does not replace it.
- **Provenance of a shipped default (FR38).** Where a production default ships for one of the v1 Situations A–D, the administrator-origin wording these setup stories use names its **provenance**, not a second authoring path: such a default exists only because the founder, as administrator, authored it through the same general template builder any user uses — never a developer-authored vertical schema (FR38, `../RULINGS.md`; the authoring law's home is `../marketplace/SPEC.md §2`). Story wording does not itself decide which named templates ship — FR38 makes that the founder's prove-through-the-app act — and Situation E's material stays held-out prediction either way.
- **Held-out / out-of-sample:** the **ER scheduler (`Situations/Situation-E/`)** is a deliberate stress-test — the harness was **not** designed to it. It exists to test whether annnä's general primitives absorb a domain they never saw. Treat its situations as predictions to check, not requirements the harness already claims to meet.
- **Situation E is the *only* held-out probe, and it stays out of v1** *(founder ruling, 2026-08-06)*. **v1 = Situations A–D.** This is not a scoping convenience — it is what keeps the probe worth running. E is the corpus's one unbiased check on whether the design generalizes, and **the moment E becomes a requirement, it stops being able to tell us anything**: a target you build toward can only ever confirm you built toward it. Do not promote E's "must work" lines into acceptance criteria, and do not let a build gate cite them.

**The failed-probe rule (what happens when a prediction turns out false).** A held-out probe that fails is the probe **succeeding** — it bought information. So a failure must land somewhere durable, or the information evaporates:

1. **It is written up as a finding**, not a bug: *which general primitive is missing*, in the vocabulary of the atoms. Never *"patch annnä for the ER"* — a domain-shaped patch is how a general system quietly becomes a vertical one.
2. **It gets a named owner.** A finding with no owner is a note, and notes do not get revisited.
3. **It gets a revisit trigger** — the concrete condition under which it is reopened (a real user in that shape; a second probe failing the same way; the primitive being touched for another reason). "Later" is not a trigger.
4. **It is recorded pass *or* fail.** Recording only failures makes the probe's result unreadable later: a silent probe is indistinguishable from one that was never run.
5. **Nothing is designed toward it in the meantime.** The finding sits, honestly, as a known limit.

**The four shapes E was deliberately not designed to** — *type-match admission · a losing/competitive request · re-solving an already-active commitment · an ordering over principals* (`Situations/Situation-E/README.md`) — are the ones this rule exists for. **They have not failed; they have not been run**, because running them needs a built harness. Recording them as failures today would be inventing a result. When the harness exists (`../harness/BUILD.md` Step 6, the J-family), each gets its row under the rule above.
- **Money is tracked, never moved.** annnä holds the *records* of money — priced, owed, paid, held, settled — written where both sides can see them; the actual transfer (cash, bank, a shop's own card machine) always happens outside the app and is *marked* settled inside it. No payment rails exist today and no story may assume them (integrating Stripe or local rails is a possible future, not a premise).
- **Changing the rules never rewrites the past.** An operator can reshape their template — prices, hours, buffers, a course — but commitments already made **keep the terms they were made under**; the change applies only forward (new bookings, next pull, next month). No story may show a live commitment silently re-priced or re-shaped by an edit made after it.
- **Two conversion engines.** Customers convert because their history is already waiting (Jun Wang opens an account and finds his logbook — Situation-C 1); suppliers convert because every phone call annnä had to *prepare* instead of place is a named prospect (the invite beat — Situation-C 5). Stories should show the network growing through use, not assume it grown. *(The customer-side mechanism is specced since FD-46, 2026-08-22: a verified-channel claim — `../security/SPEC.md §2` — and the logbook is the union of what his own tokens already showed, assembled on the new account; the supplier side is the invite path, harness O-family.)*
- **The console gold-reference:** `Situations/Situation-A/story-sofia.md` is the canonical telling of what *talking to annnä* feels like — the conversational forms, the agent's questions, the consent gate. Other setup stories may summarize the console; Sofia's is the one that renders it.

## How this folder changes

This folder's prose is load-bearing for other layers, and it is load-bearing *because* the corpus's citation law is right: `../AGENTS.md` forbids citing an in-repo line number and mandates **quoting the phrase** instead, so a pillar scenario proves its derivation by carrying story prose **verbatim**. `engine/SCENARIOS.md` does exactly that and cites no path at all. Rewriting a sentence for depth can therefore void another layer's derivation record with every gate still green — nothing fails, nobody finds out. Three rules answer that.

1. **Identifiers are frozen, and additions append.** No `Situations/Situation-<slug>/` folder is renamed, no `situation-N.md` is renumbered, and no file here is deleted or moved (deletion is already forbidden outright by the FR37/FR38 principle above). A new run is `situation-<next>.md`; a new setup story is a new `resource-*.md` / `operator-*.md` / `story-*.md`. Gaps in the numbering are tolerated over renumbering — the same trade `../AGENTS.md` records for the `OR-##` series.
2. **A phrase quoted out of this folder survives verbatim, or the change is recorded as a deliberate re-cite naming the citing file.** The citing file is never edited from inside this folder; the re-cite is handed to that layer's owners. Nothing in the corpus checks this — `cross-layer-cite.mjs` resolves only citations naming a `SCENARIOS.md` file and an ID, and `cite-check.mjs` walks bare scenario IDs — so it is a discipline until a gate exists for it.
3. **Depth is added by appending, not by rewriting.** A beat needing more detail gains a sentence, a sub-bullet, or a paragraph beneath it; the existing sentence stays. Where a sentence is genuinely wrong — it contradicts a `SPEC` — that is a **finding** naming both sides, not a silent edit, because the resolution is a founder ruling or a pillar edit and neither is this folder's to make.

## The bar a story passes

Six checks. Each is already law somewhere in the corpus and is collected here only so a beat can be judged in one pass; every one names its home.

1. **Fixture, not product.** The beat describes an emulated user's situation and never names a feature annnä should have — **FD-80**, *"a Situation is never a ship unit"* (`../PRD.md §6.5`, the home; `../RULINGS.md` carries the row). A beat satisfiable only by a domain-shaped feature is a **finding** — a missing *general* primitive in the vocabulary of the atoms — not a requirement.
2. **Probe, not target.** The beat could come out false. A beat true by construction probes nothing — the meta-principle stated under "Principles that apply here" above, and `../harness/SCENARIOS.md` J5 is the corpus's own worked example of catching that failure and re-cutting the prediction.
3. **Provenance declared.** Every new or extended run states its register in-file, from the four in "Provenance" below: *elicited-blind* · *elicited-to-design* · *scripted* · *held-out*. Scripted material says so, and by that section's own words it "cannot refute" the list it was written from — so it is never cited as coverage evidence.
4. **Both directions.** Must-work **and** must-be-refused, the pairing this file opens with. A probe run with no refusal is incomplete, and a refusal carries a structured reason — **FR34** (`../harness/SPEC.md §3.4`, the clocked-offer law; `../RULINGS.md` carries the row).
5. **Derivation reachable.** Every beat either names a covering scenario or is recorded as owed, in the form `../PRD.md` §4.6 already uses for its requirements — *"owed — "* followed by what the covering probe must show. Owed is a debt kept visible, never an exemption.
6. **v1 versus end-state marked.** Where a beat depicts something one of the **five named gaps** above defers, the story stays true as written and that gap list covers it. A beat deferred by nothing gets a sixth gap entry, or it is not written.

## Provenance (how each probe was made — the vocabulary, added 2026-08-22)

A story is only as strong as where it came from, and the 2026-08-22 coverage review found the corpus citing scripts as if they were falsifiers. Four registers, recorded per probe so nobody has to reconstruct this later:

- **elicited-blind** — told from the domain before the mechanism existed. The only register that can *falsify* a design.
- **elicited-to-design** — requested to pressure-test a design that already existed. A useful stress and a real probe of absorption, but its NOTES citing itself as the design's "justification and test" is the tell: it cannot be independent evidence of generality.
- **scripted** — written from a scenario or question checklist. It restates the list in prose and cannot refute it; it earns its keep as a demonstration and a readable script, never as coverage evidence.
- **held-out** — deliberately not designed to; predictions only, run when the build exists, recorded pass *or* fail under the failed-probe rule above.
