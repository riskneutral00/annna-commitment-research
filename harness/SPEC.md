*This is the single authoritative specification of the annnä **harness** layer. It supersedes, for the harness, everything in `../archive/DESIGN.md`, `../archive/05-post-critique-decisions.md`, `../archive/06-round-two-decisions.md`, and `../archive/07-elicitation-mechanism.md` (kept in git history). ## 0. What annnä is

annnä is an **agent-first commitment harness** — what that means, in both of its senses, is `../PRD.md` §1 and is not restated here. What the harness layer takes from it: the user talks to the agent through a **console**, and the agent creates and edits **commitments** on the **Board**. It is **standalone** — import IN is allowed, there is **no export/sync OUT** beyond a legal minimum (defined at `../security/SPEC.md §8`), and the design assumes a user's *entire* schedule eventually lives in annnä (meals, workouts, cycle, work — all just commitments/presets on one substrate).

**Owner assistance and bounded guest assistance.** The owner uses the board/per-commitment agent. An off-app party uses the board-blind exported form and the approved template-bound conversation described in §2, with credential-derived access under `../security/SPEC.md §3`; returned data uses the existing trigger loop. This permits neither an unrestricted guest assistant nor private owner context.

## 1. Architecture — four layers, thin agent / rich engine

| Layer | Owns | Status |
|---|---|---|
| **Model** (the LLM) | language, world knowledge, judgment, normalization, narration | later |
| **Harness** ← *this spec* | the loop, the tool contract, the elicitation policy, the clarify/permission policy, the context-assembly policy | **now** |
| **Engine** | deterministic compute + storage behind the tools: board math, no-double-book by construction, atomic commit, consistency/coverage checks, the type-value system, concurrency/re-solve | later |
| **App** | console + Board view + per-commitment page + generative-UI rendering + delivery channels + the traditional guest form + SOP/management views | later |

**Thin agent / rich engine (structural, not aspirational):** the LLM translates and narrates; it does **not** author correctness-critical values. Such values enter the system only as **opaque handles returned by a compute tool** (`calculate`), never as LLM-authored literals; read-back is derived from stored structure, not regenerated by the model. See `INTERFACES.md`.

The harness is built and tested **in isolation** against stubbed Engine/Model/App (the seams in `INTERFACES.md`).

## 2. The harness inventory — exactly two harnesses

A harness = one distinct interaction pattern = {loop + tool contract + elicitation policy + clarify/permission policy + context assembly}, on the shared Engine/Model/App. H1 and H2 are two **instances** of the harness *layer* (§1) — same five responsibilities, same tool surface; they differ only in which app surface grounds the interaction. Named by *which app surface* the agent interaction is grounded in (final names deferred; referred to as H1/H2).

- **Harness 1 — the board / calendar surface.** Owner ↔ agent to **create a commitment and see it placed** on the board. ("Put a 3pm dive lesson on Thursday.")
- **Harness 2 — the per-commitment support surface** (one page per commitment; unbounded pages). Owner ↔ agent to author **everything that *supports* one commitment** — rules, SOP, stakeholder assembly, availability-sharing. Deliberately **not** on the calendar.

**There is no Harness 3.** H2's agent *exports* a board-blind form (via the generative-UI tool); the party fills and returns it, and the return fires the existing trigger-driven loop. The approved template-bound guest console assists only with that authorized request's fields, rule explanations and bookability, under `../security/SPEC.md §3`'s credential-derived read/operation limits. It is no independent harness or unrestricted guest agent; its conversation/context implementation retains its existing BUILD obligations. On-app party ↔ on-app party = two H1 instances working **the same one commitment** — creator-owned, shared through the **engine share seam** (specified at `../engine/SPEC.md §7.1`) — not a separate harness and not two records to reconcile. Off-app edges the network can't reach are **assisted, recorded, and converted**: the agent prepares the owner's phone call, records the answer as ordinary internal writes, and offers a floor-gated invite — no new tool, and no contact with a real person without a basis. (A guest-side negotiating agent is a possible future door, not a current need — do not build it.)

**Template-bound guest execution.** Conversation is an interactive use of the existing console input, current draft, `PendingAsk`, model calls and form/render carriers, with `context_mode: guest-interactive` derived by the capability-token admission door. It is a turn in the owning tenant's existing inbox (§4a), not a new harness, trigger source or owner session. The guest actor, bound request/booking, credential revision, read/field/operation scope and any arrangement revision come from current server-held authority (`../security/SPEC.md §3`), never from submitted text, refs or model output. Recheck before assembling or returning data and at the executor immediately before apply; the actual diff and every target must fit that authority even on direct calls. A bare public entry URL still cannot converse. A walk-up single-visitor must first have a live server-bound current request/draft through the existing offering/form flow; its initial stored offering render needs no model. Missing binding is an input/admission gap, never permission to assemble owner context, mint per-recipient rights or create another booking. The same guest-mode refinement preserves each token class’s independently established binding and lifecycle.

The closed guest intent subset of the existing model vocabulary is `answer.provide` for an allowed current field/ask, `commitment.edit` for a permitted request-field proposal, attributed coordinator report or own-booking move, `commitment.confirm` for the current reviewed proposal, `commitment.cancel` for an expressly permitted bound cancellation, and `board.query` restricted to this request's published rules/bookability or permitted own-booking read. These route through existing draft/`commitment.propose`, `calculate` and commitment operations; intent names add no tool or right. Intersect that subset with the credential's current operations and permitted fields. A reader may ask bookability and read the authorized shared proposal/result, never persist a proposal, report agreement, confirm, move or cancel. A coordinator still needs §3.6's current arrangement, attributed report and content-bound confirmation; its label proves no participant vote. Individual own-booking moves/cancels retain H8/H9 and class-specific binding. No guest intent reaches owner rules, saved definitions, directory/contact edits, Grants, issuance, other bookings or private board reads, send, import, taxi dispatch or payment processing. Contacts confer neither access nor send authority.

Guest context is assembled from the authorized published/current request projection, not an owner slice (§8; wire shape `INTERFACES.md §2.1`). Raw guest text takes `summarize` first under `../security/SPEC.md §5`; the validated guest-tagged report may then normalize a legitimate request. Typed values, price and bookability still come from the engine. `../model/SPEC.md §7` owns qualified app-supplied guest routing and `../security/SPEC.md §10` owns finite admission/request limits. Ordinary stored-page rendering calls no model. Submitting the reviewed structured form or confirmation remains `on_form_return` and deterministic trigger processing: it never calls normalize. A guest conversational turn cannot spend the same confirmation again as a returned-form trigger; the existing request/submission/write identity and §7's consumed basis govern the one apply.

After a rule/conflict refusal, retain all still-authorized entered fields in the same draft, mark only the invalid selection, and await another guest input. No silent rounding, replacement booking, price acceptance or rule override. Display the current engine-checked proposed interval, duration, price, applicable published terms and permitted standing; changed input, terms, availability, credential or arrangement invalidates stale acceptance. A finite option submits that answer once into the draft, not a booking; final confirm/move/cancel requires a fresh content-bound act. Keep booking leaves the live booking unchanged. A lost apply result reconciles its existing write id before any fresh attempt. Revocation clears protected visible state and pending access; other credentials, retained booking history and independent lifetimes remain security §3's.

The two harnesses share the same object model, engine, and most of the tool surface; they differ mainly in *which* tools dominate and *what* is being authored.

## 3. The object model (what the harness reads and writes)

All correctness-critical values below are **engine handles / typed values validated by the engine** (see `INTERFACES.md`), not free LLM literals.

### 3.1 Principal / party
The actor model. A principal is: the **owner** of a board, the **actor** on a turn, and the **customer** on an order. Carries identity and (extensibly) attributes (e.g. an ordering like seniority — see held-out E in `SCENARIOS.md`). Owner saved-location entries and optional Home selection are ordinary principal attributes with the identity, revision and reference lifecycle in `../app/SPEC.md §8`; they are not contact-channel permissions or a new primitive. Owner account profile descriptions, intended-use descriptions, app language, region and display zone/format stand on the same footing (`../app/SPEC.md §8`): attributed diffs through the ordinary seam rather than `display_settings` members, granting no authority and minting no role. The schedule zone is not one of those principal attributes: it is the board's own `zone` (§3.2), which stays scheduling truth. **How a role or category is drawn stands apart from what it classifies** *(2026-09-12; the presentation members retired with the visual law 2026-09-17, FD-110 — the separation stands)*: any presentation a design scheme gives a classification is app display state at `../app/SPEC.md §7`, while the classification a style points at keeps whatever home already stores it — a kind, a rule scope or a stored attribute — and a `display_settings` diff can neither create, rename, retire nor re-scope one. §6's existing rule is what that protects: editing presentation or role labels cannot silently rescope rules, release commitments or reset quota.

### 3.2 Board — the universal availability primitive
Both people and resources have boards. **Sharing availability is sharing inventory:** a person's bookable time and a physical asset's units are the same primitive, which is why "others engage your board" is one mechanism across every use case (a teacher's hours, a bike, a pool, a room).
```
Board {
  id
  owner            -> principal
  capacity | balance                 // occupancy is a NUMBER, not a boolean:
                                      //   capacity = recorded admission/expansion accounting (engine/SPEC.md §1.2)
                                      //   balance  = cumulative draw-down over a period (class-pack)
                                      //   (real boards may need both — engine/M3 concern)
  attributes { … }                   // authored facts: has-ventilator, language, depth, unit-class…
  empty_means: free | unknown        // per-board declaration (default unknown for proxy boards)
  zone                               // [timezone — Phase-4/engine]
}
```
- Written via `CRUD_Board`, which edits by **DIFF, never destructive replace** (so a local rule can't wipe seeded governing rules).
- **Empty ≠ free by default.** An external stakeholder's board (no app) reads `unknown`; availability comes via confirmation. The owner's own boards may be declared `free` where appropriate.

### 3.3 Commitment-kind — the vocabulary layer
```
Commitment-kind {            // OWD, rental, ER-shift, lesson…
  id
  attribute_schema { fields[] } // revisioned field definitions below; values belong to their use
  authority: governing | org | individual   // governing defines the kind; org/individual EXTEND, never override
}
```
Predicate rules quantify over these attributes (admission / qualification; composition rides `dependency`/`fallback`, `../engine/SPEC.md §3`). The *temporal* type (event/task) is separate and derived (§3.4).

**Field definitions and their lifecycle — the normative home.** Each `attribute_schema.fields[]` entry declares stable `field_id`, `revision`, `label`, supported `type`, required/optional status, value scope, optional default with its explicit prefill scope, and dependency bindings. The id is local to its enclosing kind/definition identity and never derived from the label or row position; the existing field-path/reference resolves that enclosing identity plus slot id and revision. A label is presentation; a type declares the supported value shape, not an executable predicate. Instance values carry the field identity and bound schema revision through ordinary attributes/provenance. A default is definition data for the declared future-use scope, not a rewrite of existing values. Explicitly cleared or intentionally blank optional values remain blank on reopen; they cannot silently reacquire a default or an example. The app node `id`/`bind` and the existing `field_ref`/scope references carry this identity, without creating a new core object, tool or engine Handle class.

Dependency bindings name the actual source and dependent field/rule refs, revisions and scopes, including the complete typed rule operand or supported calculation input they connect. They are structural bindings to stored schema slots, never label matching or arbitrary formulas. Derive the affected set from current authoritative references, not the visible rows or a cached model list: required inputs, rules, computed outputs, defaults, current uses/links and bookings can all depend on a field. Historical references retained under their original revision are distinguished from active references requiring resolution. Privacy and authority still fence the returned explanation; a dependency does not grant access to its referenced contact, another owner's board or a protected value.

- **Add, edit and retire definitions by revision.** An unsaved optional row may be added, edited or removed in the existing shared draft (§6); removing it removes its draft value and invalidates its dependent proposals, never a stored booking. Saved definition changes use the existing definition branch and account-document path (`../marketplace/SPEC.md` §§2–3); engine-owned schema/rule changes use ordinary attach-point diffs. Keep the stable field id for a label edit or a supported new revision; never reuse a retired id for a different meaning. A type change validates the new type, defaults and all affected active bindings; incompatible values or dependent operands need a user-chosen supported replacement or remain unresolved. No implicit coercion, destructive store-schema migration or reinterpretation of prior values is permitted. Retire removes a field from new use of that revision while retaining the prior revision for bound uses, forms, terms and history. The engine's additive-only physical schema law (`../engine/SPEC.md §1.10`) is unchanged: authored schema entries are revisioned data, not removal or retyping of stored object members.
- **Name the operation and scope before applying it.** Clearing one value retains its field and enclosing object. Changing a default affects its declared future-use scope. Revising or retiring the definition changes the authored schema, not all existing uses. A calculated output is read-only: change only supported typed inputs, invalidate the old Handle/acceptance and obtain a new engine result. A price total cannot be overwritten to simulate editing a rate, duration or basis. Explicitly moving an existing use to a new definition revision remains a separately checked act under the definition home; a booking-specific edit never asks Replace existing/Save as new or changes template defaults. A label edit cannot retarget a rule, remove its constraint or rewrite the historical meaning displayed by a bound form.
- **Independent optional removal succeeds; dependencies require valid resolutions.** Show the selected field/rule, current revision and affected scope. For an independent optional field or rule, remove its pending row or retire its saved definition through the appropriate existing path. For a required or referenced field, retain the current effective state and expose the concrete reason and valid choices: keep it; supply and explicitly rebind to a compatible supported input; or revise/retire the dependent optional rule or calculation with authority over that dependency. Making a field optional is available only when the resulting schema and every constraint permit it; a universal requirement such as title is not removable. Disabling a required input or overwriting a calculated output is not a resolution. If no supported authorized change exists, explain that limitation and keep the candidate pending or let the user abandon it. The product user chooses the policy; no default choice or invented rule meaning ships.
- **Apply only the reviewed current revision.** Keep the accepted draft ref/revision, field/scope/value and dependent Handles on the existing PendingAsk/diff path (§§3.13/6). A commitment-backed pending dependency choice uses the existing PendingDecision path (`../engine/SPEC.md §1.14`); a definition-only choice stays on the existing PendingAsk/draft and document operation record, without inventing a commitment for a schema question. Reuse an unchanged covering answer, but a changed field, type, reference set or dependent input invalidates the affected acceptance/calculation. At commit, re-read authority, expected schema/field revisions and the complete current dependency set, including references added after review; validate the chosen resulting schema and typed rules. Staleness, a new reference or an unauthorized/unresolved member applies none of the candidate engine diff. The app document adapter separately serializes its use/link references and revision compare under the definition home; never claim a transaction across both stores. Finish and read back separately authorized dependent acts before retrying the definition change, reporting any such completed act honestly. Recover an unknown write by its existing identity before another attempt.

**Restriction rows are views of typed rules.** Bind each authored restriction row to the existing Rule identity, target, authority, scope and complete `Rule.operand` (§3.5; `../engine/SPEC.md` §§2–3). Duration maps to `duration`, windows to `location-window`, buffers to `buffer`, and a supported count/time allowance over a recurring window to `quota` — **a count allowance and a time allowance are two separate rules, never one row carrying both** *(2026-09-11; `../engine/SPEC.md §3`'s participant-quota block)*, and the row states the counted identity and period it was bound to; price input uses the existing `pricing` shape. A caption such as “Monthly occurrences” is not a new type or proof of enforcement. Clarify the user's intended operands/scope under §6; preserve ordinary provenance and the menu's binding times. Unknown types, unsupported predicates or conditional pricing outside that menu refuse truthfully and remain unenforced, even if their words can render as text. Rule add/edit/retire uses its attach-point diff and current dependency/authority checks; lower authority cannot remove a governing rule. Removing a row cannot evade these checks.

This lifecycle applies to the field/rule portions of personal Events, Tasks, Routines, template definitions/uses, meeting details, saved places, contacts, restrictions and reminder configuration. Removing a field containing a reference never deletes its contact, place, booking or enclosing object, never merges identity or resets quota, and never supplies delivery permission. Those objects retain their own cancellation, withdrawal, completion, reminder and account lifecycles (§§3.3–3.5/3.12; `../app/SPEC.md §8`; `../marketplace/SPEC.md §2`). Historical bytes, bound terms and provenance survive ordinary edits under `../engine/SPEC.md` §§1.5/1.10, subject to the existing lawful erasure/crypto-shred boundary at `../security/SPEC.md §4`; retirement and value clearing are not erasure receipts and promise no perpetual readable PII. Story labels, people, dates and amounts are fixtures for these general operations.


**A kind may declare reminders (FD-61, 2026-08-22 — the product scored no-shows in detail and never prevented one).** `reminders?: [ReminderPolicy]` is a **creator-set kind property**, and its whole mechanism is machinery that already exists: each reminder instant is an ordinary **clock-trigger firing** (§4's fifth source — no new source); the outward send rides `send` on an elicited **reminder-notify Grant** (the FD-25 shape: no grant, nothing sends, and the empty case is correct behaviour, not an error), addressed through the party's stored contact (§3.12), under `../security/SPEC.md §10`'s caps and §3.11's suppression; content is `narrate(structure)` from the commitment — never composed. Discharge-attention, not capture: a reminder goes only to its explicitly authorized recipient about a commitment in the confirmed scope, and nothing else may ride the channel. Gated at D28.

**Owner reminder configuration and activation.** The owner-selected policy is stored on that kind through the existing diff path: `ReminderPolicy {id, revision, recipient_ref, scope, offset_before_start, channel, contact_ref, contact_version, activation?: {grant_ref, confirmed_by, at}, removed_at?}`. `scope` uses §7's scope shape; the contact reference/version selects the owner's verified account destination in §3.12, without copying an email address into a projection. `offset_before_start` is an engine-typed duration. The app elicits and shows the recipient, exact verified destination, channel, offset and scope together; these are the product user's choices, asked once and stored. In `../user-stories/Situations/Situation-A/story-matt.md` S07 the confirmed choice is Matt, his verified account email, fifteen minutes before booked English lessons in the selected scope, including owner-entered and student-booked lessons. It covers neither personal appointments/routines nor students as recipients. A saved student contact or its channel preference supplies no send authority.

Saving configuration without a live content-bound confirmation saves a **draft**, with no activation or send eligibility. An unsent example, a declined proposal or an abandoned draft activates nothing. Activation requires a saved usable kind; a confirmation inside an unsaved setup remains a pending proposal until the setup and activation are committed under a live content-bound owner confirmation. Saving alone supplies no authorization. Activation couples the confirmed policy revision to an explicit §7 Grant with `operation: reminder-notify` and `action_class: third-party-communication`; its scope binds the lesson scope, and its operation is bound to this exact policy reference/revision, which fixes recipient, destination version, channel and offset. Policy identity is part of the confirmed operation's structural arguments (§7), not a free-text rule predicate. Grant minting and the policy's activation apply together through the existing commit path (`../engine/SPEC.md §6` item 1); a failed or unknown write is resolved by its existing write id before any active state is shown. No copied template or saved draft can import activation. Edits affecting what was authorized require a fresh content-bound owner confirmation; while an edit is merely proposed, the prior active policy stands. Removal is an attributed withdrawal from active use, retaining history, with the selected instance versus whole-English scope shown; revocation follows §7. Neither silently deletes a governing rule or cancels unrelated bookings.

**Reminder eligibility at dispatch.** Read the current confirmed booking revision, current policy/activation and unexpired, unrevoked covering Grant; resolve the still-verified owner destination and recheck §7's floor, §3.11 suppression and the existing security caps. A removed policy, cancelled booking, superseded registration or missing grant sends nothing; absence of reminder authorization is not an unattended escalation. A changed/unverified destination or unsupported requested channel stays unsent and is surfaced for the owner to resolve, never silently switched to a student or another channel. Registry replacement and replay are owned by `../engine/SPEC.md §1.15`; actual dispatch also obeys §4a's current-claim fence and §7's basis-spend rule. A cap-deferred reminder rechecks these same facts when eligible again; once the lesson has started it is obsolete and sends nothing, with the disposition recorded. Delivery states and account-authenticated navigation are `../app/SPEC.md §6`'s transport/display contract; a schedule or a basis spend is not delivery evidence (§3.14).


### 3.4 Commitment — the atom

The user-facing Event/Task choices follow the time-role derivation below. Routine maps to the existing Pattern and its identified occurrences (`../engine/SPEC.md §1.4`), beside those choices; it does not extend `temporal_type`. Stored instance reads retain the Pattern ref, generation and original local date/time/zone along with the occurrence id. A due-only Task retains its deadline and selected identity through rename/removal, without a fabricated reservation or an implicit completion; §6 owns the scope conversation and §7 still gates its acts.

```
Commitment {
  id
  title                                   // the ONLY universal required field

  kind        -> commitment-kind          // optional for a BARE commitment
  exception   { reason, by }?             // M2: on a GOVERNED board a commitment must resolve to a
                                           //   kind OR this explicit exception; silent untyped-on-
                                           //   governed is UNREPRESENTABLE (never recorded compliant)
  attributes  { … per kind's schema }

  // time — fields carry ROLES; temporal type derives from ROLE, not field-count:
  start   { value, role: occupies | defer }
  end     { value, role: occupies | deadline | terminal-constraint }
  actual_end                              // actual done/returned — FREE (no ≥ constraint)
  temporal_type = derived from ROLES (event if it has an occupying interval; else task)
                                           //   `role` is contract/engine-classified, never an LLM literal
  completed     = derived from recorded completion / permitted clock completion below
  completable   = derived from kind        // the kind's schema declares whether completion requires an
                                           //   explicit act (a tick / recorded return); BARE => false (FD-98)

  consumes    [ { board_ref, quantity } ] // capacity/balance draw
  depends_on  [ commitment_id ]           // instance-level prereq edge (NOT a rule); drives `blocked`

  party  { customer?, executor?/board_ref, … }
  order  -> order_id                              // composition root (see 3.7)

  form_ref    { schema_id, version }?     // FR16: the authoring form this commitment was created
                                           //   with, pinned at creation. Optional because a BARE
                                           //   commitment has no form. See the note below.

  // STATUS = lifecycle precedence below; stored facts are never cleared to change status:
  confirmed_at { by, at }?               // write-once confirmation HISTORY, not a terminal outcome
  cancelled_at { by, at }?               // terminal decision, stored + attributed
  declined_at  { by, at }?               // terminal decision, stored + attributed
  expired_at   { at }?                   // terminal clock latch; no un-expire
  status = lifecycle_status(stored_facts, unmet_conditions, clock)
           //   terminal outcomes: cancelled / declined / expired / completed
           //   otherwise: draft[not yet committed — persistent form state] /
           //              offered[live unanswered offer and hold] /
           //              blocked[deps unmet, including pending+blocked] /
           //              pending[own preconditions unmet] /
           //              review[completable past end, no recorded completion] /
           //              active[start reached, not done] /
           //              confirmed[confirmed future booking]

  // THE PARK — the loop stopped and a HUMAN must look. Neither a latch nor a status:
  needs_human { reason: no_basis | unreachable | unverified
                      | budget_exhausted | slice_unfittable | quarantine_failed
                      | engine_unavailable,
                cause?: { kind: covering-rule, rule_ref }          // L3's named covering rule
                      | { kind: budget-ceiling, measure: routed-steps | effects | provider-charge,
                          ceiling, spent }                          // §4a; both values use the measure's unit
                      | { kind: failing-layer, layer }             // L5's failing quarantine layer
                      | { kind: ladder-exhausted, escalation_ref } // §3.9's walked-out ladder
                      | { kind: engine-unavailable, call },        // the unreachable seam call
                since, trigger_ref,
                cleared_by { principal, at }? }?
           //   written by the loop, cleared ONLY by a human act (D4, K2)
           //   (2026-08-22: the three mandated parks — §4's budget ceiling, §8's unfittable
           //    slice, the failed quarantine — gained their members + the structured `cause`;
           //    the union previously forced them into a wrong member, breaking D17's legibility)

  preconditions [ { kind: signature|id|payment|…,
                    satisfied_by { principal, at, evidence }? } ]   // evidence, not a bare tag — a CLOSED union (2026-08-22):
                    //   { kind: 'attributed-assertion', basis }   // operator's reported basis, not independent verification
                    // | { kind: 'in-form-consent', form_ref, at,
                    //     bundle { timestamp, ip, user_agent, document_version_hash } }   // security §6's evidence
                    //     bundle rides the member (2026-08-31): the four fields a digital signature stores as this
                    //     precondition's evidence (`../security/SPEC.md §6`) — the closed union carries them, not a bare tag
                    //   principal = who supplied the consent or reported the assertion; at = the attributed event time
  expires_at                              // hold timer → feeds the expired_at latch

  provenance [ { field, value, author: owner|customer|template|engine|llm,
                 author_utterance?, at } ]   // PER-FIELD attribution + timestamp
}
```

**Precondition evidence admission.** New v1 returns admit structured field values and the closed evidence members above through `INTERFACES.md §3.3`. An attributed assertion records the operator and reported basis through `satisfied_by`; it is not independent proof of a participant, payment, clearance or physical event. In-form consent binds the exact approved ruleset/form version and retains the complete `../security/SPEC.md §6` bundle. Missing required consent refuses; neither a filled answer nor source-form approval substitutes for consent or satisfies an unrelated precondition. Source-form identity/language/version follows `../security/SPEC.md §4` and cannot elevate the admitting `source_tag` (§8). The former participant `vault-attestation` evidence and verification/attestation form-return riders are excluded from new v1 inputs under that home and the breaking-change notice at `INTERFACES.md §7.2`. Historical custody receipts remain readable as attributed storage events, never rewritten as verified participants or accepted as new uploads; `../security/SPEC.md §4` retains their receipt/tombstone and erasure semantics.

**`owner` vs `customer` in `author`.** `customer` throughout this corpus means the *counterparty* — the person who books (`Order.customers[]`, the `per-customer` quota scope, the `customer` rung of the scope ladder). `owner` is the account holder who runs the board. The two were previously collapsed, which made "the owner hand-set this field" unexpressible and left §6's repetition predicate with no referent. This is the vocabulary's **single normative home**; `../engine/SPEC.md §1.3` asserts the `engine` member for override precedence and remains true unchanged, because that precedence ranks travel-value sources, not author tags. The author list `../engine/SPEC.md §1.3` names inline — "customer-, template-, and model-authored" — is **illustrative of the vocabulary, not the normative statement of it**: the vocabulary lives here (§3.4), and the `model`-vs-`llm` wording in that inline list is the engine spec's prose, not a second definition. A reader (or `/contradiction-sweep`) should treat that list as a pointer to §3.4, not as a diverging restatement.

**Status transitions and precedence — one home.** `confirmed_at` is a write-once history fact: confirmation ends an offer, not the commitment's lifecycle. An authorized later cancellation or valid recorded completion determines current status without clearing or rewriting that confirmation. `cancelled_at`, `declined_at` and `expired_at` are terminal latches. `completed` remains derived from the kind's completion facts, never a caller-written status or a new latch.

| Stored state / later input | Current status and permitted transition |
|---|---|
| No terminal outcome; unmet own preconditions and dependencies | `blocked`; retain both `pending` and `blocked` conditions. Own preconditions alone yield `pending`. |
| No terminal outcome; preconditions and dependencies met; authorized confirmation before start | `confirmed`; retain `confirmed_at` unchanged through every later transition. Confirmation alone grants no authority for a later act (§7). |
| Confirmed, no terminal outcome; start reached / completable past end without recorded completion | `active` / `review`, respectively, with confirmation history intact; completion and capacity follow the per-kind paragraph below. |
| Confirmed, no terminal outcome; authorized cancellation | `cancelled`, with both confirmation and cancellation facts retained. The owner-crossing and bound-counterparty paths keep §7's respective authority requirements. |
| No terminal outcome, with or without confirmation; valid completion under the kind and existing precondition checks (`../engine/SPEC.md` §3 precondition, §6) | `completed`: a completable needs its explicit tick/recorded return; a non-completable event may complete when its end passes. A task needs its tick. An early recorded return is valid; a completable never completes from elapsed end alone (FD-98 below). |
| Expired hold; later signature, accept or purported completion | `expired`; record admissible evidence, but refuse confirmation, renewed consumption or any competing terminal transition. No un-expire. |
| Cancelled or declined; later confirmation, completion claim or elapsed dates | Keep `cancelled` or `declined`; refuse revival or a competing terminal transition. Later admissible facts remain history, not authority to resume. |
| Completed; later competing cancellation, decline or expiry attempt | Keep `completed`; refuse the conflicting transition. The completion facts and any earlier confirmation remain recorded. |

**Only genuinely competing terminal outcomes use earliest-terminal precedence.** The first effective terminal outcome in the valid lifecycle governs; the engine rejects a later conflicting transition in its atomic write path (`../engine/SPEC.md §6` items 1–2). Confirmation is never a competitor against later cancellation or completion. Neither a backdated input nor a later-arriving fact manufactures an earlier authorized transition: recorded attribution/history distinguishes when evidence says something happened from when a lawful act applied. Existing terminal facts are not replaced, and no write may clear or rewrite a set latch (`../engine/SPEC.md §1.3`). Ordinary corrections to `actual_end` retain the existing interval-widening checks (`../engine/SPEC.md §6` item 7); they neither clear a terminal latch nor manufacture a different terminal outcome. Receipt, firing termination and budget state are separate objects, unaffected by this commitment-status rule.

**`expired_at`'s one shape is `{at}` — the normative shape, stated 2026-08-31.** It is the one latch without `{by}`: lapse is the clock's consequence, not a principal's decision, so there is no author member to store. Its attribution is the ordinary per-field provenance entry — `author: engine` (`../engine/SPEC.md §1.3`'s member), written when the clock latches it. `../engine/SPEC.md §1`'s "each `{by, at}`" phrasing reads over the three decision latches; this block is the home and this shape governs (FR13). The latch invariant is untouched.

**The condition layer is a set.** `pending` and `blocked` can coexist; the table selects `blocked` when both hold. Readers retain both conditions even when a terminal outcome determines the scalar status. The app consumes this computed status and condition set without deriving its own precedence (`../app/SCENARIOS.md` C1/C2).

**`completable`, defined — and a completable's capacity is consumed until `actual_end` (FD-98, 2026-08-31).** `completable` is a per-kind declaration: the commitment-kind's schema says whether completion requires an explicit act (an owner tick or a recorded return); a BARE commitment is non-completable. These completion/capacity rules apply to a live commitment; a cancelled or expired record is not revived by a later return. Completion facts retain ordinary per-field attribution; a recorded return is an attributed report, not verification of a physical return. Two consequences, previously implied and now law: `review` derives exactly for a completable past its `end` with no tick, and **a completable's `consumes` draw stays consumed past `end` until `actual_end` is recorded** — a late return keeps the unit consumed, the engine's availability math counts it as still drawing, and nothing auto-completes it at `end`. The engine capacity row and the COVERAGE late-return row consume this definition as they land. **The declaration is the whole source of the behavior** *(2026-09-12)*: a non-completable event derives `completed` at its passed end and a completable holds its draw until `actual_end` is recorded, so the early-return recovery a rental kind gets is **that kind's declaration, not a property any kind acquires by resembling it**; and no other signal supplies the fact — a delivered reminder, an elapsed clock and an opened joining link establish no attendance, return, completion or payment, which is stated once for all of them at `../engine/SPEC.md §1.9`.

**The park union's engine-raised member, and the closed `cause` (2026-08-31).** `engine_unavailable` joins the reason union: an unattended firing whose engine seam stays `unavailable | timeout` past the loop's one bounded retry **parks** rather than spinning or dying silently, and the engine-side restatement of a park round-trips with its `cause` intact — the restatement carries the cause, never drops it. And `cause` is now a **closed union**, one member per mandated park detail — the covering rule, the spent ceiling, the failing layer, the exhausted ladder (§3.9's full-exhaustion park now names its ladder), the unreachable seam call — so D17's legibility is typed rather than promised.

**Budget cause units.** In `budget-ceiling`, `measure` discriminates `ceiling` and `spent`: `routed-steps` and `effects` carry counts; `provider-charge` carries monetary amounts in the accounting unit of `../model/INTERFACES.md §2.2`. Both values describe the same measure, never a count compared with money. This refines the existing cause, not the `needs_human.reason` or termination vocabulary; the declared compatibility amendment is `INTERFACES.md §7.2`. §4a owns when each allowance stops work.

**Why `offered` is derived and not latched.** An offer being out is a **condition** — the offer exists and its hold has not lapsed — not a decision a principal made, so there is no `offered_at {by, at}`. The decisions that end it *are* latches: acceptance is `confirmed_at`, refusal is `declined_at`, and a lapsed hold is `expired_at` (`expires_at` feeds it, §3.4 above) — which is why a late "yes" cannot un-lapse an offer. **One terminal event is not a latch and still ends the condition** *(ratified 2026-08-24 — the retired `CLARIFY.md` §9.4; ordinary concurrency: first commit wins, the other gets a structured conflict, the hold releases — before this sentence, engine I2's conflict case had no legal status to land on)*: a **commit-time conflict** on an accept is recorded as an attributed terminal event on both boards (`../engine/SPEC.md §7.1` item 5), and that event **releases the hold**, so "its hold has not lapsed" is false and `offered` no longer derives — the commitment reads by its remaining conditions (typically `draft`), no latch set, no fourth status value invented. This block is the **single normative home** for the commitment status vocabulary; `../engine/SPEC.md §7.1` prints the share-relevant subset and cites here rather than defining a second list.

**Why `form_ref` is stored and not reconstructed (FR16, ruled 2026-08-06):** `../app/SPEC.md §5` and `../app/SCENARIOS.md` C2 both require the commitment riser to anchor on **"the same form the commitment was created with,"** pre-filled from stored structure. Before this ruling, nothing in the type pointed back at that form, so the app could only re-derive it from `kind` — which is wrong in two cases the corpus already contains: a **BARE** commitment has no `kind` to derive from, and a `kind`'s schema can be **versioned after the fact**, so re-deriving would reopen the commitment under a form the owner never saw. Pinning `{schema_id, version}` at creation makes the app's assertion true by construction rather than by convention. It is **optional** because a BARE commitment legitimately has no authoring form; when it is absent the riser anchors on the bare title, which is the honest answer. `form_ref` is a **read anchor only** — it grants nothing, and changing-the-rules-never-rewrites-the-past is untouched: a later schema version changes what *new* commitments pin, never what an existing one already pinned.

**Why the park is neither a latch nor a status:** a latch is a **decision a principal made** (`{by, at}`) and is irreversible by design; a derived status reports **the commitment's own conditions**. A park is neither — it is an **unfinished firing**: the loop reached an act it could not take unattended (D4) or could not verify (K2), and stopped. The commitment's real status is unchanged and still true — a pending course is still pending — so the park rides **alongside** `status`, never replacing it. Two consequences are load-bearing: the board must **surface** a parked commitment however its status reads, and only a human clears it — `cleared_by` has no `engine` or `llm` author, so **the loop can never un-park itself** and a park can never be silently absorbed by a later retry. While a park is uncleared, the loop may not retry the act that caused it.

**The clocked offer is a composition, not an atom:** an offer to a person (a job sent to an instructor on Review) is the one commitment in `offered` with `expires_at` set from its **hold** — the creator-set share field (`../engine/SPEC.md §7.1`: default 5 minutes, 0–24 h). Lapse fires the trigger loop and the engine re-solves to the next ranked name; a late "yes" hits the expired latch exactly as a late signature does — lapsed stays lapsed. **This composition is also the definition of "reachable" (founder-ruled 2026-08-07, #7): reachable = responded within the offer's hold window.** The offer walks the owner's ranked list one candidate at a time — a divemaster at sea simply lapses to the next name — and full exhaustion **parks to the owner, attributed**, exactly like ladder exhaustion (§3.9). A decline is never bare: it carries its structured reason (`../engine/SPEC.md §7.1`), and the owner's re-offer on changed terms is the only counter that exists.

### 3.5 Rule — the governance atom
```
Rule {
  id
  authority: governing | org | individual   // precedence by level; governing is NON-overridable
  owner_org                                  // TENANT — whose rule (so kind-targeted rules don't leak across shops)
  target: board | commitment-kind | audience | party
          //   party = a counterparty's own constraints ("Harold will never move")
          //   — stored and versioned like any rule; force in resolve: engine §1/§7
  type:   buffer | capacity | balance | quota | hold | precondition |
          admission | qualification | fallback | dependency | pricing | …
          //   quota = a limit over a RECURRING window, scoped (owner-wide / per
          //   customer / per link) — "max 10 hours a month per student," "max 3
          //   lessons a day." Operand is a typed rate; evaluation is engine/M3.
  operand (complete Rule.operand)            // engine SPEC §3 shape, §2 typed leaves; correctness-critical → engine handle
  enabled
  effective_from / supersedes                // version-of-record (completed history stays truthful)
  provenance { author_utterance, normalized_by, at }
}
```
**Duration uses the existing rule, not a new type.** Its range-only and optional typed step/anchor forms, compatibility checks, binding time and length math are `../engine/SPEC.md §3`’s duration contract. Pass the complete `Rule.operand` unchanged through the attach-point diff and stored readback: the aggregate holds typed range/step/anchor leaves, is not itself a `TypedValue`, and occupies one Conflict operand entry beside its source ref (`../engine/SPEC.md` §§2–3/8). A label or display string cannot replace it.

Rules edit by **diff** (as boards). Instance-level facts (e.g. "day 2 depends on day 1") are **commitment fields (`depends_on`), not rules.**

**Changing the rules never rewrites the past — at every authority level.** `effective_from`/`supersedes` is not only for governing revisions: commitments keep the terms they were made under (price, shape, buffers, windows); an edit to any rule governs only forward (new bookings, next pull, next month). No live commitment is silently re-priced or re-shaped by a later edit.

### 3.6 SOP & Shared (optional layers)
- **SOP** — optional bundle of kinds + rules; gains document identity when authored/named through the existing SOP path. Managed in an app-side SOP view. Authoring consumes admitted content or an existing authorized content reference, never owner/guest file bytes or an upload reference. Admitted SOP/catalog text keeps the `document` tag and quarantine (§8); `../security/SPEC.md §4` excludes owner/guest file uploads and participant authentication. Naming a document or an administrator approving a source form opens no ingestion route and verifies no participant.
- **Shared** — optional publication (rules/SOP + audience + scope). The thing H2 *exports* to off-app parties as a board-blind form. A Shared is **published inventory** — the outward face of a board's capacity. A publication delivered to recipients carries a **per-recipient token**, so a returned form attributes to exactly one recipient and its data lands with that attribution (token generation/securing is an app-seam concern).

**Reusable groups and shared requests — the normative home.** A saved group is an owner-scoped entry in the existing principal's attributes (§3.1): `{id, revision, label, roster: [party_ref], defaults, retired_at?, provenance}`. Its stable entry identity is engine-minted and resolved under the owning principal; `group_ref` uses that principal Handle plus the existing stable field/entry reference, not a new Handle class; its roster contains distinct existing parties (§3.12), never copied contacts, names as keys or a new group principal. Defaults include an optional reference to the confirmed coordinator arrangement below. Author it through the existing current draft, principal-attribute diff and stored relevant-slice read; retain §3.3's stable field/revision binding. Saving a group creates no request, booking, grant or send. Discard leaves unapplied group changes absent and discloses independently saved contacts. Reopening resolves the same entry and current contact references. Reuse across people does not determine attendance: use supplied individual/group intent and ask only for missing per-use choices, never route on story names or a fixed group size.

A **shared request is the existing unconfirmed Commitment**, linked to its existing Order and Shared, not a new booking per recipient. Its `id` is the request identity and remains the booking identity on confirmation; an account-document use records that reference through its existing adapter, without claiming cross-store atomicity. Commitment attributes retain `{group_ref?, group_revision?, selected_participants: [party_ref], booked_participants: [party_ref], arrangement_ref?, agreement_refs}`. Absent legacy members mean no group binding, no delegated authority and no inferred attendance. The Order's customers reflect the participants of this one shared lesson; its members contain this one teaching commitment. Group defaults prefill a new use, whose selected participants are explicitly reviewed; another subset is another use, not a roster edit. Both selected and booked sets contain distinct party refs; a repeated ref is an invalid candidate, never another allowance draw. Before confirmation `booked_participants` is empty and a saved request holds only proposed placement/draw inputs, with no teacher reservation or quota draw; any explicitly acquired temporary hold keeps its existing separate lifecycle. Final commit atomically binds the accepted selected set as booked participants, placement, terms and participant draws; the teacher interval and its travel/buffers are reserved once. Seat/inventory draws still follow the actual consumed board's rules (N students can consume N seats without reserving the teacher N times). Opening, reading or issuing links consumes no allowance and casts no vote. Actual attendance is a separate attributed fact; absence or an attendance report cannot silently change booked participants, terms or quota.

**One request, individually scoped access.** Shared's existing per-recipient digest entry binds `recipient_ref`, this commitment ref (including while it is a request), read scope and allowed operations, with any arrangement ref/revision. Every link resolves the same current request/booking, subject to its own current authority. There is no per-link request copy or per-member teacher booking. Only owner-confirmed shared fields are selectable: group label, participant/coordinator labels, lesson details, shared total, attributed reporter label/report outcome and request/result state in the confirmed scope. Contacts, another participant's quota/marks, private calendars and blocking reasons remain absent by construction. Each participant's own standing retains the booking-manage fence. Read permission is not write permission, including on a manage token. Publishing the names/details is an outward act under §7; selecting contacts or a venue is not permission to expose them. Individual revocation removes only that link's access; conversion does not widen a reader into a writer. Credential binding, individual request fill/check/confirm, booking read/move/cancel, forwarding and replacement lifecycles are owned by `../security/SPEC.md §3`. The admitted recorded party and bound request, not a typed contact/name, supply the actor and relevant slice. Recheck that credential before assembling any guest context and at the actual executor, including replay; a stale request page supplies no authority. Guest attempts to edit owner rules, saved definitions, contacts, others' marks or another booking refuse regardless of generated output. Shared request membership does not grant access to other requests using the same group.

**Coordinator arrangement and reported outside agreement.** Reuse Shared's scoped authorization metadata, the existing `grant.give`/`grant.revoke` authorization gate and §7's canonical operation/scope/condition encoding; no new role primitive, credential class or seam verb. An arrangement is revisioned Shared data `{id, revision, owner, coordinator: party_ref, scope, participants_scope, operations, conditions, valid_from, expiry, suspended, revoked_at?, confirmed_by, confirmation_ref}`. The owning board/instance scope and the structural group-entry binding together bound reuse; `participants_scope` records whether the confirmed arrangement covers selected subsets of that named group, or only an explicit participant set. Neither missing scope nor a missing conditions member means unlimited authority. Each allowed operation binds its actual tool operation and target; permissions are an explicit set, never inferred from the word coordinator. The closed operation refinements on the existing `CRUD_Commitment` path are `commitment.propose` (request candidate only), `commitment.report` (with required `agreed` or `objection` outcome binding), `commitment.confirm`, `commitment.change` and `commitment.cancel`; these are discriminators for ordinary commitment diffs, not new tools. An authorization may allow either report outcome or both explicitly. Unknown operations/outcomes refuse as schema mismatch; property-based risk classification still applies to the actual diff, not its label. Minting/widening this authorization is console-only, live and content-bound to the entire arrangement, like any authorization under §7; an outside report alone cannot mint it. Storing this token-access scope does not mint a cross-owner ShareGrant, and the §7 Grant matcher remains the separate floor check for acts that need a standing basis; an internal report is not forced into a new Grant risk class.

| Existing path / operation | Allowed actor and basis under the arrangement |
|---|---|
| Declared scoped read | An admitted reader or coordinator of this request; read permission only. |
| `CRUD_Commitment` / `commitment.propose` for this request, including selected participants, time and supported terms | Owner, or this request's coordinator only if the exact edit is in the confirmed operation set and participant scope; ordinary typed validation and content-bound draft acceptance still apply. |
| `CRUD_Commitment` / `commitment.report` with `agreed` or `objection` | Owner, or the currently authorized coordinator with that explicit report operation. Record reporter and affected participants; never attribute a reader's alleged statement as a direct authenticated act by that reader. |
| `CRUD_Commitment` / `commitment.confirm`, `commitment.change`, `commitment.cancel` | Owner, or coordinator with that exact operation; current arrangement plus a current covering outside-agreement report and the acting person's content-bound confirmation of the exact proposed act. Ordinary §7 consequence/floor checks still apply. |
| `grant.give` / `grant.revoke`, permission widening, participant credential issuance | Owner-only authorization path; no coordinator or reader can delegate, issue credentials or turn an outside report into permission. Publication/issuance retains the existing app/token path. |

An outside report is ordinary attributed commitment data `{reporter, recorded_by, at, affected_participants, request_ref, expected_revision, terms_ref, terms_revision, proposed_act, arrangement_ref, arrangement_revision, outcome: agreed | objection, valid_from, expiry, supersedes?}`. The proposed act uses §7's canonical structural encoding, including selected participants, placement and applicable terms; correctness-critical values are Handles. `reporter` is the owner or admitted coordinator who actually supplied the report; `recorded_by` preserves the applying actor, and any reported speaker is separately labelled as reported, never verified. Store the person's report of the agreement outside annnä, not signatures/votes from everyone or proof of identity, attendance or payment. Unknown or expired validity is not agreement. Required scope/validity choices are elicited from the product user once and stored. A report of one participant's removal names that participant and the affected resulting arrangement; if the remaining people's terms change, agreement must cover those affected people too. A report with unresolved objections cannot authorize application.

Every apply rechecks current arrangement/credential state and revision, affected participants, proposed act, report/terms revision, validity and authoritative engine inputs. A changed roster, request participant set, time, venue, price/terms or permitted-action scope invalidates any report/acceptance it changes; obtain renewed agreement for the changed act. Reuse an unchanged covering group arrangement for a selected subset only where the owner confirmed that scope, while obtaining this request's own agreement. Revoke latches permanently; suspend blocks use until the owner's attributed clear, which does not refresh expired/stale reports. Changing coordinator or widening scope requires a fresh owner confirmation; a revived or replacement arrangement cannot revive the old report or pending act. Revocation and application serialize: a commit already applied remains history; a pending stale act cannot apply after revocation. A reader can contact the owner/coordinator outside annnä; **reader links cannot submit objections or agreement reports**, even by calling the executor directly. An allowed actor records the outside objection, suspending the affected agreement's usability pending resolution; it does not silently cancel a booking. Resolution is a fresh attributed report and review of the exact resulting act, not deletion of the objection. If nobody is authorized or agreement remains disputed, keep the proposal pending and explain the available owner path; never choose for the group.

**Roster retirement and booking changes are different acts.** A group/member removal names the selected group entry, expected revision and exact scope. Re-read actual dependent requests, recipient links, arrangement bindings and future bookings, including references inserted after review. Explain live dependencies separately from retained history and ask the user for required resolutions: retain an explicit frozen request binding, revise its selection/authority with renewed agreement, or separately withdraw/cancel through its authorized path. A surviving request must retain resolvable party/group revisions; a removal cannot leave a dangling binding or silently carry authority to a replacement member. Unresolved dependencies refuse the whole candidate. Serialize the reference check with the diff; separately stored document references use their own adapter guard, never a claimed transaction across stores. Retire by attributed revision, retaining prior identity/history, not destructive deletion. Saved contacts and booked participants remain unchanged by roster retirement. Changing one booking's participants instead uses that commitment's accepted diff, current agreement and engine checks, with one resulting participant set and atomic per-participant effects; a failed member, stale reference or unknown commit cannot leave a partial set. **Bound-term replacement now has its engine home and its required members** *(2026-09-11; `../engine/SPEC.md §1.5`)*: a booking's quote changes only through that one validated act, and this section supplies three of its members — the proposed roster, time, rate and total; the recorded outside agreement covering exactly those affected people and that exact act; and the acting person's current authority — while the engine matches them against the expected current quote revision and refuses the whole candidate on any mismatch. Where the remaining people's terms change, the agreement must cover those affected people too, as above. Unsupported quota policy remains a visible unresolved dependency at its existing engine home, and neither an attendance change nor a literal price overwrite ever simulates either. Whole-booking cancellation is a separately authorized act, not member deletion. Later verified party/account linking and chosen availability sharing follow security §2 and engine §7.1; account creation or group membership grants no calendar read, and unknown remains unknown. **What the group console may compose from, once members have linked** *(2026-09-11; the permission law is engine §7.1's, the identity law security §2's, and this sentence only says what the console does with them)*: a common-time proposal is composed **only** from the availability each member currently permits and the owner's current rules, and it identifies a member who shared nothing as a **missing answer to coordinate with that person directly**, never as free time and never as a guess. Revoking one member's sharing and asking again recomputes from current permissions. A returned proposal is a candidate: this section's arrangement, agreement and content-bound confirmation checks and the engine's final admission are unchanged by it, and **neither account creation nor a successful proposal mints coordinator authority** or any participant's agreement. Verified linking itself continues to belong to security §2 — a name, a forwarded credential or control of a shared inbox supplies the console no identity evidence.

**Attendance does not choose the money outcome** *(2026-09-11)*. An unmarked unknown attendance outcome keeps the booking's bound quote, current `priced` revision and ordinary `owed` derivation. Only an authorized human `no-show` mark activates the separately configured no-show policy bound at booking; its full-rate arm reads the current bound quote, while custom or deposit-forfeit arms use their own bound terms and stored deposit evidence. Reports of attendance, `actual_end` or payment are attributed facts and cannot replace a quote or create a no-show mark. **What such a report carries — the exact booking and revision, the reported instant, the reporter, the applying principal, the basis, and for a payment the payer and named channel — and how one is corrected or withdrawn, is `../engine/SPEC.md §1.9`'s** *(2026-09-12; it reuses this section's report vocabulary and adds no member here)*. Two consequences this section owns: a report about a **participant** names a participant the booking already carries, and any other reads `unknown`; and recording one is an ordinary write under §7's floor, so a guest credential acting on its own booking cannot record another person's attendance or payment — the refusal above covers others' marks and this is the same refusal, not a second one.

### 3.7 Order — composition root
```
Order {
  id
  customers [ principal ]        // one order may have MANY customers (group class)
  payment_preconditions [ … ]      // each member is a §3.4 precondition with kind: payment;
                                 // its optional satisfied_by.evidence is §3.4's closed
                                 // two-member union. §3.4 is the home; nothing is added here.
  members [ commitment_id ]      // commitments that belong together

```
- **Whole-order cancel** dissolves all members and releases their slots.
- **Partial cancel** dissolves ONE member (release its slots) without touching the rest.
- A **group booking** = one order, N customers, consuming N seats on a seat board; its shared teaching commitment reserves the teacher once, under §3.6.

### 3.8 Money — records, never moved
annnä holds the **records** of money — priced, owed, paid, held, settled — as typed values (engine/M3) and latched marks `{by, at}` on commitments/orders. The actual transfer (cash, bank, a shop's own card machine) always happens outside the app and is *marked* settled inside it. **No tool transfers value:** the `value-transfer` reversibility class (§7) is defined but unoccupied today — future payment rails would occupy it; marking paid/settled is an *internal* act.

### 3.9 Escalation — the object behind "escalates to a ranked on-call list"

§4 and `BUILD.md` Step 5 both instruct the loop to *escalate*. Until now nothing named **who**, and an instruction with no object is not implementable. This is that object.

**The on-call list** is board-owner-scoped configuration, not a per-event choice:

```
OnCall {
  owner        -> principal              // whose board this list guards
  ranked       : [ { principal, channels: [in-app | email], quiet_hours? } ]
  step_timeout : duration                // how long one rung waits before the next
  total_timeout: duration                // the whole ladder's budget
}
```

**Escalation itself is a first-class stored object**, not a message that vanishes:

```
Escalation {
  id
  commitment   -> commitment             // what is stuck
  reason       : missing_basis
  raised_at
  ladder_state : { rung, notified_at }
  status       : open | answered | timed_out_parked
  answered_by  -> principal?             // {who, basis, when} on the resulting act
}
```

**Why `reason` carries exactly one member.** Four members were removed, deliberately and entirely, and are written out here rather than left as an absence. `check_work_mismatch` was removed because §4's bounded loop terminates in a gap or a park and never raises an Escalation. `min_occupancy_shortfall` and `unsolvable` were removed because the engine already parks for both — escalating them would create a second outcome for a condition that already has one. `offer_expired` was removed because a lapsed offer **cascades to the next ranked name** (§3.4) and only full exhaustion parks — it never reaches the ladder. What remains is the one condition a woken human can actually resolve: a missing basis. **Removing them granted nothing** — no new act became permitted, and the ladder's authority is unchanged (it never had any — it only ever notifies; the human's answer is the sole basis, §7).

**How it walks.** Rung 1 is notified; after `step_timeout` with no answer, rung 2; and so on. **The ladder is best-effort notification, never authority** — reaching a human does not create a basis. The human answering *is* the basis, captured the ordinary way (§7). A rung that is unreachable is skipped, recorded, and the ladder continues. Across-firing deadlines and their race rules are owned by §3.13’s escalation-deadline registration contract; walking never depends on a live request or an in-memory sleep.

**Exhaustion is the safe default, and it is not a failure.** When `total_timeout` passes with no answer — or the list is empty, or every channel is off — the commitment **parks in a needs-human state and is surfaced**, and the Escalation closes `timed_out_parked`. A park is cleared by a human or not at all (`../engine/SPEC.md §1.3`). **No ungranted across-the-line act ever fires because nobody answered.** Timeout can only ever produce *less* action, never more. This is the D4 scenario, and it is the whole reason the ladder is allowed to be best-effort.

**What authorizes the ladder's own sends (FD-25, founder-ruled 2026-08-21).** A rung notification is an outward act like any other — email to a real address, capped by `../security/SPEC.md §10` — and the floor does not except it. Its basis is minted where every standing authorization is minted (§7, the auto-accept precedent): **eliciting the on-call list mints an ordinary Grant** — `action_class: third-party-communication, operation: escalation-notify`, scope exactly the ranked list (§7) — and each rung send fires on that basis, attributed `{who, basis: that grant, when}`, riding `send` (§5.2). No list, no grant, nothing to send — the empty-list case below is unchanged. The **in-app** entry is rendering into the owner's own console, not an outward send, and needs no basis. What the ladder still never has is authority over the *stuck* act: reaching a human creates no basis for it (below) — FD-25 gives the notification a basis, never the act.

**Channels (the FR4 ruling, and the 3 a.m. question answered).**

- **In-app is always on and cannot be disabled.** Every escalation lands in the owner's console regardless of any other setting. It is the floor of the notification story.
- **Email is default-on, per-user disableable** — a real setting, not a hidden one, subject to `../security/SPEC.md §10`'s volume caps.
- **What happens when the last channel is off:** nothing changes about correctness, and the spec says so out loud rather than leaving it inferable. In-app is undisableable, so **a channel set can never be empty**; the worst reachable state is "in-app only," which means *the escalation waits in the console until someone opens it.* The ladder then simply exhausts on `total_timeout` and the commitment parks. **An escalation nobody receives is a park, not a silent proceed** — the outcome is identical to the reachable-but-slow case, by design.
- **Quiet hours suppress a rung's *email*, never its in-app entry, and never the ladder's advance** — a sleeping rung 1 costs `step_timeout`, not the escalation.
- **A capped-out rung behaves like quiet hours** *(2026-08-21 — the per-recipient email cap, `../security/SPEC.md §10`, previously had no stated reader here, and a capped address is not "unreachable")*: when a rung's email would exceed the recipient's daily cap, the email is **not sent and the non-send is recorded** on the ladder state; the in-app entry still lands, the ladder advances after `step_timeout` exactly as it would past a quiet-hours rung, and nothing is dropped silently — the ladder's park attribution names the capped rung if exhaustion follows. The cap defers the channel, never the escalation.
- **The owner is told when a park happened this way.** A park raised by exhaustion is visibly attributed to it (*"nobody answered by 04:10; held for you"*) — the difference between a system that failed quietly and one that stopped honestly.

**Scoping note:** the on-call list is *availability* configuration, so it is elicited like any other setup answer and stored addressably (§6's ask-once). An owner with no list is the common single-operator case — the ladder is empty, exhaustion is immediate, and the commitment parks. That is correct behaviour, not an unconfigured error.

### 3.10 PatternDecline — the object behind "a decline is remembered"

§6's noticed-pattern offer promises three things: a declined offer does not return; a *better* later offer may ask again; and any single offer can be declined permanently. All three need a stored record, and none of the five store-routing shapes fits — the thing being remembered is a fact about the **owner**, not about a board, a kind, a commitment or an authorization. This is that object. It follows the `OnCall` precedent (§3.9): owner-scoped configuration, elicited and addressed the ordinary way, outside the five routing shapes. Like `OnCall`, it **persists through the existing `commit` verb — never a new seam verb** (`../harness/INTERFACES.md §4`, the OnCall/Escalation precedent; the I2 discipline that the store gains no sixth verb).

```
PatternDecline {
  owner               -> principal            // whose preference this is
  pattern_key         : { field_ref, scope_ref } // structural references only — never utterance text
  proposed_value_hash : hash                  // structural hash of the offer's stored {field_ref, scope_ref, value}
  permanent           : boolean               // "don't ask me again" for this pattern, forever
  declined_at  { by, at }
  revoked_at   { by, at }?                    // addressable and revocable, like every stored answer
}
```

**What writes it.** A spoken decline of the offer writes it, and so does a **narrowed acceptance**: an accept carried as `../model/SPEC.md §2`'s `narrow(scope)` response writes a `PatternDecline` for the offered pattern in the same firing as the narrowed store — that record, not the scope ladder, is what keeps §6's "accepting a narrowed scope cannot make the same offer return" true (B8's assertion).

**How it suppresses.** Before offering, the loop looks for a matching `PatternDecline` on `pattern_key`. A record with `permanent: true` suppresses **unconditionally** — every offer at that `pattern_key`, whatever value it would store. A record with `permanent: false` suppresses **only** an offer whose `proposed_value_hash` **equals** the stored one — a re-offer proposing the *same* value stays silent, while an offer proposing a **different** value is a new hash and may ask once. A revoked record suppresses nothing. This is what makes requirement 3 testable: "a later, better improvement may ask again" is exactly "it proposes a different value."

**Why `pattern_key` holds references and `proposed_value_hash` is a hash, not text.** A decline must be comparable across turns without storing what the owner said. `pattern_key`'s structural references locate the pattern; `proposed_value_hash` is computed **harness-side from the offer's stored `{field_ref, scope_ref, value}`** — the value the offer *would store*, not any utterance — so it is deterministic, thin-agent-safe (the model authors no part of it), and equal exactly when the proposed value is equal. Both compare exactly, carry no personal data, and keep this object outside `../security/SPEC.md §4`'s PII classes — so no retention clock attaches to it.

**It is not projectable.** The bundle shape-projection selects kinds, kind templates, rule shapes, shared shapes and resource shapes (`../engine/SPEC.md §1.7a`, the one list). A `PatternDecline` is none of those, so it cannot ride into a published template — the fence holds by what the projection is *able to select*, not by a filter that has to be right.

**It is visible.** Like any stored answer it is shown, editable and revocable from the same surface, so an owner who declined something months ago can find and undo it.

### 3.11 Channel suppression — the per-party stop, and not the per-owner one

*Two stops exist and they are not the same stop (`../security/SPEC.md §10`, "Two stops", split 2026-08-08 under FD-12). The **send halt** is per owner, about volume, and trips on a bounce rate. **Channel suppression** — this section — is per party, about consent, and trips on **one** complaint. Both thresholds are security's law; both readings are this layer's.*

`../security/BUILD.md` Step 6 builds both, and `../app/SPEC.md §6` records the raw facts as events — `sent`, `delivered-failed`, `handed-to-owner`, and `complaint` — while deciding nothing about what any of them means. **Deciding is this layer's.** A bounce is a fact; "stop sending to this address" is a judgement about a fact, and §1's rule that the app holds no policy puts every such judgement here.

**`DeliveryEvent` — the stored shape those reads run over** *(2026-08-31 — the record this corpus asserted, stored and read everywhere, and never printed)*:
```
DeliveryEvent {
  kind: sent | delivered-failed | handed-to-owner | complaint,
  party_ref, channel,
  act_ref,          // the outward act it reports on — the spend's write id (§7)
  at
}
```
Structural members only: no provider payload text, and never a raw address — the address lives on `PartyContact` (§3.12) and is reached by `party_ref`, so this record carries no PII class and takes no retention clock. `../app/SPEC.md §6` records the raw facts into this shape and decides nothing; suppression (this section) and §7's unknown-fate park are reads over it.

**It is derived, not a new atom.** Suppression is computed from the delivery events already stored, against the volume and complaint thresholds declared in `../security/SPEC.md` — the threshold is security's law, the reading of it is the harness's act. Nothing new is stored, no sixth seam verb appears (`INTERFACES.md §4`, the I2 discipline), and no tool is added to §5's contract.

**Its effect is a subtraction, and that is why the floor is untouched.** A suppressed party-and-channel makes an outward act naming them come back **unsent** — the identical shape to a party with no reachable stored address (`../app/SPEC.md §6`), which the loop already handles by taking the hand-me-the-link path. Suppression removes reach; it never creates any. So D20's floor property covers it **unextended**, on O4's reasoning: a path that needed its own floor rule would mean the floor was never a property.

**D20's generated input space — the constructor roster of record** *(printed 2026-08-22; previously widened in three separate BUILD steps with no single enumeration, and a missed widening silently shrinks the property while `fast-check` passes cheerfully)*. The property-test's arbitrary must generate sequences drawn from **all** of: every §5 tool call (each tool a constructor); live content-bound confirmations (including approve-then-drift cases); grant events (`grant.give`, revocation); trigger firings across **all seven** §4 sources; complaint/suppression events (§3.11 — the unextended-coverage claim above is only tested if suppressed parties appear in generated sequences); assisted-call firings (`BUILD.md` Step 7); and external-caller sequences (`BUILD.md` Step 8). A BUILD step that widens the space edits **this roster in the same commit**; the set-equality gate against the built arbitrary lands at Step 3 (`../deployment/SPEC.md §7a`).

**A complaint latches, and nothing self-clears.** **One** spam complaint suppresses that party permanently — no rate, no averaging, at the first one (`../security/SPEC.md §10`, "Two stops"). **That is the whole trigger: suppression is about consent and trips on the complaint alone.** Bounces belong to the *other* stop — the per-owner send halt at security's declared rate (R2) — and this section claims no per-party bounce threshold, because security declares none. Re-enabling is an ordinary attributed owner act through the existing write path — never automatic, never on a timer, never because a later send happened to succeed. This is C9's discipline (a park never self-clears) applied to reach: the system does not restore a capability it withdrew on evidence, because the evidence has not changed.

**The owner is told, once, per party.** Suppression is not silent — an act that comes back unsent surfaces as a gap the ordinary way, saying which party and why, so "they never replied" cannot be confused with "we stopped writing to them."

### 3.12 PartyContact — the object behind "the party's stored contact" and "channel choice, stored per recipient"

```
PartyContact {

  directory_active,                // reusable listing, not existence of the party

  addresses: [{ id, active, channel, type, address, source, evidence_ref?, verified_at? }],

```

**Identity and contact values.** The party's display name remains its existing identity attribute; neither that label nor an address is an identity key. These fields are checked against the evidence’s existing subject/value/scope; a caller cannot stamp verification or upgrade an owner assertion. Changing a value drops its current evidence association unless the existing evidence covers that exact new value; prior versions retain their provenance subject to erasure. No upload, participant verification, authentication, inbox access, send capability or delivery permission is created by this shape. Existing rows follow engine §1.10 additive evolution: retain their party and addresses as active directory entries, with no Student relationship or verification inferred. Missing source/type/slot metadata is explicitly legacy/unknown until resolved through the ordinary attributed path, never fabricated from a name or timestamp.

**Selection and association.** Selecting an existing contact supplies its authorized party Handle. Adding a channel to that person explicitly confirms that association through the existing proposal/OK path, showing the selected person and current contacts (S10); an earlier association is reusable, not re-asked. Names or matching contact strings may retrieve candidates but never auto-merge strangers, transfer a token or establish a party↔principal claim. Name/contact edits, relationship removal/re-add and directory retirement/reactivation preserve party identity, booked attribution and quota references; no delete/recreate reset. Quota calculation stays engine-owned, account linking security-owned.

**Resolved additions persist once.** Submission of a new person's resolved details and relationship is the add instruction: persist the PartyContact and any needed new party together through the existing stored-object `commit` diff, with engine-minted identity and the existing authenticated write id (`../engine/SPEC.md` §§1.17/6). Do not ask an additional save-contact question. Selecting an existing person reuses it without a create. Unsent text, an unresolved identity/platform and rendering create nothing; explicit blank optional contact values remain valid. Each accepted add uses its own write identity and stays within §4a's existing work/effect bounds; gathering multiple people does not authorize exceeding a firing's limits. Report **Saved to Contacts · Student** only after that add's successful acknowledgement, correlated to its submitted draft revision; refusing or unknown is never saved. No match is an empty result, never permission to invent a party. A selected-entry read also reports actual authorized references and their revisions relevant to the proposed contact/association change. Tenant/owner identity is authenticated context, not query input; a guest token, foreign party/cursor or caller-authored owner cannot obtain rows, names, counts, references or existence hints. Malformed selectors use `invalid`/`schema-mismatch`; missing keys yield unavailable protected values, never cached plaintext or reconstructed history. Both console lookup and direct Contacts browse enter through the harness and render this readback on existing console/form surfaces, with the same identity, scope and permission checks. Only the requested slice enters context, with §8's source tags and quarantine; there is no directory-wide context dump. Readback supplies data, never send authorization.

**Edits and removal name their scope.** Use §3.3's existing stable field binding, expected revision and ordinary attributed diff for (a) clearing/editing one contact value, (b) retiring that contact entry, (c) removing a relationship or directory association, or (d) changing a group roster/one booking's participants under that object's own contract. Removing Student changes the filter membership only; removing the directory association hides its reusable listing, retaining identity/history. A group-member removal affects that roster only, not the independent contact or any booking's participants. Removing a group never cascades into saved contacts. Before application, read and disclose actual affected delivery uses, preferred-channel selection, active requests/links, group references and future bookings; distinguish those requiring a resolution from retained historical references. PendingAsk {

Immediately before a rung notification dispatch, recheck the current escalation/rung and total cutoff as well as the current claim and §7 floor. FD-25's `escalation-notify` Grant still covers only notification; in-app rendering needs no outward basis (§3.9). An answer/closure or stale claimant cannot license a later dispatch. Already-dispatched outcomes and unknown fate retain §§3.14/7's receipt and no-retry laws; cancellation does not erase an effect or its evidence. D12–D14/D16/D21 retain their SHOULD weight and their runtime proof at `BUILD.md` Step 5 checkpoint (3); typed registration/clock fixtures prove no persistence, restart or scheduling.

### 3.14 FiringEvent — the object behind "what this firing was shown, did, and decided"

*(2026-08-28 — the sixth instance of the instruction-with-no-object pattern §3.9 named. `../security/SPEC.md §14` owes "execution-level observability — the record of what a firing was shown, which spans ran, what the slice dropped, which rung was notified" before the first real model is bound; `SCENARIOS.md` L2 asserts a firing's assembled context is identical on replay, and nothing stored what any firing was actually shown, so the assertion could only ever be made against a live re-run. This is that object. **Drafted 2026-08-28, not ratified — pending FD-84.**)*

**The invariant, stated first because the two-part shape makes it easy to lose.** There is **exactly one `FiringEvent` per firing id**, written in **at most two write-once parts — birth and seal** — each identified by its **(firing id, part)** part identity under sub-step 2(f), with **at most one of each per firing id** representable by the atomic (firing id, part) uniqueness constraint. Neither part is ever mutated and neither is ever duplicated. **An unsealed record past its firing reads as `interrupted` — derived from the seal's absence, never stored.** A seal records the firing's termination when known; until then its absence supplies the derived reading. This firing record follows its own write-once birth/seal rules, independently of the commitment lifecycle at §3.4.

**Persisted through the existing `commit` verb** — the `OnCall`/`Escalation`/`PendingAsk` precedent (`INTERFACES.md §4`, the I2 discipline). **No sixth seam verb, no additional trigger source, no new event constructor**, and the writes land under sub-step 2's latched-record law.

**Its members are invariants, not a frozen field list.** The exact field list is BUILD-step design work exactly as tool signatures are Step 2's; what is law is what each member must be:

- **(a) A deterministic reference to what was assembled** — the store version, the slice's member refs, and the truncation record — **never a text copy**. L2 replays assembly *from the store*; a copied prompt would be a second, divergent record of something already stored.
- **(b) The model's actual returns, per model call, verbatim** — the structured returns and the final `narrate` text. This is the one thing replay cannot reconstruct, because a probabilistic output is not a function of its inputs.
- **(c) The tools that fired**, each with its **declared reversibility class** (§7 rule 1) and its results **by reference**.
- **(d) A closed termination member, carried by the seal:** `completed-verified | gap | escalation | park | budget-exhausted | discarded` — every termination the corpus actually names (§4's four conditions including the escalation ending, and X4's discard, whose *"the turn record itself survive[s] by law"* is this record). **`interrupted` is never a stored member** — it is the defined *reading* of an absent seal.

**What it sits beside, and never absorbs.** The record **references** the four fragments that already exist and refactors none of them (the `../engine/SPEC.md §1.14` precedent — naming a primitive is not unifying its instances): X4's turn state, by write id · `Escalation.ladder_state` (`../engine/SPEC.md §1.13`) · the stored delivery events §3.11 reads · the `PendingAsk` of §3.13.

**The D20 consequence, stated so the roster is not silently widened.** Both record parts ride `commit` — writes an already-generated firing makes — so §3.11's printed constructor roster is **unchanged** and no new constructor enters D20's generated input space. (If execution-time analysis contradicts this, widening the roster *in the same commit* is §3.11's own rule.)

**The PII posture.** The structural members — (a), (c), (d) and the identities — carry no personal data and are permanent. The **verbatim model-return members** of (b) are assumed PII-bearing and take `../security/SPEC.md §4`'s **crypto-shred** pattern: encrypted at rest, so lawful erasure destroys readability while the append-only structure survives and `../engine/SPEC.md §1.10` holds literally. Key granularity is Step-level design work bounded by that invariant. `../security/SPEC.md §4` owns the admitted field/copy inventory and subject associations for personal context, current drafts, summaries, provenance and linkable structural references; §§8/12 own restore fences and the complete erasure attestation. The structural/no-personal-data assertion requires that inventory assessment, never automatic anonymity from a hash or reference.

**Required-on-read, and its opposite side by side, so neither is read as the other.** Domain records evolve **"additive-only with declared defaults"** — *"no field is removed or re-typed, every historic shape stays readable (upcast on read, never rewrite)"* (`../engine/SPEC.md §1.10`). The `FiringEvent` vocabulary is the **reverse**: **a reader encountering an unknown member refuses the whole read, fail-closed** — never a partial read, never a skip — because a skipped event in an audit trail reads as *"nothing happened,"* which is the one wrong answer a log can give. **An absent seal is not this case**: it is a *defined* state — the true trace of a firing that died between birth and termination — read as `interrupted` and surfaced, never hidden. **The refusing layer, named (2026-08-31):** the refusal is the **harness reader's** — the engine's `../engine/SPEC.md §1.16` store returns the record as stored, append-only and uninterpreting, and every harness read of a `FiringEvent` decodes against the closed vocabulary and refuses whole on an unknown member; the cross-layer test drives an unknown-member record through the engine store and asserts the refusal at the harness read.

**The latched-record law (part of FD-84).**

- **(a) The two write families, defined once (FR13).** §7's K1 sentence, X4's printed constraints and §5.3/`BUILD.md` Step 8's one-commit-point language all point here and restate nothing.
  **Work commits** — writes executing the firing's routed intent: domain-structure writes, and every basis-spending act's commit. Engine horizon preparation from already committed Patterns is a separate domain-writing job under `../engine/SPEC.md §5`, not application of that draft and not loop bookkeeping; its effects are real, separately recorded and not counted as harness work commits. The birth ordering in (b) covers a firing that requests it. **K1's "at most two commits, of which at most one spends a basis" and X4's "one commit point per turn" count exactly this family** — K1's own text already names the spend as the counted thing (*"the commit point is the basis-spending commit"*).
  **Loop-bookkeeping writes** — writes the loop makes *about its own firing*, excluded **by enumeration, never by adjective**: the terminal `PendingAsk` persist (§3.13), the `needs_human` park write (§3.4), `Escalation` advances (`../engine/SPEC.md §1.13`), and **both `FiringEvent` parts**. Uncounted by K1 and X4; each idempotent on a firing-id-derived key. The doctrinal foothold is X4's own wording — *"attribution records and the turn record itself survive by law"* — the corpus pre-approved a turn record outliving the counted class.
  **Post-effect receipt writes are enumerated loop bookkeeping** — only immediate and delayed `DeliveryEvent` facts (§3.11) and publication mint receipts (`INTERFACES.md §3.3`), recording results of already-authorized outward acts. They are excluded from K1/X4's work-commit count; domain edits and basis spends remain counted. Persist the declared structural result, never raw provider payloads or addresses.
  **Each receipt write has its own caller-supplied write id**, distinct from the spent work write id (`act_ref`) and from birth/seal ids. Derive it deterministically, within the owner, from a receipt-family tag and the existing fact identity: delivery = `(act_ref, party_ref, channel, kind, at)`; publication mint = `(act_ref, publication-mint)`, whose payload is the returned complete `minted[]` set. Use an unambiguous branded encoding (§5), not a timestamp or act id alone. Thus `sent` and a later `complaint` for one act are different receipt writes; exact repeated delivery facts are one receipt, while facts differing in any declared member remain distinct. Identical publication replay preserves the original mint set; a different payload on the same receipt id takes the existing `write-id-reuse` conflict, never overwrites or remints. These are existing `commit` writes under `INTERFACES.md §1.2`, not new seam verbs or authorizations.
  **Observation and persistence are separate states of a receipt.** A known result still awaiting storage stays known and must persist under its receipt id even when the rest of the turn stops. Retry that write idempotently, never the outward call; preserve an already stored receipt unchanged. `INTERFACES.md §3.3` owns correlation before this write. When the engine is unwritable, pending receipt content shares (e)'s process-local exception and loss ceiling, with its own receipt id retained for the late write; this promises no durable outbox or delivery guarantee. Receipt absence alone never proves an unknown outcome or an unused basis.
- **(b) Birth — atomic with the first work commit, or durable before preparation.** The birth part carries everything knowable then — the deterministic assembly reference, the trigger/utterance reference, and the model returns and tool calls so far — and, unless already persisted before preparation as below, co-writes **atomically inside the firing's first work commit**, bundled into that commit's payload under the **host commit's own single caller-supplied write id** (`../engine/SPEC.md §6` item 5(c)'s one-id-covers-the-bundle shape), the part checked against its (firing id, part) identity in the same transaction under (f). The property this buys: **no firing that touched domain state can lack its record's birth** — a work transaction co-writes birth unless the preparation path below already persisted it, in which case the transaction requires and preserves that same birth atomically. The assembly reference is pinned even for a firing that later dies unsealed.
  **Before a harness availability request can invoke horizon preparation**, require its existing durable birth or, if none exists, persist birth as an ordinary standalone bookkeeping `commit` under `birth_write_id`, carrying the assembly reference and calls/returns known so far. Resolve an unanswered birth write idempotently before issuing that request; if durable birth cannot be established, no preparation runs. This is an ordering change using existing parts, write ids and claim context, not a new query member or seam verb. The engine checks the stored birth and current claim in each preparation chunk (`../engine/SPEC.md §5`); its history correlates actual effects to that firing. A birth may therefore survive with no preparation and no work commit if the next step never runs; it does not assert either occurred. Later work uses that birth without rewriting or re-bundling it; subsequent calls/returns and the actual termination belong to the seal. Stopping after preparation preserves the completed chunks and birth, then lands the `discarded` seal under (c); crashing leaves birth unsealed and reads `interrupted`, with actual durable effects in engine history and the unrecorded tail subject to (e)'s loss ceiling. An already persisted birth takes §4a's post-birth recovery path, never automatic pre-birth re-enqueue.
- **(c) Seal — composed only at settled termination.** The seal carries the firing's tail — post-birth returns and calls — plus the closed termination member, composed **after check-work settles the outcome, or at the gap/park/escalation/discard decision**. The member is never a guess, and neither part is ever mutated. Landing: where the termination decision itself produces a bookkeeping write — gap → the `PendingAsk` persist; park, budget-exhausted included → the `needs_human` write; escalation → the `Escalation` persist — the seal co-writes atomically **inside that write**, bundled under the host write's own id per (f). `completed-verified` and a `discarded` decision with an existing birth produce no terminal write of their own, so their seal lands as its **own standalone bookkeeping write under its derived `seal_write_id`, the firing's last act**: the firing terminates by landing its record.
- **(d) The no-work-commit firing.** A firing with neither a work commit nor a birth already persisted under (b) — a console read/narration that cannot invoke preparation, a pre-commit discard, or a gap before either boundary — lands birth and seal **fused in one bookkeeping write at termination**: co-written with the terminal bookkeeping write where one exists, standalone otherwise, one call under the derived `birth_write_id`, both part identities checked within it. A firing that persisted birth before a possible preparation request has only its seal left to write under (c), even if no chunk or work commit followed. X4's no-half-applied-domain-effect guarantee covers the atomic user work; completed engine preparation and its records survive under `../engine/SPEC.md §5`.
- **(e) Residual path — engine unwritable, the carve stated honestly.** A firing whose engine seam is unwritable at termination (`unavailable`/`timeout` — `INTERFACES.md §1`'s infrastructure members) holds its pending record as **process-local state — the one named exception to §8's assembled-from-stored-structure rule, printed here as a carve with its loss ceiling.** A process death before the engine returns loses the unsealed content, and **the loss is detectable by construction**: a work commit's write id with no matching birth, or a birth with no seal, reads `interrupted` on the read path and is never disguised. When the engine returns, the record lands **late**, keyed to the **same firing id**, each part as its own standalone call under its derived id — independently retryable, idempotent on its part identity — recording **both** the firing time and the engine-attributed arrival time, so lateness is visible rather than smoothed away. **No buffering daemon, no new trigger source, and no delivery guarantee stronger than the engine's own availability.** The second ceiling, printed with the first: an owner whose engine never becomes writable again never gets that record.
- **(f) The part-identity law — one caller-supplied write id per call, never doubled.** The seam's law is *"Every write carries **a** caller-supplied write id"* (`INTERFACES.md §1.2`), so the **firing id is the parent key of the record and is never itself a write id** — two distinct payloads cannot legally share one id, because *"a known id arriving with a different payload is refused (`{conflict, reason: write-id-reuse}`)"* (`../engine/SPEC.md §6` item 6). Each part's identity is the pair **(firing id, part)**, deterministically encoded as a **branded derived id** — `birth_write_id`, `seal_write_id`: pure functions of the firing id and the part name, no new randomness, branded under §5's branded-id law. **§6's idempotency law then applies to the part identity unchanged**: a part landing where its slot is occupied returns the original result for an **identical** payload and is refused `{conflict, reason: write-id-reuse}` for a **different** one — the part identity is a write identity at record grain, and no new refusal reason is needed (`INTERFACES.md §7.1`'s closed table is untouched).
  **How the identity meets the one-id-per-call law.** On the **standalone paths** — the pre-preparation birth, the standalone `completed-verified` or existing-birth `discarded` seal, the fused no-work-commit write, and (e)'s late landings — the derived id **is** the call's caller-supplied write id, so each standalone part retries independently and idempotently on its own id. On the **co-write paths** — birth inside the first work commit (b), seal inside a terminal bookkeeping write (c) — the **host call keeps its own single caller-supplied write id and the bundled part rides it** (`../engine/SPEC.md §6` item 5(c)'s Order-ref precedent: one id covers a multi-object atomic write), the part checked against its part identity **inside the same transaction**, and a host-call retry is idempotent on the host id.
  **Exactly-one-of-each is engine-enforced** by the **atomic (firing id, part) uniqueness** the part-identity check implies — at most one birth and one seal per firing id representable, on every path, under any mix of call ids (stored per `../engine/SPEC.md §1.16`); a bundle attempting a conflicting part is **refused whole** under §6's atomicity. **Re-entry** (the one bounded retry, §4) reuses the firing id and therefore derives the **same** part ids, and **birth bundles only with the firing's first work commit when not already persisted before preparation** — a wrongly re-bundled birth is inert when identical and refused whole when different — so **a second birth is never representable**.
- **(g) The refused alternative, recorded in one sentence.** Folding terminal verification into the domain commit is **refused**: check-work is the **harness** verifying that the engine did what the model said, by read-back through the model seam *after* tool effects (§4); moving it inside the engine's transaction would make the engine verify itself and migrate a harness responsibility across the four-layer seam.

**The replay invariant.** A recorded firing's assembled context is **re-derivable byte-for-byte from the firing log plus the store** — the mechanical proof of *model-visible ⟺ logged* — and what it replays from is the **birth's** assembly reference, pinned at the first work commit or before preparation under (b), even for a firing that later died unsealed. The machinery that would check it already exists at its own homes: L2's byte-identical assembly (`SCENARIOS.md` — *"the assembled context is identical both times"*) and B9's byte-compared transcripts (`../deployment/README.md` §The one green command, the `b9-twice-run.mjs` row). **The replay CI mechanism itself is not built here** — its landing site is the model qualification step, with the custody rule below.

**Streaming, ruled with the log vocabulary (F3).** It is ruled *inside* this ruling because the vocabulary is the expensive thing to change once required-on-read binds. **The v1 answer is a recorded refusal:** the console renders **complete narrations**, and the firing log stores **final `narrate` text only**; chunk-level streaming is a future **log-vocabulary change under the required-on-read law**, and that is its named revisit path. **The alternative is stated rather than buried** — chunk-level log members from the start, chunks logged and the final message derived — and FD-84's draft carries both, **flagged for the founder's attention**, because perceived write-path latency is an **open finding** (`../deployment/SPEC.md §8` DR-10). It is cited as that open finding, never as a founder want; the founder rules with both visible.

## 4. Responsibility 1 — the loop

- **Turn-driven** (a console utterance) **and trigger-driven**: the loop may fire on a *sale*, a *hold expiry*, a *decline*, a *returned form*, a *clock time*, a *delivery report*, or an *offered* arrival — not only a human turn. (This is what lets an overnight booking progress with no human present.) **Seven sources, and an engine-written `PendingDecision` is not an eighth** — it is found during a firing rather than causing one (§6). **Each source's firing payload is typed at the seam** *(2026-08-31)*: the kind-discriminated `Event` union printed at `INTERFACES.md §3.3` — one member per source, riders discriminated — so a firing decodes its trigger instead of sniffing it. **The `sale` and `decline` sources have named emitters** *(the two this list carried with no writer)*: both arrive through the app's existing inbound event shape (`../app/INTERFACES.md §1`, zero new verbs — the delivery-report precedent below): a completed sale is emitted by the app's commerce surface, and a counterparty's structured decline of an offer (`../engine/SPEC.md §7.1`'s reasoned decline) is emitted by the surface that captured it. *(The delivery report joined 2026-08-21, ratified 2026-08-24 — the retired `CLARIFY.md` §9.4: a bounce or complaint arrives out of band after `send` resolved (`../app/SPEC.md §6`), and with five sources it had no firing in which the harness could ever store it — D22–D23 were MUST scenarios reading a store nothing could write. It rides the app's existing event shape (`../app/INTERFACES.md §1` — "delivery results", zero new verbs); the firing commits the event as an ordinary attributed fact and ends — suppression (§3.11) is then a pure read at the next outward act.)*
- **Initial on-app offer arrival (`offered`) is engine-owned.** The initiator's offer-creating commit (`../engine/SPEC.md §7.1`) emits the fact to the **recipient owner's** existing inbox (§4a); read-only `resolve` emits nothing. It carries the offer reference, recipient owner and creation attribution defined at `INTERFACES.md §3.3`, under the proposed closed-union amendment at its §7.2. Admission matches the authenticated inbox owner and engine-stored offer recipient; a missing or wrong recipient or mismatched attribution refuses before any recipient work. An initial offer needs no sale, form reply, decline or expiry to wake the loop. Re-delivery of that same offer-creation fact is the same inbox entry, not a new consent or commitment; §4a's ordinary enqueue/claim discipline applies. The recipient's stored accept mode governs their yes under §7: only a matching Grant or live confirmation can supply the stored basis that acceptance apply requires. The creation attribution is not that yes. No separate share executor or app-emitted offer source exists.
- **A trigger firing never calls `normalize` (FD-28, ruled 2026-08-21).** All seven sources are structured facts; the firing routes deterministically — assemble the slice (§8), `calculate`, `commit` — and the model is reachable on a firing only through `summarize` (the quarantined read of any free text the trigger carried) and `narrate` (outward text under an existing basis, D7's law). Interpretation is for people; the consequence of an engine-owned condition is the engine's, and a short-lived `normalize(trigger_event)` union is reversed (`INTERFACES.md §2.1`).
- **Check-work before termination:** after tool effects, the agent verifies the committed structure against the normalized intent — turn-driven via `narrate`-from-structure read-back, trigger-driven via an engine re-read of the affected commitments. A detected mismatch re-enters the loop **once** — one retry, not a tunable count, so there is no constant to set and no knob to tune. If the retry still mismatches: **attended**, the mismatch surfaces to the owner as a gap (§6); **unattended**, the firing **parks** (`needs_human.reason: unverified`, §3.4). This is `../model/SPEC.md §8`'s one-bounded-retry rule, whose unattended half that spec assigns to "the harness loop" — this is the harness's half, written out. Completion is never claimed unverified.
- **Termination:** a turn ends when the agent has completed **and verified** the requested effect, or hit a gap it must elicit (see §6), or an escalation — **or exhausted its declared per-firing budget** *(the fourth condition, 2026-08-21)*: every firing carries the independent allowances defined at §4a, and a firing that exhausts the allowance needed to continue **parks** (`needs_human`, D4's shape) rather than continuing unbounded. Step and provider-charge limits are configuration beside the routing config (`../model/INTERFACES.md §2.2`); the effect allowance retains §7's existing basis-spend constraints; what this spec fixes is that exhaustion is a park, never a silent continue and never an error state — the unattended 3 a.m. loop is exactly where an unbounded firing would otherwise be discovered on an invoice.
- **What check-work verifies, and what it cannot** *(stated 2026-08-21 so the claim is not over-read)*: check-work verifies that **the engine did what the model said** — committed structure against normalized intent. It structurally cannot verify that **the model said what the owner meant**: a valid, well-formed, wrong normalization passes it. Attended, the owner reading the `narrate` read-back is that check; unattended, the control is the exam (`../model/EVALS.md`, the reliability set), not this loop. Safety claims built on check-work must be sized to the first half only.
- **Unattended behavior:** when the loop fires with no human at the console and hits an action it cannot take under the standing grants (§7), it **escalates** to a ranked on-call list; if no human is reachable within a timeout it **takes the safe default — park the commitment in a needs-human state and surface it.** It never performs an ungranted across-the-line act unattended. *(The object, the ladder, the channels, and the empty-list case: §3.9.)*
- Concurrency/arbitration of simultaneous triggers is **engine** work (see `INTERFACES.md`) — and that sentence governs **commit-time races** (`INTERFACES.md §1.2`/`§1.5`), which is a different hole from the loop-side one. The **read-staleness** hole atomic commit does not cover — two triggers landing during one firing, the second assembling a slice that has not seen the first's commits — is governed by §4a's per-owner serialization *(pointer added 2026-08-28 so the two cannot be read as contradicting)*. The harness still only guarantees it hands the engine a representable state.

## 4a. Turn flow — the step machinery

*(2026-08-28 — §4 states when the loop fires, when it verifies and when it terminates; `BUILD.md` Step 5's prose says "normalize → plan → tool calls → check-work → narrate" and until now **`plan` named nothing** — no section said who chooses the next call, what a step is, or what the per-firing budget counts. An instruction with no object is not implementable, §3.9's precedent, and this is the loop's own instance of it. **Drafted 2026-08-28, not ratified — pending FD-86.**)*

**The driver ruling: harness-planned deterministic dispatch.** The model produces intent **once**, through `normalize`'s closed intent vocabulary (`../model/SPEC.md §2`). The **harness** then routes intent → tool sequence **deterministically** — FD-28's trigger-firing law (*"firings route deterministically"*) generalized from the trigger firing to the console turn, because the two differ in where intent comes from and in nothing after that. **The model never chooses the next call.** The routing tables are **harness policy the domain pack supplies** (`BUILD.md` §Guardrails, the domain-blind rule — the loop core walks them, domain-blind, and the tables carry the domain). **The tables' provenance, printed as four facts (FD-95, 2026-08-31): producer** — the routing tables are **platform-authored** domain-pack content, written by the platform; never derived at save or install time, never owner- or model-authored. **Storage** — they ship with the harness build as the pack's static configuration, beside the routing config (`../model/INTERFACES.md §2.2`'s precedent); never engine truth. **Interface** — the loop core loads them at boot through the pack's declared policy interface (§5), never through a seam read. **Baseline** — a platform-authored default pack always exists, so marketplace absence leaves routing whole, never empty. **Tool returns are consumed by the harness**, never delivered to the model as a message: the model meets results only as **stored structure**, through `narrate`/read-back.

**Adaptive owner assistance — what the model may propose, and what still dispatches it** *(FD-105, founder-approved 2026-09-12; it **amends** FD-86's fixed-only reading and strikes nothing above)*. Inside an **authorized owner conversation**, after a validated observation of that turn's own context, the model may **propose the next permitted owner action**. The proposal rides the **existing** `normalize` return — its single-intent candidate or its ordered-sequence branch (`INTERFACES.md §2.1`) — so there is still no fifth seam call, no `tool_schemas` member and no tool menu shown. **The harness validates and dispatches each proposal, or records it refused**: a proposed intent outside `../model/SPEC.md §2`'s closed vocabulary, a rule shape off the engine's closed menu, a step the routing tables do not map, or an act without its §7 basis is **inert data** with a recorded disposition — never an executed call. **What this does not move.** A **structured trigger firing** keeps FD-28's fixed deterministic routing, unchanged and not proposable (§4). Return-schema validation (§5), engine-owned calculation, the §7 floor and its permission lookup, the effect allowance above, and the claim/recovery fencing below all bind the dispatched step exactly as before; an untyped identifier in an id position is still a build-time type error. A proposal is a **candidate**, so R1's determinism is asserted over `{intent, store state}` as before — what the model returned beyond intent and fields still changes no routed sequence. The **guest**-interactive side of this boundary is not widened here: the admitted guest request's allowed operation set is `§2`'s, and the guest-console adaptation is its own separately assigned work.

**The current-capability manifest — what the loop may answer a capability question from.** A "can annnä do X / which release adds X" question is answered from a **bounded report carried in the existing owner-console context** (`INTERFACES.md §2.1`), not from model memory. The report is a discriminated value: `CapabilityReport = { state: current, manifest_revision, source_refs: [{kind: tool_surface | rule_menu | installed_adapter, revision}], entries: [{capability, status: supported | unknown | unavailable, source_ref}] } | { state: absent } | { state: stale, manifest_revision, expected_manifest_revision } | { state: unavailable, source: manifest | connections }`. The harness ships the static manifest projected from the closed §5 tool surface and `../engine/SPEC.md §3` rule menu; the app's existing owner-console adapter supplies the current account connection snapshot from `../app/SPEC.md §9` and stamps the report before the harness assembles the turn. `current` requires the build manifest revision and connection snapshot to be present and current; `absent` means the shipped manifest or account snapshot is missing; `stale` means a supplied revision does not match the current build; `unavailable` means the manifest or connection read failed or was unreachable. The harness remains the sole context assembler and validates this bounded shape; the app adapter produces no answer, ranking or continuation.

It reports, per entry, **supported at this version**, **unknown**, or **unavailable** — and **nothing else**: it carries no roadmap, no future-release target and no entitlement inference, so **no release version may be narrated as a promise** (`../AGENTS.md` §Two standing constraints — readiness, never schedule). An absent, stale or unreachable report is narrated as exactly that. **Three refusals that must stay distinct** when the answer is no: **capability** — nothing in the report does this (a taxi dispatch, a payment collection); **permission** — the act exists but this principal has no covering basis (§7); **rule** — the act exists and is permitted but a stored rule forbids this instance (`../engine/SPEC.md §3`). A capability refusal still offers what **is** supported — an ordinary owner Task to arrange the thing, or the attributed money record (§3.8) — and offers no outside act. Graded at `../model/EVALS.md`'s J-set; the report is not a new tool, seam verb or context accumulation.

**This adds no fifth model-seam call and no `tool_schemas` context member.** The four-call pin (`INTERFACES.md §2`) stands unchanged, and **the model is never shown the §5 tool surface** — it cannot select from a menu it has never seen. Stated explicitly because the model-driven alternative would require exactly those two things.

**Composing a payload the harness requested is not choosing a call.** This is the reconciliation the section owes, because §3.2 says *"The LLM composes"* and §5.1's generative-UI row says the model *"proposes the nearest known template"* — and read alone against the paragraph above, those read as a contradiction. They are not. **Dispatch** — which tool, when, and whether at all — is harness-owned. **Composition** of a payload the harness asked for — the generative-UI typed schema, a propose-with-scope proposal — rides the **existing** calls: `normalize`'s returned structure and `narrate`'s proposals. The model fills a shape it was handed; it never decides that the shape should be sent.

**What a step is.** One **routed tool call executed under the floor** (§7), with its validated return consumed by the harness. Not a model turn, not a message: the unit is the call.

**Three independent measures.** The harness owns **routed-step count** and **effect allowance**; accumulated **provider charge** is owned at `../model/INTERFACES.md §2.2`. Neither count can stand in for that monetary total.

**Legacy budget wording.** The “step-and-spend budget” and “step-and-spend ceiling” names in preserved narratives and derived references denote the independent routed-step, effect and provider-charge allowances distinguished in this section — the routed-step count and effect allowance owned here, the accumulated provider charge owned at `../model/INTERFACES.md §2.2`. They are collective shorthand, never a combined counter or a change to any limit.

- **Routed steps** count the §5 tool calls the loop executes, including routed read-only calls and executed calls returning failure. Check-work re-entry retains the firing's count; a refused or unattempted sequence member still needs its disposition but is not an executed tool call. Provider attempts inside a model call are not additional routed tool steps. `max_steps_per_firing` is the existing config limit at the model home above.
- **Effects** count basis-spending commits under §7, with the existing work-commit/basis-spend bounds at §3.14; this is an allowance to execute already-authorized acts, not a new configurable number or a grant. Consume it at the atomic basis-spending commit, even if dispatch is subsequently stopped or its outcome is unknown. Re-reading the original write result does not spend it again, refund it or authorize another dispatch. An internal write may be a counted work commit without spending a basis. Missing, expired or nonmatching authority still takes §7's ask path, not a budget diagnosis.
- **Zero-effect work can still cost money.** `normalize`, `summarize` and `narrate` do not themselves spend an effect basis; their provider attempts consume the provider-charge allowance at `../model/INTERFACES.md §2.2`, including failures, retries and fallbacks. Judgment inside a carrying call is not separately charged again. Provider activity outside the routed tool sequence is still accounted there.

**Exhaustion is measure-specific.** Before the next routed step or basis-spending commit, the harness checks its corresponding remaining allowance; before every provider attempt, the model adapter enforces the monetary protections at `../model/INTERFACES.md §2.2`. If unfinished work requires an operation the exhausted allowance forbids, stop that work and park with `reason: budget_exhausted` and §3.4's `budget-ceiling` cause identifying the exhausted measure, its ceiling and consumed amount. Unused capacity in another measure cannot license the operation. Consuming the permitted effect does not forbid zero-effect check-work that remains within the other limits; it never licenses a second effect. The per-call failure ladder remains `../model/SPEC.md §8`'s, subordinate to the per-firing ceiling; the per-credential daily trip remains suspension under `../security/SPEC.md §10`, not a new park reason. A budget stop uses §3.14's existing `budget-exhausted` seal and landing rules.

**Accounting never renews authority or erases evidence.** Re-entry, fallback, request cancellation/release and an authorized continuation retain consumed allowances for the same firing; a new firing cannot reset its credential's daily total. §7 still governs prior basis spend, fire-time validation and no-resend/no-remint. An unknown dispatched outward result retains `reason: unverified` and its `park` seal; a simultaneous accounting stop does not relabel it as a mere budget failure. Record the exhausted measure in the firing's retained tool/results bookkeeping without overwriting an existing seal. Known results awaiting persistence and recorded receipts retain §3.14's identity, retry and loss rules. Accounting exhaustion stops new work, not those authorized bookkeeping writes, and grants no stale worker ownership (§4a's fencing below). Durable asks still release the active request and claim under the request-release paragraph below; keeping a cost outstanding does not keep a human-waiting request open.

**Bookkeeping is not work.** The `FiringEvent`'s writes are neither steps nor counted commits — §3.14's work-commit-family law excludes loop bookkeeping by enumeration, including its receipt writes. These exclusions do not exclude charges for provider attempts already made.

**What proposes completion.** The **routed sequence completing** — every step executed, or refused with a disposition — is what proposes that the firing is done. **Check-work then verifies it** (§4). Completion is never model-claimed; §4's law is unchanged, and this section only names the thing check-work is handed.

**The compound utterance routes as one sequence (part of FD-86).** A compound utterance normalizes to `normalize`'s ordered-sequence branch (`INTERFACES.md §2.1`), and the harness routes the steps in order. **Independent steps proceed** — a step that does not depend on a failed or refused step executes normally; there is no global halt. A step **dependent on a step that failed, was refused, or went unattempted** takes the internal disposition **`refused-unmet`** — a stored, reported outcome at the routing layer, deliberately *not* a seam refusal reason (`INTERFACES.md §7.1`'s closed table is untouched; this is bookkeeping about the sequence, not a seam return). An unfinished sequence never claims done: check-work is handed the whole routed sequence (above), and R4 gates it.

**Firing serialization — per owner, one inbox (part of FD-86).** Firings for one owner are **serialized**: one **engine-stored** inbox (storage at `../engine/SPEC.md §1.17`; enqueue and claim are ordinary engine writes under `INTERFACES.md §1.2`'s idempotency law), FIFO claim semantics, one active firing at a time. **All seven trigger sources and ordinary console turns queue identically at v1** — no wake-priority distinction. **A firing's slice is assembled *after* claim**, so a later firing sees earlier commits. Engine arbitration governs the commit-time race; this governs the read. Control of an existing firing follows the stop paragraph below, not ordinary turn admission.

**Claim ownership and fencing.** A claim identifies its owner, inbox entry, firing and ownership attempt in engine-stored state; the worker cannot confer ownership on itself. At most one worker can act as the current owner of an owner's active firing. A dead or invalidated claimant must be recoverable without its cooperation. Recovery invalidates the old ownership before another worker can act; competing recovery attempts take the same durable disposition once per lost claim. A stale worker cannot commit new work, spend a basis, advance the loop or dispatch an outward effect. Enforcement must hold at the work commit and at actual dispatch, including a worker paused after an earlier ownership check and resumed after takeover; a process-local flag or an unchecked check-then-send gap does not satisfy it. An idempotent lookup returning an already-applied write is evidence of that write, not renewed ownership or dispatch permission.

**Recovery depends on the durable birth, not a missing response.** Resolve a racing or unanswered commit through its existing write id before classifying the loss. **Before birth (FD-96):** the claim releases back to the inbox for re-attempt, and an **owner-visible loss record** is written — attributed to the lost claim/firing and recovery, surfaced like any gap. Release and loss recording have one atomic, idempotent disposition (storage home: `../engine/SPEC.md §1.17`): repeated recovery cannot duplicate either, release a later claim, or lose the entry. The re-attempt follows ordinary FIFO; a later, distinct pre-birth death has its own visible loss. **After birth:** retire the lost active claim without automatically re-enqueuing or executing that firing. Its existing birth remains; absent a seal it reads `interrupted` under §3.14 until an authorized resume or discard through §5.3's existing turn controls. This releases the dead claimant's hold on ordinary queued work; any authorized continuation still acquires exclusive ownership under this section. Resume/discard retains §7's commit-point, basis and no-refire constraints and the existing principal/credential boundaries; recovery is not consent and cannot clear a human-only park.

**Fencing preserves evidence.** Ownership loss does not erase atomic work, spent bases, observed receipts or either write-once record part. Already-authorized receipt persistence and retries remain governed by §3.14(a), including a result observed by the old worker before or after takeover from an act dispatched while authorized. Persist only that correlated fact under its receipt identity, never new intent or dispatch disguised as bookkeeping. Pending record parts retain §3.14's residual, identity and immutable-seal rules; stale ownership grants no right to make a new termination decision. Unknown dispatched outcomes retain §7's unverified disposition, with no resend/remint; a lost process-local observation retains §3.14(e)'s explicit loss ceiling.

**Stop reaches active work; durable asks release requests.** The authenticated stop/discard control in §5.3 and §7 targets the running firing through the existing turn-state machinery **without joining behind it as another queued normal turn**. It stops remaining work even while a model or app request is pending; §7 resolves commit/dispatch races and preserves already-observed receipts independently. Once an ask is durable under §3.13 (with its §3.14 termination), release the active cloud request and claim rather than hold a request open awaiting the human answer. A later answer is ordinary stored-answer work under that home's authority and expiry rules, never an implicit resume or renewal of a spent basis. Releasing or cancelling a request does not establish the fate of a dispatched act. Neither control creates a new trigger source, seam verb, executor or service; ordinary inbox FIFO is unchanged.

**Implementation boundary.** The existing engine storage owns claim arbitration and durable recovery (`../engine/SPEC.md §1.17`); the harness and its adapters enforce execution/dispatch fencing and request release. Lease/heartbeat mechanics or a proved equivalent, including detection and timing choices, remain adapter implementation work. Required proof uses injected time and competing workers at `BUILD.md` Steps 5/8 and `../engine/BUILD.md` Steps 5/9; this contract fixes observable effects, not an unbuilt algorithm.

## 5. Responsibility 2 — the tool contract

One canonical surface (resolves the prior double-statement). **Every tool declares a reversibility class** (§7). Correctness-critical values are engine handles. The tables below specify each tool's name, reversibility class, and purpose — deliberately not its exact typed signature: signatures are the **builder's design work** (BUILD Step 2), constrained by the reversibility classes here and pinned by the `SCENARIOS.md` suite.

**The return leg is under contract too, not just the call.** Every tool **return** validates against its **declared return schema** **before the harness consumes it** *(consumer corrected 2026-08-28 — §4a abolished the model-as-return-consumer reading; the requirement is unchanged, only who is downstream of it)*; a mismatch is surfaced as a **structured error** (which shape/constraint failed and what the next move is), never a silent pass-through and never an undecoded payload handed onward. A tool whose call is typed but whose return is unvalidated is a hole in the thin-agent boundary — the harness would be routing on an unchecked payload, and whatever reached the model as stored structure afterwards would inherit that — so both legs get the same contract. (`BUILD.md`'s Tool ACI guardrail is the prose face of this return-legibility requirement; the normative rule is here.) **There is deliberately no argument-repair loop** *(recorded 2026-08-08 so the absence reads as a choice, not an oversight)*: the common industry pattern — validate the model's tool arguments, and on failure ask the same model to repair them under stricter instruction — is not adopted, because a repair turn is precisely an invitation for the model to author a correctness-critical literal on the second attempt. A malformed call surfaces as a structured error and re-enters through the ordinary path; the loop's one bounded retry (§4) is the only retry that exists, and it re-verifies rather than re-authors.

**Every opaque cross-seam identifier is a branded type, never a bare string** *(2026-08-28)*. The write id (`INTERFACES.md §1.2`), `proposal_ref`, an ask id (§3.13), a token digest ref, a handle ref, `connection_ref`, a credential ref, and the derived `birth_write_id`/`seal_write_id` of §3.14 are **branded/nominal types at the tool-contract level**: a bare string in an id position is a **build-time type error**, not a runtime check — M2 applied at the tool boundary, exactly as the reversibility class is (`BUILD.md` Step 2's unconstructability rule). The reason is that these identifiers are structurally interchangeable and semantically not: nothing but a type stops a `proposal_ref` being passed where a write id belongs, and the failure would be silent. This **strengthens an existing discipline and forks no policy** — the return-leg-validation precedent. One clause relating it to `../engine/SPEC.md §4`: **handles remain the enumerated stored-object case** with their set-equality gate; this law covers the residue of opaque ids that enumeration does not reach.

### 5.3 External clients — the same contract, one more caller

*Appended 2026-08-21, landing `../PRD.md §4.5`'s harness-side rows (RQ-5, RQ-6, RQ-7, RQ-8's harness half; the seam rows are `INTERFACES.md §6`). - **One contract.** An external client calls the tools this section already defines — the surface adds no verb and removes none (`INTERFACES.md §6`; RQ-3). Nothing below is a second code path.
- **What it can never reach: console-only authorization-and-recovery eligibility (FD-24, FD-26).** Minting or widening a Grant, issuing or withdrawing a credential, clearing a credential's suspension (FD-33 — else a second credential re-arms a rate-limited first), confirming a restore, re-enabling a suppressed party — these are console-only by ruling, excluded from parity (`../PRD.md` RQ-2 Out of Scope), and refused at this surface. The principle is FD-26's: a credential must never control who may act as the owner.
- **The floor binds every client identically (RQ-7).** An across-the-line act is refused for an external client on exactly the terms it is refused for the console; possession of a valid credential is attribution, never permission (`../security/SPEC.md §3`, the fifth row). A refusal is **recorded and surfaces in the owner's console**, not only in the calling client's response — the owner learns their agent was refused without having to read that agent's logs.
- **No capability depends on session affinity (RQ-5).** Already structural — context is assembled from stored structure per firing (§8), and there is no conversation to lean on. What this adds: where an interaction spans more than one call, its continuation is addressable by an **explicit handle the client holds** — never an implicit server-side session. Two identical calls against the same store return the same answers, whichever client makes them and in whatever order relative to unrelated calls.
- **An interrupted turn resumes or abandons explicitly (RQ-6).** After an interruption a client can query the turn's state and either resume it or discard it; an abandoned turn preserves any atomic work already committed under §7’s cancellation law; neither path requires the client that started the turn to be the client that ends it. This closes the turn-level idempotency gap the harness backlog carried: §7's re-entry law already forbids re-firing an attributed outward act, and diff-only internal writes re-commit harmlessly — the turn-state shape and its query are the builder's design work (`BUILD.md` Step 8), gated at `SCENARIOS.md` X3–X4. **The same machinery serves the console owner** *(2026-08-28 — the asymmetry closed: it was written for an external client and reads as if only one existed)*: the owner's mid-turn stop is this shape with the owner as caller, and its law is §7's owner's-brake paragraph.
- **The surface is a door, and it stamps (RQ-8, this layer's half).** Free text arriving through an external client is tagged `import` at the door — never a tag the caller asserts (law: `../security/SPEC.md §5`) — and takes the layer-2 tool-less read (§8), because the door cannot establish where the words came from — a credential proves whose agent is calling, never who authored the sentence it carries (`../PRD.md` RQ-8's reason; §8 is the mechanism) — failing closed when no summary can be produced. **Structured parameters — enums, handles, IDs, dates — pass without the layer-2 read:** a structured parameter cannot carry an instruction, so a capability whose parameters are all structured incurs no quarantine cost. One named consequence, judged correct rather than a regression: the §6 noticed-pattern count runs over `owner`-tagged material only, so patterns the owner establishes *through their agent* generate no standing-policy offers (`../PRD.md` RQ-8 Notes).

## 6. Responsibility 3 — the elicitation policy

Turn unknown user policy into stored, reusable policy — **ask once, apply forever** — without nagging, over-applying, or silently guessing. (How this policy was reached: `../archive/07-elicitation-mechanism.md` — history, not authority; the policy is stated whole in this section and its stored objects, §3.10/§3.13.)

- **Fires only on a gap:** A **gap** is a value or policy the agent needs in order to act and does not have — every gap is therefore **blocking**, and this is the whole reason the agent does not chatter. gap-1 missing required input · gap-2 an uncovered floor-crossing · gap-3 a rule conflict · gap-4 an ambiguity the agent can't safely resolve · gap-5 a coverage hole about to go live. (Numbered `gap-N`, not `GN` — the `G` letters name scenarios in `SCENARIOS.md`.) **Anything reversible and inferable → just act** (the floor is the act/ask line).
- **Propose, don't interrogate:** the agent states a *recommended answer and its scope* ("apply the 5-min buffer to all your teaching sessions?"); the user accepts or narrows. Scope-in-the-proposal is the poka-yoke against both nagging (too narrow) and over-applying (too broad).
- **Explicit recurring intent:** a newly submitted creation request describing a repeating schedule prompts “Is this a routine?” with that proposal's OK/Edit actions. Preserve the submitted source span and proposed schedule; an unsent example is not an instruction. OK records the user's confirmed type and accepted scope through the ordinary validated Pattern/Commitment write path (`../engine/SPEC.md §1.4`); Edit or disagreement keeps the input for correction and creates neither a one-off substitute nor a duplicate Routine. Later edits reuse the stored confirmation/covering scope. “Every” in quoted, unrelated, negated or past-tense text is not by itself a recurrence request; interpret the full request and context. Preserve an alternate interval and elicit an absent anchor, reusing a stored one. This is requested recurrence, separate from the noticed-pattern offer and implicit relationship recurrence below.
- **Routine edit/removal scope:** resolve a dated request against the stored Pattern and exact occurrence/generation using engine-verified year, zone and calendar components (`../engine/SPEC.md` §§1.4/2). A wrong weekday/date asks which is intended; missing or ambiguous identity is not “next Monday.” Read back usual destination/travel settings separately from a one-time origin/departure/buffer exception, and saving a named place separately from applying it. Preserve accepted choices across firings/form edits; a genuinely different or stale scope requires renewed resolution. “Remove this run” asks one occurrence versus stop-from-date when unresolved. Before applying the selected scope, show its dated target or concrete future instances/exceptions and dependencies, including stored records beyond the horizon; obtain authorized decisions for stateful instances under §7. Read back any unresolved scope honestly under engine §1.4, without declaring a complete stop. Retry uses the existing write identity (§5/engine §6.6), not a fresh creation; a single cancellation never clears a latch or becomes a series stop.
- **Proposals within an unsaved edit.** The existing form and console edit the same draft, correlated by ref/revision on the render/owner-input path (`INTERFACES.md §3.1`). Its fields, ordinary proposed diffs and computed Handles are pending data, not committed facts. The message’s OK accepts that exact proposal into the draft through `PendingAsk.proposed` (§3.13); Edit keeps it correctable. Acceptance binds the reviewed content, target versions and scope, never chat text or a displayed number. Final form Save submits the reviewed current ordinary diffs and Handles for engine revalidation. Changed inputs invalidate dependent computations and acceptance; unchanged covering scope answers remain reusable. Refusal, abandonment or a stale response cannot apply the pending edit or retarget another object. Independently accepted stored acts retain their own write ids and are reported separately. This uses the existing draft/proposal/write mechanisms, not a domain-specific lifecycle; T2 authoring save/resume/abandon remains below. Control semantics and current field/scope/ask selectors are owned by `INTERFACES.md §3.1`. Unsent text has no effect to reverse; discarding an unapplied candidate preserves the current stored rule. If a write is pending or its outcome unknown, recover it by its existing write identity before claiming discard or retrying. Report independently committed saved-place/contact changes (and any separately accepted booking move) with their actual outcome; abandoning the parent cannot undo them or revoke a Grant. Removing conversation display is not erasure of asks, attribution, grants or domain history; those retain their existing permission/retention homes.
- **Travel values and saved-place consent.** Use `../engine/SPEC.md §5`’s typed route query/result as values in that draft and `../app/SPEC.md §8` for saved-place identity/lifecycle. Resolve absent origin, mode or dated timing before computing; do not assume Home when skipped. Ask usual-versus-dated scope only when unresolved, then reuse the covering answer. Picker Save updates the draft; reusable persistence is a separately accepted principal-attribute diff. Narrate the engine Handle’s source, freshness, estimated duration and departure alongside the current buffer and the proposed replacement total for the selected scope. The estimate is not a measured journey or an arrival guarantee. Input/place revision, estimate freshness and occurrence/generation changes follow engine §5’s invalidation and final Save checks. Unknown travel names the actual limitation; guest readback stays within the Shared fence. Story names, activities and worked durations supply scenario values, never routing branches.
- **Restriction readback and admission agreement:** for a natural-language scheduling restriction, preserve the raw instruction/provenance, resolve its closed-menu type and operands through the engine, show the stored typed rule’s readable meaning and scope, and carry that same rule through projection and final admission (`../engine/SPEC.md` §§2–3). For a duration range, elicit the increment if not supplied or already stored, with its anchor made explicit; a user may explicitly choose the supported range-only form. Missing/ambiguous anchors, incompatible endpoints or unsupported restrictions remain visible gaps, never silently rounded, reduced to a displayed field, or declared enforced. Distinguish duration step from start-time granularity. The English overnight window and both buffers remain kind-scoped; editing presentation or role labels cannot silently rescope rules, release commitments or reset quota. **The participant-quota choices are elicited, stored and read back, and none of them ships a default** *(2026-09-11; the law is `../engine/SPEC.md §3`'s participant-quota block and this sentence only says what the loop does with it)*: a stated monthly allowance is resolved into **which denomination it is** — a count of lessons, an amount of booked time, or both as two rules — and an amount whose denomination is ambiguous is a gap, never a guessed count. The **counted identity and period** are confirmed explicitly: which offering or scope is counted, and that the period is the month the lesson takes place in on the owner's own calendar zone rather than the month a link was opened or a use begun; a request to count something else is a different scope answer, not a re-reading of this one. Because the two limits are independent, read them back as two, and never narrate one as satisfied because the other has headroom. The **cancellation-release choice is asked once, at the moment a stage is actually reached with no stored answer**, as the engine's two named options — release the count and booked time, or keep them counted — and the stored answer is read back beside the limits it governs; the stages are separate questions and answering one never answers another. The harness proposes and records; it authors no answer, ships no universal release or no-show rule, and a still-unanswered stage is narrated as the open question it is, never as a completed policy. A scope edit that would re-partition existing draws is likewise an explicit stored decision before it applies. Field/rule removal follows §3.3’s current dependency and revision checks. A dependency without a supported authorized resolution, or a pricing shape outside the engine menu, remains an explicit limitation, never simulated by overwriting a calculated value. **Conditional rate by booked participant count is on that menu** *(2026-09-11; `../engine/SPEC.md` §§1.5/3)*, so read it back as the stored tiers it is: propose and confirm the **currency and the per-hour basis explicitly** before an hourly amount is treated as settled — one combined proposal may confirm both, and the same number may carry another explicit basis or currency — then read back the engine-derived lesson total for the selected duration, never a per-participant multiplication. An amount whose currency or basis is unconfirmed is a gap, not a stored rate. A consistency remedy is narrated with all source refs and complete operands under `../engine/SPEC.md §8`. Read back a coordinated `edits` entry as one jointly required choice, including unchanged contributors; never split ineffective members into separate alternatives. Choice/confirmation and current authority must cover every member. Send the whole chosen set through the ordinary attach-point diff in one commit/write id with current-state revalidation and no partial application under `../engine/SPEC.md` §§6/8; a stale or unauthorized member refuses the set, never silently narrows it. The existing governing/own/latent routes remain, and an unsatisfiable composition never receives an override affordance.
**Quota scope-decision carrier.** A quota scope edit that would split or merge existing draws is an engine question with the quota rule as its subject, distinct from a definition-only schema question: the harness reads the engine's `PendingDecision` with exactly **keep existing scope** or **apply reviewed repartition**, and carries the rule ref/current revision, proposed target/revision, complete affected booking/draw refs and the owner-authored answer through the existing stored-object diff. The harness reads a rule-subject decision through that member and **supplies no booking for it**; a record carrying both members with different refs, or neither, is the existing whole refusal rather than something narrated. **The closed Step-0 `PendingDecisionRead` scaffold remains the historical commitment-backed fixture; it cannot be treated as successor proof or as a rule-subject read until the typed reader, stub and Step-1 fixture propagation named by `harness/BUILD.md` land.** The harness narrates the engine's names unchanged, asks only when the decision is missing, and applies none of it from `PendingAsk`/draft state. A stale target or revision, incomplete assignment or changed affected draw is surfaced as the existing whole-diff refusal; a successful replay returns the original result. This is a carrier and elicitation control, not proof of engine re-partition math.

- **Store by what the answer governs:** Rule / Grant / Board-field / Commitment-field / Exception — each **addressable** (shown, edited, revoked).
- **Ask-once** is enforced by the store: before asking, check whether a stored answer at a covering scope already resolves it. Scope ladder: `instance < kind-on-board < kind-global < board < customer < global`.
- **The noticed-pattern offer — explicitly not a gap, explicitly non-blocking.** When the owner hand-sets the same field to the same value repeatedly, the agent may offer to record it as standing policy. This is **not** a sixth gap: the agent has the value, so nothing is blocked and nothing is missing. It is an offer, and it fires under these restrictions, all of which are structural rather than advisory:
  - **Inline only.** It fires on the console turn in which the owner performs the repetition — never queued, never surfaced on a trigger firing, never in the absence of a human. This makes "it never speaks unprompted" true by construction rather than by policy, and it is why it does not touch FR-B (`../app/SPEC.md §3`): it is a response inside the owner's own turn, not initiation.
  - **Rule and Board-field proposals only.** Never a Grant — a Grant's scope comes from the owner's own ranked setup answers (§7), and an inference wearing a confirmation is exactly the substitution the floor exists to prevent. Never an Exception — an agent-proposed hole in a governed board would defeat the go-live gate.
  - **Counted harness-side, over `owner`-tagged material only.** The count runs over the already-assembled relevant slice (§8), reading only strings whose source tag is `owner`. Guest, import and document text is not countable — a stranger must not be able to manufacture a pattern that produces a rule proposal on the owner's board. No engine call, no new query type.
  - **The detection never enters the assembled context.** It is computed *from* the slice, never carried *in* it. The context contract is a closed shape, the truncation ladder cannot rank a detection (it is *about* a scope, not *at* one), and a firing that cannot fit a self-sufficient slice **parks** — so a detection competing for context budget could cause a park.
  - **Known ceiling, stated rather than hidden:** the slice truncates deterministically under a full budget, so the count undercounts on busy boards. The offer fires *less* often exactly where repetition is most common. Acceptable for a heuristic offer, unacceptable for anything correctness-critical, which is why it is neither.
  - **The model may phrase it and suggest a scope; it never authors the pattern.** The count is structural.
  - **It exists for an owner only if that owner turned it on.** The stored answer is named **`self_improvement`** — the **self-improvement setting**, and this is the name the rest of the corpus cites it by (`SCENARIOS.md` B6–B7, `BUILD.md` Step 4, `../app/SPEC.md §3`, `../app/SCENARIOS.md` C7). It is elicited like any other setup answer (ask-once, above), stored addressably, and revocable. Absent or off, the mechanism does not exist for that owner — nothing detects, nothing counts, nothing is offered.
  - **The repetition threshold is a parameter of that setting, not a constant.** How many identical hand-sets trigger an offer is **elicited from the owner with a seeded default**, stored addressably, and revocable like any other stored answer — repetition tolerance differs per shop, so no number is fixed in this spec. The count (below) runs against the owner's stored threshold.
  - **A decline is remembered** (§3.10), so accepting a narrowed scope cannot make the same offer return. Without that record the offer would nag by construction, because a narrowed answer re-satisfies "no covering answer at this scope."
- **An engine-written `PendingDecision` routes through this same path — it is not a sixth gap, and it is not an additional trigger source (§4).** This is the harness half of `../engine/SPEC.md §0`'s law: the engine records questions and never asks them, so a `PendingDecision` (`../engine/SPEC.md §1.14`) it writes is **inert until this loop reads it** — it is **discovered during a firing the loop was already making**, typically the clock trigger at the deadline (§4's fifth source; `SCENARIOS.md` P2), and never causes a firing of its own. Nothing surfaces it but the loop. Once found, a `PendingDecision` is gap-1 with its answer set already enumerated: the harness surfaces the engine's named choices through the **existing** store-routing/elicitation machinery, exactly as it routes the freed-window keep-vs-reopen question (`../engine/SPEC.md §1.11`'s `decision`, `SCENARIOS.md` P1 step 7). The harness adds, renames, and reorders nothing; a choice whose consequence crosses the customer-facing line is floor-gated per §7 like any other act, and one that does not is an internal write at full autonomy.
- **Conflict:** vs a *governing* rule → **hard stop** (only forward move is a recorded exception); vs the user's *own* rule → surface both, require an **explicit override stored with a reason**; **latent** inconsistency → alert, don't block.
- **Correction/revocation:** edits/revokes surface downstream impact before applying; outward consequences cross the floor.
**Blocked rule candidates — what the harness carries, and what it may not author** *(2026-09-12; the affected-commitment half of the bullet above. Surfacing downstream impact is a display; refusing to apply over a real record is a gate, and the gate's law is `../engine/SPEC.md §8`, restated nowhere — FR13.)* A candidate rule revision whose affected-commitment compatibility result carries blockers is **not a sixth gap and not a conflict**: it is gap-1 with its answer set already enumerated, routed through the existing store-routing/elicitation machinery exactly as an engine-written `PendingDecision` is. The harness **narrates the engine's own members** — the blocking records, each violated candidate constraint and the engine-named resolutions — and **authors none of them**: it invents no blocker, no reason, no additional resolution, no grandfathering choice and no override affordance, because the engine makes that path unreachable for this result. While the candidate is blocked the harness keeps showing the **stored** rule as effective beside the proposed one.

**Resuming a blocked candidate, and the answers that must not be re-asked** *(2026-09-12)*: the candidate is **retained, not engine-stored** — its home is the app account-document adapter's operation record (`../marketplace/SPEC.md §3`, which already retains a pending replacement's candidate fields and branch), and the current verdict is **computed on each check**. The answers already settled on the way there survive in the retained structured candidate of the *Proposals within an unsaved edit* contract above — including the **definition branch** (replace the existing definition, or save a new one), which is re-presented as already answered rather than re-asked, under the same ask-once discipline as any covering answer. What is **not** reused is the verdict: a resumed candidate is revalidated against current records before anything applies, and an OK given against an earlier clearance is stale (`INTERFACES.md §3.1`'s stale-response rule). A booking move recorded while the candidate stands is an ordinary authorized act under §7 — waiting for an outside reply authorizes nothing — and discarding the candidate leaves both the stored rule and any independently accepted move exactly as they are.
- **Implicit recurrence:** a repeat counterparty (the same person's third session, with no formal recurrence rule) is treated as a standing relationship — on an owner-side cancel the agent offers to invite a rebook rather than closing a dead one-off. "Observed repetition" names both in English and nothing else.
- **T2 authoring:** templates front-load — **a worked example of a *populated* catalog, not a guarantee every account has one** *(scoped 2026-09-12: Situation C's operator installs a governing bundle that ships its kinds + rules, so their onboarding is mostly *adopt + confirm*; the founder's initial catalog is **empty**, so that run is one branch of the route below and never the universal first route)*. **The route is marketplace-first, and the lookup is real** (FD-105; the retrieval contract is `../marketplace/SPEC.md §6` and the result's carrier is `INTERFACES.md §2.1`): a shareable need the owner just expressed is answered from an actual catalog lookup **before** authoring begins, and each outcome has its own continuation — a **suitable** result opens with the **nearest template pre-shaped**, customized Lego-style (§5 generative-UI); an **unsuitable** one is reported as no match rather than pre-shaped anyway; a **successful empty** result permits neutral from-scratch authoring; **unavailability** remains distinct and permits retry or user-chosen authoring; and the owner **declining** a suitable result permits that same neutral authoring, with the decline recorded rather than re-offered (§3.10). **No listing, template or emptiness is ever narrated that the lookup did not return**, and a seeded fixture is not proof of owner authoring (`../marketplace/SPEC.md §2`). ## 7. Responsibility 4 — the clarify/permission policy (the inviolable floor)

The one thing a user cannot configure away. Everything above it is user-configured (grants).

**The floor = the reversibility line.** The danger of autonomy is not acting, but acting *irreversibly on a wrong inference*; reversible mistakes cost ~0, irreversible ones land on third parties, money, and the user's only records.

1. **Every tool declares whether it crosses the line:** third-party communication / value transfer / destruction of the sole record — and, since FD-24, **creation or widening of an authorization** is its own gated class (below).
2. An across-the-line act fires **only on an explicit basis** — a live confirmation, OR a stored **grant** whose action-class, operation, scope and conditions actually match.
3. No matching basis → **ask. Never infer a grant. Silence ≠ consent.**
4. Every crossing is **attributed** `{who, basis, when}`.
5. **Property-based, not an enumerated list** — a never-seen tool is classified by its declared property. Reversible work runs at full autonomy. A tool whose reversibility class is **undeclared or unclassifiable is treated as across-the-line: the floor fails closed, never open** — an unknown act asks, it never runs unattended on the guess that it was reversible. (This is M2's twin at the tool boundary: a missing reversibility declaration is made unrepresentable at the tool-contract type level — `BUILD.md` Step 2 — so "undeclared" is a build-time impossibility; rule 5 is the runtime backstop for anything that ever slips the type.)

**Where a rule is enforced, stated as law rather than left to build-time taste** *(2026-08-28)*. **Schema omission, prompt filtering, facades, wrappers and listener order are not enforcement.** A rule is enforced **only where the operation that executes the state change refuses** — because a direct or alternate caller bypasses everything upstream of that operation: a trigger firing (§4's seven sources) routes without `normalize`, the external surface (§5.3) is a second caller by construction, and a future tool is a caller nobody has written yet. Anything that works by *not offering* the act is a presentation of the rule, not the rule. This states where the floor's existing rules bind; it permits and forbids nothing new.

**The test policy that follows from it, at the floor-property's home.** Every consent or permission rule gets a scenario that **drives the forbidden call through the executor and asserts the refusal** — denial is tested **at the executor**, never inferred from a call's absence from a schema or a menu. D20's generated sequences already drive tools directly (§3.11's constructor roster is what they draw from); this sharpens what its assertions must check, and adds no rule to the floor.

**Authorization is its own floor class (FD-24, founder-ruled 2026-08-21).** The three classes in rule 1 describe what an act *does*; creating or widening a Grant changes **what future acts are permitted**, and an ungated grant write would let the loop author its own basis — the substitution this floor exists to prevent, run one level up. So: a Grant is minted or widened **only on a live, content-bound owner confirmation at the console**. A Grant is never the basis for minting a Grant; the act never runs unattended; `grant.give` arriving on a trigger firing or through the external surface (§5.3) is refused, not queued. The write itself still persists through the existing store path — no new seam verb — but at the tool boundary it carries the **`authorization`** class and the gate above. Narrowing or revoking a Grant is not widened by this rule (revocation already takes G3's impact path). This is why `../security/SPEC.md §5`'s "a successful injection could only propose" holds for authorizations too: a proposed Grant that no live owner confirms stores nothing. The same live owner gate governs creating/widening §3.6's operation-scoped Shared token authority, persisted through that existing authorization path; an outside report and an internal report permission cannot create a standing floor basis. **The one carve: the engine-minted `ShareGrant` (FD-32, ruled 2026-08-21).** FR28's stored accept modes have the accept mint the counterparty-side `ShareGrant` unattended, on a trigger firing, on a Grant's basis — three of this paragraph's prohibitions — and without a carve FD-24 killed auto-accept. The exemption is exact and single: the `ShareGrant` minted by `../engine/SPEC.md §7.1`'s stored-accept path is the **application** of a Grant the owner already minted under this paragraph's discipline (the accept-mode Grant, elicited and confirmed live), scoped to exactly the share it accepts — never a widening, never elicitable by the model, never mintable from any other path. Everything else this paragraph says stands unchanged.

**Re-entry never re-fires an attributed act — and the record that stops it is the spend, not the proof of delivery** *(sharpened 2026-08-22: one record was being asked to mean two things, and the two readings each broke a MUST)*. When the loop re-enters after a check-work mismatch (§4), it re-verifies and may re-commit stored structure; it does **not** re-issue an across-the-line act that already fired. Two facts, two rows, both already specified: the `{who, basis, when}` record written inside the commit is the **spend of the basis** — from that commit on the basis is unusable, so an interrupted or re-entered turn can never fire the act as unspent (X4's commit-point constraint). The **evidence that the act reached the world** is the *delivery event* the app's raw outcome writes back (`INTERFACES.md §3.3` — `sent | delivered-failed | handed-to-owner`), a second attributed fact. A send of unknown fate therefore holds a spent basis and **no** delivery event — which is exactly why it parks as `needs_human.reason: unverified` and is never retried, rather than being read as delivered. A second send is a new act needing a new basis, exactly as rule 2 requires of any crossing — and K1's turn-wide count reads precisely: **at most two commits, of which at most one spends a basis**. **Idempotent internal writes re-commit harmlessly** — diffs, and any write carrying its caller-supplied write id (`INTERFACES.md §1.2`), which returns the original result rather than applying twice; a create without its id is not in that set, which is why the id exists. This rule exists because an outward send is not idempotent at all. (The same discipline the guest seam already carries at `../security/SPEC.md §3`, where hold creation is idempotent per guest-and-interval — a double-tap returns the existing hold, never a second one.) **Receipt persistence follows §3.14; cancellation follows the owner’s-brake law below.**

**The owner can stop a firing in flight, and what that costs depends on the commit point** *(2026-08-28 — RQ-6's turn-state machinery was written for an external client, and the owner's own reading was left inferable. Same mechanism, second caller, no policy fork: the owner is a caller.)* The console owner stops a firing through the **same X3–X4 turn-state machinery** — no new mechanism, no new verb, no second path. Cancellation stops the remaining work; it does not undo a committed write. Resolve a racing or unanswered work commit by its existing write id (X3–X4), never by assuming that no response means no commit.

- **Before the work commit**, abandon leaves the user's proposed domain edits unapplied, spends no basis and dispatches nothing. It cannot erase completed engine preparation: occurrences, conflict records, attributed history and registrations derived from already committed Patterns survive exactly as `../engine/SPEC.md §5` states. Unsaved new Patterns, proposed changes to usual settings, dated edits, skips and stop boundaries remain unapplied; preparation cannot turn them into committed input. Without an existing birth, birth and `discarded` seal land fused under §3.14(d); with the pre-preparation birth, preserve it and write only the seal under §3.14(c). Resolve racing preparation against its recorded atomic chunks, stop further chunks and report an incomplete window as unknown. A crash uses §3.14's interrupted-record and §4a's claim-recovery rules, never a fictitious clean discard or completion.
- **After the work commit but before dispatch**, preserve the atomic committed work, its birth and its spent basis. Stop without dispatching; there is no delivery or mint receipt to invent, and the basis never becomes unspent. The deliberate abandon seals `discarded` under §3.14(c), not the fused no-work path. `discarded` describes stopping the remaining turn, never rollback or verified completion.
- **After dispatch with no known outcome**, preserve those same committed facts and any other known receipts; park with `needs_human.reason: unverified` and seal `park` with that write. Never infer failure or success, resend, or remint. A subsequently observed result still follows §3.14's receipt persistence law; it does not rewrite a seal or automatically clear a park.
- **After observing a known delivery or publication result, before its receipt persists**, stopping the remaining turn does not make the result unknown. Stop work immediately and persist that exact receipt independently of the stop under §3.14 before landing the final standalone seal; the cancellation decision seals `discarded` with the observed result in its tail, without claiming check-work completed. Engine unavailability follows §3.14(e), not a resend/remint path.
- **After the receipt is persisted**, preserve it unchanged; cancellation during unfinished check-work seals `discarded`, not `completed-verified`. If termination already settled and its seal exists, preserve that write-once seal; a later stop cannot replace it. A verified completion remains verified, and a parked firing remains parked until its ordinary attributed recovery.

In every case the existing §3.14 birth/seal identity and residual-write rules apply; a dead firing with no seal reads `interrupted`, never an invented terminal member.

**A live confirmation is content-addressed.** The basis rule 2 accepts — "a live confirmation" — binds to the **exact act it confirmed**: the tool plus its canonicalized arguments. Approve *"send Maria the 3 pm move"* and let the argument become 4 pm before it fires, and the 4 pm send has **no basis** — it is a new act needing a fresh confirmation or a matching grant (rule 3), never carried by the 3 pm approval. The confirmation's identity — tool + canonicalized args — is exactly what `basis` records in rule 4's `{who, basis, when}`, so an approve-then-swap-args can never read as authorized after the fact. (A grant basis is already content-scoped by its `action_class`, `operation`, `scope` and `conditions`; this closes the same gap for the live-confirmation basis, so the two basis kinds fail the same way when the act drifts from what was authorized.) **And the binding is re-verified at fire time, over what the recipient will actually receive** *(2026-08-21, closing the deep-pass drift finding)*: the arguments name a payload and a party, but the narrated content is derived from stored structure *as of the send*, and the address is resolved **by the harness** from the party's stored contact *as of the send* (2026-08-22 — resolution moved here from the app, which sends to the literal it is given and resolves nothing; `INTERFACES.md §3.3`'s `recipient` shape) — both can drift after approval through ordinary internal writes. So the send fires only if the narrated-content identity, the resolved address, **and the party's un-suppressed state** (§3.11 — a complaint latching between confirmation and fire must stop the send, because that direction is the unrecoverable one) match what the confirmation was shown; any drifting makes it a **new act needing a fresh basis**, exactly as a changed argument does. **And the act awaiting confirmation is stored, not held in flight** *(2026-08-31)*: a floor ask persists the act as the `PendingAsk`'s `pending_act` member (§3.13 — tool, canonicalized args, class, operation and scope), so the confirmation has a stored referent to content-address and an interrupted turn loses no pending act.

**Canonicalization law** *(2026-08-31 — the definition the paragraph above leans on, printed as something a builder can implement)*: the canonicalized arguments of an act are its tool identifier plus its argument structure encoded **deterministically** — structural members only (branded ids and refs, typed values through the `INTERFACES.md §1.4` vocabulary's encoding, never utterance text), keys sorted, declared defaults materialized — so two acts are the same act **iff their canonical encodings are byte-equal**. It is an encoding function, pure and total over valid calls, built once at `BUILD.md` Step 2 and used by both basis kinds: the live confirmation records it as rule 4's `basis`, and a grant's covering check compares against it. **Narrated-content identity is defined the same way, one level up:** the identity of an approved narration is the canonical encoding of its **derivation inputs** — the stored-structure member refs and their store versions the narration was derived from — recorded at confirmation; at fire time, the same members at the same versions mean the shown content stands, and any drifted member makes the send a new act (the fire-time re-verification above, its equality now defined). The re-derived *prose* is never the identity — `narrate` is a model call, and prose equality would be both unstable and unverifiable.

**Standing authorization = a grant:** `{ action_class, operation, scope, conditions, expiry, revocable }`, sitting above the floor, elicited from and owned by the user.

**The grant's members, closed and shaped (2026-08-31).** `action_class` is the **closed union** `third-party-communication | value-transfer | destruction | authorization` — rule 1's three classes plus FD-24's, property-classified per rule 5; a fifth class is a spec change, never a widening. `scope` is `{ rung, subject_ref }` — the rung from §6's ladder (`instance < kind-on-board < kind-global < board < customer < global`), and the subject that rung binds. **`operation` is one typed purpose, separate from risk class.** It identifies the supported operation of the actual validated §5 tool call, using that tool's required operation discriminator, never arbitrary caller prose or a second purpose field. It is a discriminated value: the operation tag plus any required structural binding; `reminder-notify` carries the confirmed policy reference/revision, and `escalation-notify` the confirmed on-call list reference/version. The Grant stores that same value, so two reminders under different policies do not match merely because their tags agree. Prose examples naming `operation: reminder-notify` or `operation: escalation-notify` abbreviate that typed value; they never omit its required binding in stored or wire data. In particular, `send` distinguishes `form-send`, `escalation-notify` and `reminder-notify`; `commitment.confirm` names booking acceptance (including the stored-accept offer path); publication and authorization operations retain their distinct §5 tool/operation identities. The executor derives this member from the validated call and its structural source: a reminder requires the registered booking/policy, an escalation its stored rung, and a form-send its catalog payload. Merely labelling unrelated prose `reminder-notify` is invalid. Canonicalized arguments include that discriminator, subject/party references and typed act values. An absent, unknown or inconsistent operation cannot match a Grant; it takes the existing schema refusal, never a wildcard operation. The type closes over the actually supported operations in §5; adding one requires the same tool-contract declaration, not a new risk class.

**Conditions reuse the engine's rule expressions.** `conditions` is the confirmed conjunction of supported attribute comparators/range membership from `../engine/SPEC.md` §§2–3, evaluated against engine-validated act attributes and current stored subjects, not LLM assertions. An empty conjunction means explicitly unconstrained within the confirmed operation and scope; a missing conditions member is not that choice. Store the confirmed typed operands, not a mutable rule reference whose later edit could widen permission. For “under an hour,” use the existing unit-bearing duration comparator `duration < 60 minutes` against the actual booked interval; exactly sixty minutes fails. Party restrictions bind the actual participant/recipient's scope chain and any supported admission/qualification predicate, never a matching display name. Unsupported predicates cannot be saved as executable permission: elicit a supported alternative or retain an inactive proposal. This adds no rule type or parallel condition interpreter.

**The covering relation, defined:** a grant **covers** an act iff it belongs to the authenticated principal's owner scope, its `action_class` and `operation` equal the actual act's, the grant's scope sits at or above the act's scope on the ladder within the same subject chain, every stored condition holds, and the grant is unexpired and unrevoked at fire time. The query's scope and condition inputs are derived from the canonical act and authoritative engine state; a caller cannot substitute another party, a shorter duration or a broader scope. This relation is exactly what the engine's pure lookup evaluates (`INTERFACES.md §1.3`'s `covering-grant` kind, FD-97 — stored grants only): the engine returns the covering grant's ref or `null`, and the decision to act on it stays this floor's.

**Auto-accept is a Grant, minted at setup time — there is no second authorization path.** When an owner says *"just take bookings from my regulars"* or *"accept any student booking under an hour,"* that is **not** a mode, a toggle, or a preference the agent consults. It is elicited during setup (§6's ask-once) and **stored as an ordinary Grant** — same shape, same ledger, same revocation, same `{who, basis, when}` attribution on every act it authorizes. *Why this matters more than it looks:* two authorization mechanisms means two places to look when someone asks "who allowed this?", and the answer to that question must never be "it depends which one fired." One shape, one ledger, one audit.

The coordinator mapping is §3.6's scoped Shared authorization: its operation/scope/condition binding uses this contract, and each actual act still meets this floor. A reminder Grant supplies no coordination, participant-edit or credential authority. The arrangement's internal report permission is token-access authority, never a fifth Grant risk class or an inferred standing basis for another operation.

- The Grant is minted **from the owner's ranked setup answers**, so its `scope` is exactly what they described and no wider.
- It is **revocable like any other Grant**, from the same surface, with the same immediate effect.
- It is **auditable before use**: an owner can read what they authorized as a list, at setup time, rather than discovering it from a booking that already happened.
- **Accepting a cross-owner share offer (`../engine/SPEC.md §7.1`) is exactly this case** — the counterparty's stored **accept mode** (auto-accept what fits the schedule, or auto-accept per person; founder-ruled, #2) is an ordinary Grant, and it is the stored basis that lets an offer commit without a live confirmation; **always-manual** is the third mode and simply means no such Grant exists. No new mechanism; the share seam reuses the floor unchanged.
- **The floor is not softened.** A Grant whose `action_class`, `operation`, `scope` or `conditions` do not actually match the act is no basis at all (rule 3 above) — auto-accept never widens by inference. The floor is universal: it re-applies with the *guest* as principal on the traditional form (the guest's own signature/payment is their across-the-line act, captured by the form); M1 governs the owner's agent when it acts on returned data.

**Outward content is narrated, not composed:** under a standing grant, the human-facing prose of an across-the-line send is derived from stored structure (`narrate(structure)`) plus the typed payload — never free model composition — so what a third party is told cannot drift from the record.

**Document-derived authorization:** a signed document whose terms *name* a consequence (a T&C-defined late fee) is itself a stored basis for **recording** that consequence — the signature evidence covers document-defined charges, like a grant scoped to the document. A consequence the document does not name has no basis → ask. **How "names" is decided is structural, never a model read** *(drafted 2026-08-21; **ruled FD-79, 2026-08-23** — carried here from the restatement. FD-79 dispositioned the `../security/SPEC.md` copy, which names itself *"the harness §7 amendment restated from this side"*; ratifying a restatement while its normative home stayed a proposal would invert FR13, so the ruling lands at the home too)*: the document's named consequences must exist as **stored structure** — rules with typed operands (`pricing`, the no-show policy) — at signature time, and the signature evidences agreement to that ruleset version (F4/F5's version-of-record law). The basis lookup is then a pure match against stored rules; the model never reads document text to determine whether a basis exists or what an amount is, because consent binds stored structure (`../security/SPEC.md §6`) and `../model/SPEC.md §5` forbids both readings; no participant upload is required (`../security/SPEC.md §4`). A document whose consequences were never structured names nothing — the honest answer is the ask.

**The cancellation asymmetry:** the owner cancelling a real person's booking is an across-the-line consequence (confirm; offer the rebook — §6 implicit recurrence); a counterparty cancelling their **own** booking is not owner-gated — the harness records it, releases the slots, and informs the owner. Their time to give up, not the owner's to approve.

## 8. Responsibility 5 — context assembly

What the harness loads into the model on every firing — the model sees only what this responsibility assembles. There is no accumulated conversation to lean on; **the board is the working memory.**

- **Guest-interactive frame:** §2's credential-derived mode selects only the authorized published/current request data. The existing context has the guest refinement in `INTERFACES.md §2.1`; no owner board inventory, private commitments, blocking reasons/places, contacts, other participants' standing or private reports can be selected. Include only authorized published labels/terms and rule explanations, permitted draft/ask fields, current request/booking revision and fenced engine bookability. The quarantine call sees the admitted submitted text, never the owner's slice; normalize and narrate receive only the fenced structures appropriate to their call. Bound and truncate within that same selectable set; a self-sufficient slice that cannot fit takes the existing park, never a wider lookup. Current draft correlation follows the existing form/console carrier, with server-validated guest scope in place of owner admission. No accumulated transcript is needed.

- **Standing frame:** who the owner is, which surface (`board` / `commitment-page` — the H1/H2 nicknames never travel on the wire), a board-inventory summary, and — on a **console** utterance — the **view-context** the app stamps: `{surface, visible_range?, selected_ref?, draft_ref?, draft_revision?, field_ref?, scope_ref?, ask_ref?}` (what the owner is looking at and has selected). This is what gives a **deictic** utterance ("push this back an hour") a deterministic referent; with no `selected_ref` an ambiguous "this" is a gap-4 ask, never a guess. The app supplies it (`../app/SPEC.md §1`, `../app/INTERFACES.md §1`) on the **existing** `normalize` context contract — a widening, not a new seam call — and its `surface` is the same surface the frame already names, stamped as one coherent object. Seam contract: `INTERFACES.md §2.1`. **The view-context reports what is displayed, never what exists** *(2026-09-12)*: an owner's display filter hides blocks on the board and narrows neither the board summary nor the relevant slice below, both of which are assembled from stored data by this responsibility — so a commitment the owner has hidden is still in the firing's context, still covered by its rules, and a firing never reads a filtered board as a free one.
- **Current draft (owner console; guest refinement above):** the matching view-context ref/revision selects `standing_frame.draft` from the existing form/owner-input payload (`INTERFACES.md §3.1`). The harness validates owner, correlation and current revision, distinguishes pending inputs from stored facts, preserves source tags and resolves correctness-critical values through the engine. The app echo supplies no target authority or acceptance. This is the current edit’s structured input, not accumulated conversation; travel values use the same carrier as other fields. Missing/stale draft state asks or parks instead of reconstructing it from displayed text. Trigger firings have no interactive draft; T2’s stored draft rules and pending asks remain ordinary relevant-slice reads. Carry the selected object/use, changed field, pending scope and particular ask from `INTERFACES.md §3.1`, with the submitted source span. Rebuild still-pending questions and settled proposal readback from §3.13's stored structure; preserve explicit blank and covering answers without offering stale acceptance. This adds neither a model-chosen trigger route nor a guest authority.
- **Catalog lookup result (owner console only)** *(2026-09-12, FD-105; seam shape at `INTERFACES.md §2.1`)*. When the turn's need is a shareable thing, the **app's marketplace adapter** (`../marketplace/SPEC.md §3`) performs the §6 lookup and hands its result in on the **existing** owner-turn context — an input to this assembly, not a second assembler and **not a new public verb** in either direction (`../marketplace/INTERFACES.md §2`). Assembly stays this responsibility's alone: the harness admits the supplied result, bounds it and orders it, and the model reads it like any other assembled structure. **What it carries:** per candidate, the **source item identity and its content version**, the eligibility the adapter resolved, and the candidate's own shape fields — so a selection resolves against **a supplied eligible candidate** and nothing else, and a candidate whose version or eligibility has moved is **rechecked before use** rather than acted on. **Three outcomes, never collapsed:** a result set, a **successful empty** lookup, and an **unavailable** lookup (service unreachable or refused). An absent member is not an empty result, and an empty result is not an unavailability. **Bounded by the existing budget and the existing discipline:** the candidate list occupies the same context budget as everything else here, truncates by the **deterministic** order the adapter supplied (identical on replay, L2), and **no ranking, scoring or recommender exists** to be inconsistent across firings (`../marketplace/SPEC.md §6`'s reserved-not-built popularity). A firing that cannot fit a self-sufficient slice still parks rather than dropping a covering rule for a candidate. **Every free-text field a catalog document carries is `document`-tagged and takes the quarantine read below before any privileged model call sees it** — listing copy is a stranger's prose, and it reaches `normalize` only as the structured `summarize` result. Trigger firings carry no catalog result; there is no guest refinement of this member.
- **Relevant slice:** the rules and stored answers at covering scope for the current target (via the ask-once store, §6) and the affected commitments' stored structure — not the whole store.
- **The slice is itself bounded (finite attention budget).** "Not the whole store" is not "however big the slice happens to be": the slice is **priority-ordered — nearest scope first** (the §6 ladder: `instance < kind-on-board < kind-global < board < customer < global`), affected commitments and their covering rules ahead of the rest. When a large target would overflow the budget (a busy governed board, a big SOP, an N-member order, six scope levels of covering rules), degradation is **deterministic**: lowest-priority items drop by that fixed order, identically on every replay (L2 preserved). A firing that cannot fit a **self-sufficient** slice within budget does not proceed on a truncated context — it **parks** (D4). Truncation never silently changes what the firing decides. **Self-sufficient is defined, not judged** *(2026-08-21)*: a slice is self-sufficient when it contains the affected commitments' stored structure plus **every rule and stored answer at a covering scope that could change what this firing decides** — the droppable set is non-covering material only. Drop a covering rule and the firing parks; drop background and it proceeds; there is no third case. The budget itself is configuration (`../model/INTERFACES.md §2.2`, `context_budget_tokens`) — a binding is qualified at a budget, and shrinking it is a re-qualification, never a silent config diff. **Drop order is not wire order:** priority governs what *survives* truncation; the serialized prompt puts the **stable material first** (standing frame, global rules) and the volatile slice after, so provider prompt caching gets a stable prefix — L2's byte-identical assembly is what makes the cache hit real.
- **Handoff frame (trigger firings):** the trigger event, the affected commitment structure, and what's pending. A trigger firing has no conversation; it must be self-sufficient from stored structure.
- **Provenance quarantine — two layers, each named for what it is.** Every assembled string carries a source tag — `owner | guest | import | document` — stamped at the door that admitted it. **The tag survives derivation:** a value assembled from tagged inputs inherits the least-trusted of them, so `owner` on the wire means every input behind it was the owner's. The law and its ordering are `../security/SPEC.md §5`; what this layer owes it is that assembly never hands the model a tag more trusting than the material behind it, and that §6's `owner`-only count reads inherited tags rather than door-stamps alone (`SCENARIOS.md` L8).
  - **Layer 1 — spotlighting / data-marking:** the tag travels with the text and the assembling model is *instructed* to treat non-owner and document text as data to read, never as instructions to obey. This is a labeling defense — it works by the model honoring the mark, **not** by making instruction structurally impossible — so it is the first wall, not the only one.
  - **Layer 2 — dual-model isolation, scoped by a property, not a list** (FD-2, founder-ruled 2026-08-07: *"assume everything is a prompt injection"*; scope restated as a property 2026-08-21): **non-owner free text that is admitted to context at all** — guest-returned text, connector-sourced text (a calendar entry's title or description is writable by anyone who can send the owner an invitation), text arriving through the external surface — plus admitted authored/named or catalog SOP text (owner-trust is not instruction-trust; `../security/SPEC.md §4` admits no owner/guest upload door) — is first read by a **quarantined model with no tool access** that returns only a structured summary/labels; the privileged, tool-bearing agent never sees the raw stranger text. **Vault-resident artifact classes are outside the property because they are outside context entirely**: artifact bytes never cross any harness/engine/app/model seam; the engine holds only permitted evidence, and there is no artifact `summarize` call to make (`../security/SPEC.md §4`, V1). Participant-file scenarios defer with the excluded feature; admitted sensitive answers and source-form text retain their custody and quarantine protections. The quarantine covers text that enters; the vault covers documents that never do. This does **not** depend on the agent obeying a label — the raw text structurally never reaches the model that can act. Spotlighting (layer 1) is kept underneath as defense-in-depth. **The call is `summarize` and its seam contract is `INTERFACES.md §2.4`** — tool-less by construction, closed structured return, never a `byo-*` binding.
  - **Layer 2 fails closed.** If no summary comes back — timeout, malformed return, or the fallback also failing, after the one bounded retry (`../model/SPEC.md §8`) — the raw text is **not admitted to the assembled context at all**. The firing surfaces a gap (attended) or **parks** (unattended, D4), exactly as an unfittable slice does above. The reading this forbids is the tempting one: admitting the raw text with a warning because the summary failed would make the security control degrade into no control at the moment it is most needed (`SCENARIOS.md` L7).
  - Law: `../security/SPEC.md §5`.
- **Principle:** context is **assembled from stored structure per firing, never accumulated conversation.** The same trigger fired twice assembles the same context. Reads come through the engine seam; the assembly policy itself is harness-owned (`INTERFACES.md §2.1`).

## 9. Cross-cutting principles (binding)

- **Poka-yoke by construction (M2):** illegal states are unrepresentable, not merely validated against — the silent untyped-on-governed commitment cannot exist; no-double-book is structural (engine).
- **Meta-principle:** design the harness's **general capability**; never make a decision catering to a specific use case. The use cases (teacher / dive / rental / ER) are **falsification probes**, not design targets. A probe that breaks the model reveals a missing *general primitive* — build the primitive, not the use case.
- **Authority levels:** `governing > org > individual`; governing content is admin-seeded and non-overridable; org/individual may extend. Governing standards are seeded at **highest fidelity, most-current** (a deliberate business posture; propagation is silent adoption — app concern).
- **Completion semantics:** events auto-complete by time (`completed` = in the past); `actual_end` is free and completion is `actual_end ?? (end passed)`; tasks complete by action.
- **Held-out validation:** use case E is deliberately **not** designed-to** — kept as an out-of-sample generality test (predictions in `SCENARIOS.md`), and it is the only one (`../user-stories/README.md`, FR10's home).
- **Commercial machinery is entered, never acquired** *(founder-ruled 2026-08-30, the ruling that re-homed `SCENARIOS.md` J5 from held-out to v1)*: an ordinary commitment that binds no kind carrying a `pricing` rule, belongs to no order and is shared with nobody — a personal preset (a meal/workout/cycle entry) is the worked case — creates no money mark, binds no `pricing` rule, mints no guest token and no Shared row, and gives rise to no outward act. Each absence composes law stated elsewhere (§3.4's single universal required field, `../engine/SPEC.md §3`'s binding table, §2's guest flow, §7's basis requirement); this bullet is where the composition binds as v1 behavior.

**Self-modification is a named refusal, not an absence** *(2026-08-28; the recorded-absence pattern §5's no-repair-loop and no-tool-zoo already use)*. annnä does **not** adopt the **self-modification capability class** of open-code-plane coding harnesses — the agent inspecting, editing, mounting or extending its own plugins and tool surface at runtime (DeepSeek Harness named as the external precedent, in the CaMeL/AgentDojo naming style). annnä's whole counterpart is the **noticed-pattern offer** (§6): owner-gated, data-plane, propose-only, and declinable permanently (§3.10) — plus FD-24's rule that the loop can never author its own basis. Recorded here so that a future contribution inspired by such a harness does not import the class as an obvious improvement; refusing it is the decision.

**The coeffect question, answered adopt-and-refuse** *(2026-08-28)*. A plugin-framework design poses the reactive-coeffects question — when the world a commitment depends on changes, what re-runs? annnä **adopts dependency declarations** through machinery it already has: `depends_on` drives `blocked` (§3.4), availability-class rules re-evaluate (§3.5), the seven trigger sources fire the loop on world change (§4), and the engine re-solves. And annnä **refuses automatic dependency-driven unwind for any consequence crossing the floor**: a changed condition **re-resolves internal state**, but an across-the-line consequence — cancelling a real person's booking because a prerequisite moved — becomes a **park or an ask**, never an automatic act (§7's cancellation asymmetry, unchanged). Recorded as the deliberate answer rather than left to be re-derived. **Neither paragraph is an FD**: both restate standing law and record a non-adoption; nothing new is permitted and nothing new is forbidden.
