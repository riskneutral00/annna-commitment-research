- **Two items from the concept-feasibility pass, 2026-08-08 (FD-16's pass — provenance in `../RULINGS.md`).** Both are this layer's, and neither blocks a build step.
  1. **The model's exam has no reliability metrics, only capability ones.** FD-16's curve is about *repeated* success, and `../model/EVALS.md` grades single attempts — nothing anywhere in the corpus names `pass^k` (success across k attempts), robustness to semantically equivalent rephrasings, or recovery from an injected tool failure, which are the three the field converged on. The engine makes them cheap to assert here in a way most products cannot manage: after a turn, stored state either matches the expected commitment or it does not, so an eval can be an **engine-state assertion** rather than a judgment about text. Destination is `../model/EVALS.md` (the exam's home); recorded here because `model/` carries no `NOTES.md` and this layer owns the model contract. **Constraint on any design:** FR5's BYO key means the exam is re-run per provider, so it has to be cheap.
  2. **Turn-level idempotency is unstated — and it is narrower than it first looked.** `SCENARIOS.md` **L2** already guarantees a re-fired trigger assembles an *identical* context from stored structure with no residue, and **L3** makes budget truncation deterministic across replays; that is the hard half of durable replay, holding by construction rather than by a framework. What no file says is whether re-firing a turn that **already committed some of its effects** re-applies them. The pieces exist — the engine commits atomically per call (`../engine/SPEC.md §6.1`) and hold creation is idempotent per guest-and-interval (`../security/SPEC.md §3`) — but the turn-level rule is nowhere. *(The research first claimed no replay mechanism at all; that was an over-claim, corrected against L2/L3 before the report was archived.)*
