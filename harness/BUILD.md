# annnä Harness — BUILD (ordered implementation plan)

*How a fresh agent session turns `SPEC.md` into a working, tested harness. Build against the stubs in `INTERFACES.md`; verify red-green against `SCENARIOS.md`. Do the steps in order — each depends on the one before. Nothing here requires a real Engine/Model/App.*

**Definition of done:** every `[MUST]` scenario passes against stubs; `[HELD-OUT]` probes are executed and their results recorded (not fixed); no harness code reaches across a seam except through the `INTERFACES.md` contracts.

## Step 0 — Project setup
- **Pin the tooling: TypeScript.** The typed tool contract (§5), the shared `EngineSeam` interface below, and the injected virtual-clock contract make an untyped language a poor fit — this is the harness build's language pin, not a preference.
- Set up a test runner and the **steppable virtual clock** (`INTERFACES.md §5`), **injected, not imported ambiently**, so hold/offer expiry and the escalation ladder advance on stepped time.
- Create the three stubs from `INTERFACES.md §5`: `EngineStub`, `ModelStub`, `AppStub`. Keep them deterministic and scenario-keyed. **`ModelStub` scripts four calls, not three** — `normalize`, `narrate`, judgment-inside-those, and **`summarize`** (`INTERFACES.md §2.4`) — plus a **failure fixture** for `summarize` that fails on every attempt including the fallback, so L7's fail-closed path is reachable rather than vacuous.
- **One injection point — `makeEngine()` / `makeModel()` / `makeApp()`** — so the stubs (now) and the real adapters (at the swap) slot in with **zero harness changes**. The engine seam is a shared `EngineSeam` TypeScript interface, implemented by `EngineStub` now and the real engine adapter later; the same point injects the virtual clock the stubs and the real engine share. This is what makes the stub-swap (`../engine/SCENARIOS.md Z2`) a drop-in rather than an edit.
- Wire an empty harness entry point: `handleTurn(input)` and `handleTrigger(event)`.
- **Verify:** the test runner runs; a trivial "echo" test passes; swapping a stub for a no-op adapter through the injection point needs no harness edit.

**CLOSED 2026-08-08.** TypeScript + vitest, matching `../engine/`. `src/seams.ts` holds `EngineSeam`/`ModelSeam`/`AppSeam` and the opaque `Handle`; `src/clock.ts` is the steppable virtual clock (nothing reads `Date.now()`); `src/stubs/` holds the three stubs; `src/make.ts` is the one injection point — `makeEngine`/`makeModel`/`makeApp` plus `wire()`, which also injects the clock **the stubs and the real engine share**, because a clock given to one and not the other would let them disagree about the time and every expiry scenario rests on them agreeing. `src/index.ts` exports `handleTurn`/`handleTrigger`, which **throw**: a Step-0 entry point that returns a plausible empty value is one a later step builds on while believing it works.

All three verify clauses are asserted in `tests/step0.test.ts`, not declared — including the drop-in: a bare object satisfying `EngineSeam` goes in through `wire()` while the other two seams still default, which is Z2's property tested rather than described.

**`ModelStub` scripts four calls**, and the failure fixture is real: `SUMMARIZE_ALWAYS_FAILS` throws on every attempt including the fallback, and an *unscripted* input fails closed too. A stub that returned a degraded summary on failure would admit raw stranger text with a warning attached — which `SCENARIOS.md` L7 says in its own words fails the scenario.

**This step is what took `../deployment/SCENARIOS.md` B9 live.** The suite writes `.tmp/transcripts/harness.txt` through a shared reporter (`../deployment/scripts/transcript-reporter.mjs`), the engine suite now writes its own, and the twice-run byte-compare has something to compare: *B9 OK — 2 suite(s) run twice, 2 transcript(s) byte-identical*. **B9's canary was fired against the real suite:** a test whose name carried `Math.random()` → `B9 FAIL — two runs, two different transcripts`.

## Step 1 — The object model (the atoms)
- Implement the SPEC §3 types as data structures: `Principal`, `Board`, `Commitment-kind`, `Commitment` (with the latched-status shape), `Rule`, `SOP`, `Shared`, `Order`.
- Implement the **derived** functions (pure, over stored structure): `temporal_type` (from roles), `completed` (`actual_end ?? end-passed`, or task-ticked), and `status = latch?.label ?? derive(unmet_conditions)`.
- Implement `needs_human` (the park) as a **stored field alongside `status`, not a status value** — set by the loop, cleared only by a human act, and always surfaced (SPEC §3.4).
- Correctness-critical values are typed handles from `EngineStub` — do **not** compute them here.
- **Verify:** C4, C5, C6, C7 (derivations); and unit tests that a set latch overrides derivation (precursor to C1–C3).

## Step 2 — The tool contract
- Define every tool from SPEC §5 with a typed signature and a declared **reversibility class** (`internal` | `outward:comms|value|destruction`). Make the class a **required, non-optional** part of the type — a tool with no declared class is **unconstructable** (M2 at the tool boundary), so "undeclared" cannot occur; the floor's fail-closed rule (D19, `SPEC.md §7` rule 5) is the runtime backstop if one ever slips.
- Route each tool to the correct seam: `calculate`→Engine, `CRUD_*`/rule-writes→Engine `commit` (as diffs), generative-UI/`publish`/`notify_and_await`→App.
- Enforce **diff-only** semantics for `CRUD_Board` and rule writes (never send a destructive replace).
- Validate every tool **return** against its declared return schema before the model consumes it (SPEC §5); a mismatch is a **structured error**, never a raw dump (A7).
- **Verify:** A1–A4's **tool-contract halves** (the dispatch, edit-not-duplicate, and conflict-surfacing behaviors driven directly through the tools — the utterance→plan path that completes them is Step 5's, the "H4's payload shape" precedent), A5 (tasks reserve nothing), **A7 (tool return validated against its declared schema)**, G7's tool-contract half (SOP lifecycle via `CRUD_SOP`), H4's payload shape (board-blind), H6 (per-recipient token attribution), N2 (no tool declares `value-transfer`), D9 (no tool declares `destruction`), and that each tool exposes a reversibility class.

## Step 3 — The clarify/permission floor (M1)
- Implement the floor as a gate **at the tool boundary**: before any tool call, if its reversibility class is across-the-line, require a live confirmation OR a matching `Grant{action_class, scope, expiry}`; else raise an elicitation gap (gap-2). Never infer a grant.
- Attribute every across-the-line call `{who, basis, when}`.
- Implement `Grant` as a stored, addressable, revocable object.
- Implement the floor's refinements: outward prose is `narrate(structure)` + typed payload (never free composition); a signed document's **named** terms are a stored basis for recording their consequences; paid/settled marks classify as internal.
- **Content-bind the live confirmation:** a confirmation's basis is the tool + its **canonicalized arguments**, so a changed argument is a new act needing a fresh basis (D18) — record that identity in `{who, basis, when}`. **Fail closed:** an undeclared/unclassifiable reversibility class is treated as across-the-line, never run unattended (D19).
- **The authorization class (FD-24):** implement grant creation/widening as its own gated class — a live, content-bound owner confirmation is the only basis; never a Grant, never unattended, never the external surface (`SPEC.md §7`). Put `grant.give` events into D20's generated input space so the property covers the mint path as well as the spend path.
- **The floor property:** raise the case-by-case D-family to one **property-based test** — no outward act ever fires without a matching basis, over any tool-call sequence (D20; the invariant's home is `SPEC.md §7`, `../TDD.md §Harness`). **Add `fast-check` here and write D20 first, before the rest of this step** — it is the harness's only non-scaffolding dependency, and writing the property before Steps 4–8 exist means every capability they add enters its generated input space automatically. Written last it would test a smaller space than the spec claims, silently.
- **Verify:** D1, D2, D3, D6 (and D5's "owner-side floor on returned data"), D7 (narrated-not-composed), D8 (document-derived basis, structural — the named consequences are stored rules), **D18 (confirmation is content-bound and re-verified at fire time), D19 (fail closed on an undeclared tool), D20 (the floor property), D24–D26 (the authorization class: live-confirm-only mint, no unattended or external mint, an injection cannot mint its basis)**, A6 (a hand-edit write transits `CRUD_Commitment` under the floor exactly as an utterance does), N1 (marks are internal, attributed). This step must be airtight before anything acts outward.

## Step 5 — The loop
- Implement `handleTurn` (console utterance → normalize → plan → tool calls under the floor → **check-work** → narrate) and `handleTrigger` (sale / hold-expiry / decline / returned-form / clock — `SPEC.md §4`).
- Implement **context assembly** (SPEC §8): standing frame + relevant slice per firing; the handoff frame for trigger firings — assembled from stored structure, never accumulated conversation. Stamp every assembled string with its `owner|guest|import|document` **source tag** (layer-1 spotlighting, L4) and **carry the tag through derivation** — a computed value takes the least-trusted of its inputs, so `owner` means every input was the owner's (L8; law and ordering at `../security/SPEC.md §5`). This is what makes Step 4's `owner`-only pattern count read what it claims to read; route the highest-risk untrusted channels (guest free text, uploaded SOP) through a **quarantined tool-less model** so the privileged model sees only the structured summary (layer-2 isolation, L5 — seeded from the injection-fixture corpus at `tests/fixtures/injection/`, `../security/SPEC.md §5`). **Create that corpus in this step**: it does not exist before Step 5, and its location, its committed-not-fetched form, and its provenance README are ruled at `../security/SPEC.md §5` (FD-8) — collect the strings from their named public benchmarks, never author them. The call is `summarize` (`INTERFACES.md §2.4`); **when it fails after its bounded retry and fallback, the raw text is not admitted at all** and the firing gaps (attended) or parks (unattended) — never admitted with a warning (L7). On a console firing, carry the app-stamped **view-context** `{surface, visible_range?, selected_ref?}` in the standing frame so a deictic utterance resolves against `selected_ref` (L6; `INTERFACES.md §2.1`). **An engine-written `PendingDecision` is found here, never fired on:** a clock firing assembles the `needs_human` park and the engine's enumerated choices (`../engine/SPEC.md §1.14`) in that same firing, and routes them through the existing elicitation path — no sixth trigger source (`SPEC.md §4`) and no sixth gap type (`SPEC.md §6`).
- Implement **check-work**: verify committed structure against the normalized intent (read-back turn-driven, engine re-read trigger-driven); mismatch re-enters the loop **exactly once**, then surfaces as a gap (attended) or parks (unattended); re-entry may re-commit but never re-fires an already-attributed outward act (SPEC §7). Termination = effect done **and verified** | gap to elicit | escalation.
- Implement **unattended behavior** against the objects at `SPEC.md §3.9`: the owner-scoped `OnCall` list and the stored `Escalation`. **Eliciting the list mints the FD-25 Grant** (`action_class: escalation-notify`, scope exactly the ranked list), and each rung notification is an ordinary outward act on that basis, riding `notify_and_await` — no exemption from the floor and no second authorization path. Walk the ladder on the virtual clock (`step_timeout` per rung, `total_timeout` overall); on exhaustion — including the empty-list and everyone-unreachable cases — **park** in a needs-human state, close the Escalation `timed_out_parked`, and surface it attributed to exhaustion. Never fire an ungranted across-the-line act. **Notification is not authorization:** reaching a rung creates no basis for the stuck act — the grant covers the notification and nothing else.
- Implement **auto-accept as a Grant** (`SPEC.md §7`): setup answers mint an ordinary Grant, matched by the same floor lookup as any other. **Do not build a second authorization path** — if the implementation grows one, that is the defect D10 tests for.
- Wire `AppStub.on_form_return` as a trigger source (the guest flow), and the hold/offer expiry as a trigger source (the clocked offer's cascade).
- ***Checkpoints (declared, not advisory — ruled 2026-08-08):*** Step 5 is the largest step in this plan and `../deployment/SPEC.md §4` names it by name as the case the checkpoint law exists for — *a declared subset of the step's gate IDs that can go green on its own*. **These eight are declared checkpoints under that law, not suggestions:** a subset's gate IDs go green together before the next subset opens, and a change that reds an already-green subset reopens it. *Why the promotion (and why only here): the subsets were already enumerated and disjoint, so the only thing "advisory" bought was permission to skip the ordering on the one step large enough for skipping to hide a hole. Step 4's I5 sub-gate stays advisory — it clusters nine sub-capabilities that do not have a forced order.* The subsets, each closable alone: **(1) loop + check-work** `K1–K4, D4, C9, A1–A4 (completed over Step 2's halves)` · **(2) context assembly + quarantine** `L1–L8` · **(3) escalation ladder** `D12–D17, D21` · **(4) auto-accept as Grant** `D10–D11` · **(5) share path** `I1–I4` · **(6) orders + cancellation semantics** `H1–H3, H5, H7, H8, C8, H4` · **(7) engine-originated round-trips** `P1, P2` · **(8) version-of-record** `F4, F5` · **(9) delivery stops** `D22–D23` · **(10) the noticed-pattern offer** `B6–B8` *(moved from Step 4 2026-08-21 — its count reads the slice this step builds)*. Every ID in the Verify set below sits in exactly one checkpoint. **An absence assertion from an earlier subset re-asserts at the close of the subset that builds the absent thing** *(2026-08-21)*: K3 and L7's no-Escalation assertions re-run when (3) closes — a vacuous green before the object exists is not a green. The step **closes** only when the full Verify set is green.

## Step 7 — The assisted off-app path

*Appended 2026-08-08, deliberately not inserted: Steps 0–6 keep their numbers because seven `BUILD.md` files cite them. **Build it after Step 5 and before Step 6's sign-off** — it composes Step 3's floor and Step 5's loop and clock, and Step 6 confirms the whole suite including this one.*

**Why it is a step at all.** `SPEC.md §2` specifies this capability in plain words — off-app edges the network can't reach are *"assisted, recorded, and converted"* — and until now **no BUILD step in any layer claimed it**. A specified capability with no build home is a capability that quietly does not get built, and this is the wedge the product actually launches into: the world where most counterparties are not on annnä yet (`../user-stories/Situations/Situation-C/README.md`, situation 5 — *"the minimal-adoption world the product actually launches into"*).

- Implement the **call preparation** as an ordinary read-back: assemble who to call, what to ask, and which stored fields the answer lands in, narrated from stored structure (Step 3's `narrate(structure)` rule, D7). It is an **owner-facing surface** — routed to the app like any other rendering, and it fires nothing outward.
- Implement the **recorded answer** as ordinary internal writes through the existing `CRUD_*` diff path under the floor, attributed to the owner's own act, classified `internal` (the same class as a money mark, N1). **No new tool, no new seam verb, no new trigger source.** The store must not be able to tell that a fact arrived this way rather than through a form return.
- Implement the **invite** as an ordinary across-the-line act: floor-gated (Step 3), attributed, and declinable — with the decline stored as a small owner-and-party record (declined/revocable, via `commit`, the `SPEC.md §3.10` precedent — O3 names the shape) so it is not re-offered on the next firing. Having spoken to someone is **not** a basis for messaging them; that is the whole content of O3.
- **Add nothing to the floor.** The floor property (D20) must cover this path unextended — extend D20's property-based test's input space to include assisted-call firings, do not add a rule to the floor. If the path needs its own floor case, stop: the floor was not a property, and that is a design finding, not a patch.
- Reuse Step 5's clocked offer and its expiry wholesale. An off-app party's silence is ordinary silence and lapses through C8's existing cascade — no waiting state of its own.
- **Verify:** **O1–O5** (the call is prepared and never placed; the answer returns as ordinary internal writes; the invite is floor-gated and a decline is remembered; no contact without a basis over the whole path, with D20 unextended; a silent off-app party lapses through C8 rather than blocking).

## Guardrails (from the project's standing rules)
- **TDD:** write the scenario test before the code that satisfies it. Every step above names its gating scenarios.
- **Thin agent, structural:** if you ever find the LLM authoring a correctness-critical literal, that's a bug — route it through `calculate`/`typed_value` as a handle.
- **Poka-yoke:** prefer making an illegal state *unconstructable* over validating against it after the fact (esp. M2 and the status latches).
- **Meta-principle:** if a probe or use case tempts a special-case, stop — build the general primitive it reveals, not the case. The use cases are falsification probes, not targets.
- **Scope:** build only the harness. If a task feels like board math, storage, rendering, or delivery, it belongs behind a seam (`INTERFACES.md`) — stub it, don't build it.
- **Tool ACI is prompt-engineering, not an afterthought:** a tool's **description** and its **decline/error returns** get the same first-class prompt-engineering and eval iteration as any system prompt. Returns carry **agent-legible context** — a structured decline says *which constraint refused and what the next move is* (the engine already distinguishes `no-feasible-placement` from `travel-unknown`, `../engine/SPEC.md §5`), never a bare error code or raw ID the model must decode. This is the prose face of the **return-leg validation** whose normative home is `SPEC.md §5` (every return validated against its declared schema before the model consumes it; A7) — legibility and validation are the same requirement seen from two sides. The tool surface is small on purpose (§5, no tool zoo); spend the saved effort making each tool's contract legible to the model.
