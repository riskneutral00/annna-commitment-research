## Guardrails (from the project's standing rules)
- **The loop core is built domain-blind** *(drafted 2026-08-28, not ratified — pending FD-83; the normative home for this rule)*. The **loop core** — the firing lifecycle, the budget/park machinery, the basis-spend machinery, and the context-assembly mechanics — is built so that **its modules never import commitment vocabulary**: no `Commitment`, `Board`, `Rule`, `Commitment-kind`, `Order`, `SOP`, `Shared`, money-mark or `PartyContact` type — `SPEC.md §3.1`–`§3.8` and `§3.12`, the commitment domain's own objects. The core works over **opaque subject references the domain pack resolves**, which is what lets it park, spend and assemble without knowing what it is parking. **The loop's own bookkeeping objects are not domain vocabulary and are the core's own** — `Escalation`/`OnCall` (`§3.9`), `PendingAsk` (`§3.13`) and the `FiringEvent` (`§3.14`) are what the loop is *about*; a rule that banned them would ban the loop. The commitment domain enters the built harness only through **the tool families and the policy tables the loop core consumes** — **including `SPEC.md §4a`'s dispatch tables**: the loop core walks a routed sequence, and the routing tables are what carry the domain. Verified external precedent, named in one clause: a coding harness whose agent loop imports no tool family (DeepSeek Harness, MIT, checked at source 2026-08-28). **This governs code module structure at build time and nothing else** — `SPEC.md §1`'s four-layer table is unchanged, and the harness spec still owns §3's object model, §6's elicitation policy and §7's floor exactly as written; what the rule bans is a loop module reaching for a domain type, not the harness knowing about commitments.
- **TDD:** write the scenario test before the code that satisfies it. Every step above names its gating scenarios.
- **Thin agent, structural:** if you ever find the LLM authoring a correctness-critical literal, that's a bug — route it through `calculate`/`typed_value` as a handle.
- **Poka-yoke:** prefer making an illegal state *unconstructable* over validating against it after the fact (esp. M2 and the status latches).
- **Meta-principle:** if a probe or use case tempts a special-case, stop — build the general primitive it reveals, not the case. The use cases are falsification probes, not targets.
- **Scope:** build only the harness. If a task feels like board math, storage, rendering, or delivery, it belongs behind a seam (`INTERFACES.md`) — stub it, don't build it.
- **Tool ACI is prompt-engineering, not an afterthought:** a tool's **description** and its **decline/error returns** get the same first-class prompt-engineering and eval iteration as any system prompt. Returns carry **agent-legible context** — a structured decline says *which constraint refused and what the next move is* (the engine already distinguishes `no-feasible-placement` from `travel-unknown`, `../engine/SPEC.md §5`), never a bare error code or a raw ID left to be decoded downstream. This is the prose face of the **return-leg validation** whose normative home is `SPEC.md §5` (every return validated against its declared schema **before the harness consumes it** — §4a; A7) — legibility and validation are the same requirement seen from two sides. The tool surface is small on purpose (§5, no tool zoo); spend the saved effort making each tool's contract legible to the model. **"Legible to the model" composes with §4a's pin, and does not contradict it** *(2026-08-31)*: the model is never shown the tool surface at runtime (`SPEC.md §4a` — no `tool_schemas`, no menu); the legibility is consumed by the **harness** (which routes on validated returns), by the **stored structure** the model later meets through `narrate`/read-back, and by the builder's **eval loop**. A description written for a runtime model menu that never exists is the misreading this clause retires.
