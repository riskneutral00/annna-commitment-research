# annnä Harness — INTERFACES (the seams to Engine / Model / App)

*The harness is built and tested in isolation. It sits on three layers that do not exist yet. This document defines the **contracts** the harness calls across those seams — enough to implement stubs so the harness can run and be tested (`SCENARIOS.md`) before Engine/Model/App are real. Each contract is a boundary the harness DEPENDS ON, not something the harness implements.*

*Rule of thumb: anything **correctness-critical** (does this fit? is this free? what's the gap? is this valid?) is an Engine call returning an **opaque handle** — the harness passes handles around, never re-derives or invents the value. This is what makes "thin agent / rich engine" structural.*

---

## 1. Engine seam

The Engine owns deterministic compute + storage. The harness never computes these; it calls and stores/forwards the result.

### 1.1 Compute — the `calculate` contract
```
calculate(query) -> Handle | ReadSnapshot | Envelope<"invalid" | "unavailable" | "timeout">
```

### 1.2 Write / commit

Field/rule diffs and declared stored reads retain the enclosing target, stable field/rule identity, expected revision, complete typed operand, value/default scope and reviewed dependency bindings from `SPEC.md §3.3`. The existing field-path/reference identifies the slot, never its label or array index. Commit rechecks current engine references and authority under engine §6; a stale Handle uses `invalid`/`expired-handle`, a malformed schema uses `invalid`/`schema-mismatch`, incompatible typed values use `invalid`/`type-mismatch`, and a governing-rule refusal retains its existing arm. Required-input or unresolved-reference failure is a schema validation refusal, with authorized concrete dependencies and valid resolutions in the existing detail/next payload; it is not a new Conflict class or free-form rule predicate. Current dependency decisions ride the existing PendingDecision/ask path. App-owned definition/use revisions remain on §3.1’s document context and authenticated adapter, never an engine document identity or new query/verb.

**Group/request writes (`SPEC.md §3.6`).** Ordinary principal-attribute and Commitment/Order/Shared diffs carry the stable group entry, request ref, expected revisions, selected/booked participant refs, arrangement/report refs and exact operation/accepted canonical act. Creation/retry uses the existing write id and applied-ref result; confirmation returns the same request as the applied booking. The `grant.give`/`grant.revoke` authorization path also persists Shared's scoped arrangement metadata under the console-only gate; it grants no new verb or credential class. A returned form carries its admitted token/recipient, request revision, allowed operation and report/proposed-act binding through the existing `on_form_return` payload; owner input carries the same domain fields through §3.1. Caller-supplied actor/scope fields cannot override admission. Expired/stale Handles, malformed or unresolved references and unauthorized operations use §7.1's existing refusals. The current state, not UI controls or a cached arrangement, decides admission and final apply. Engine §6 owns atomic participant/capacity changes; app-owned document references retain their separate guarded write/recovery.

**Bound-quote replacement writes (`SPEC.md §3.6`; the law is `../engine/SPEC.md §1.5`).** A booking whose roster, time, rate or total changes by explicit re-agreement rides the **existing** Commitment diff above — no new input arm, no pricing-specific parameter and no second write path. The diff carries the proposed roster, time, rate and total, the recorded agreement's ref and revision, and the **expected current quote revision** beside the existing expected object revision; the acting authority rides the call's authenticated context as every other write's does. A stale quote revision, an agreement covering a different roster, time, rate or total, or an authority revoked since it was recorded returns §7.1's existing stale or authority envelope, and the replay of an accepted id returns the original applied result under the idempotency law below. There is no seam member by which a reported attendance, `actual_end` or payment mark reaches a quote.

The replacement refusal map is closed and shared with the engine seam: malformed replacement members use `invalid/schema-mismatch`; incompatible typed values use `invalid/type-mismatch`; a stale handle-typed quote revision uses `invalid/expired-handle`; an agreement that does not cover the exact proposed act uses `refused/no-basis`; and revoked or suspended acting authority uses `refused/credential-invalid`. No `conflict/stale` or `conflict/unauthorized` reason is introduced. An unknown attendance outcome leaves the bound quote and its `priced` revision unchanged; only a human-marked `no-show` reaches the separately configured booking-bound no-show policy, whose rate-dependent arm reads the current bound quote source. A report, `actual_end` or payment mark never triggers either replacement or no-show pricing.

**Reported-outcome writes (`SPEC.md §3.6`; the law is `../engine/SPEC.md §1.9`).** A reported `actual_end`, a per-participant attendance outcome and a payment record ride the **existing** Commitment diff above — no new input arm, no report-specific parameter, no second write path. The diff carries the booking ref and its expected revision, the reported instant, the reporter, the basis and, for a payment, the payer and the channel the reporter named; the acting authority rides the call's authenticated context as every other write's does. A correction or withdrawal is another such diff naming the record it supersedes, so **there is no seam member by which a caller unsets a mark, clears an outcome or rewrites a reporter**. Refusals use the existing map: a malformed report is `invalid/schema-mismatch`, an incompatible typed value `invalid/type-mismatch`, a stale expected revision `invalid/expired-handle`, a payer or participant the booking does not carry `refused/no-basis`, and an actor without the recording authority — a guest credential reaching for another party's attendance or payment among them — `refused/credential-invalid`. An expanding `actual_end` correction returns the existing widening `conflict` unchanged. No reason and no verb is added for any of it.

**PartyContact writes** retain `SPEC.md §3.12`’s party/slot Handle, expected object revision, exact contact-versus-association-versus-membership operation and reviewed reference resolutions in the existing stored-object diff. New party/contact creation applies together; same-input recovery returns the original applied pair, while stale/reference and payload-mismatch refusals retain §7.1’s envelope. Independent contact writes carry their own result and never commit the surrounding definition/use/group draft.

Routine uses the existing Pattern/Commitment diff path (`../engine/SPEC.md §1.4`), with the Pattern ref, occurrence id/generation, original local date/time and zone, interval/anchor and accepted scope retained through stored reads and write targeting. The relevant-slice read and existing context `stored_answers[]`/`commitments[]` carry these authorized inputs for `SPEC.md §6`'s ask-once behavior; the UI/model cannot author identity or bypass version checks. Stop-from-date carries the checked scope and each required authorized resolution, not a bulk cancellation disguised as a Pattern edit. No new success arm, temporal type or permission follows. Travel edits keep engine §5’s request identity, estimate Handle, draft revision and accepted usual/datetime scope through this diff path. Saved-place entry creation/edit/retirement is a principal-attribute diff under `../app/SPEC.md §8`, independently accepted and idempotent, never a new stored-object class. Current reference revisions and every reviewed future resolution are rechecked atomically; no partial retarget on failure.

```
commit(input: commitment | diff | proposal_ref, write_id) -> {ok, applied_ref, committed_revision} | Envelope
```
- **The write id is `commit`'s second parameter** — the caller-supplied id the idempotency law below names, in a printed seam position at last. The two identity components `../engine/SPEC.md §6` item 6 keys its indexes by — `(owner_org, credential)` for the apply record, `(owner_org, issuing principal)` for the turn-state read — ride the call's authenticated context, never the payload.
- **The success arm is the neutral applied-result `{ok, applied_ref, committed_revision}`**: `applied_ref` names what the write applied — a commitment ref for commitment writes, the applied diff's object ref for Board/Rule diffs, the proposal's ref for a `proposal_ref` apply, and the bookkeeping object's ref for a stored-object write (`SPEC.md §§3.9–3.14`). Nothing untrue rides a field named for one input form. Failures are the §1 envelope (`conflict` carries `alternatives` as `next`). `committed_revision` is the engine-minted opaque applied revision under `../engine/SPEC.md §5`, returned unchanged on same-write-id replay. The harness correlates this result with the submitted write id and draft revision; neither the model nor the app supplies it.
- **A stored-object write uses the existing `diff` arm over the object's declared shape**: the target shape and its permitted fields come from that shape's owning home (`SPEC.md §§3.9–3.14`; `../engine/SPEC.md §§1.13–1.17`). There is no object-specific entry point and no second actor/field matrix. The seam rejects a caller-authored engine-only member, engine-minted reference, `ShareGrant`, or identity, tenant, scope, or other trusted-context field; both identity components ride authenticated context, never the diff payload. An authenticated human answer is the permitted exception for the `PendingDecision` choice described at `../engine/SPEC.md §1.14`; the engine/LLM may not select it.
- Enforces **no-double-book by construction** and **atomic commit-time checks**; two commits racing for the same capacity → at most one succeeds.
- **Firing ownership travels through the existing stored-object contract** (`SPEC.md §4a`; storage `../engine/SPEC.md §1.17`): claim, invalidation, recovery and owner-visible loss use `commit` diffs and declared stored reads, not worker-authored authority. The engine checks current ownership atomically with new work/loop writes; the harness adapter enforces it at actual outward dispatch, including takeover after an earlier check. A replayed apply result never restores ownership. Pre-birth recovery couples release with its attributed loss once; post-birth recovery retains the interrupted continuation without automatic execution. Already-authorized correlated receipts still persist by `SPEC.md §3.14`'s own ids after ownership loss; neither receipt writes nor late record writes authorize new work or dispatch. Shape and mechanics are BUILD design work under these homes, with no new verb or failure vocabulary.
- Reminder activation and derived registry writes use the host commit transaction under `../engine/SPEC.md` §§1.15/6, with no new verb or proposal-ref form.
- Re-entry after a check-work mismatch may re-commit; it never re-fires an already-attributed outward act (`SPEC.md §7` — the normative home).
- Enforces the **latch invariant**: once `expired_at` is set it cannot be cleared by later precondition satisfaction (no un-expire).
- `CRUD_Board` / rule writes arrive as **diffs**; the engine applies them non-destructively (never wipes seeded governing rules).
- **A rule diff still carries no candidate declaration** *(2026-09-12; the law's home is `../engine/SPEC.md §6` item 1, restated nowhere here — FR13)*: every commit carrying a rule diff is a candidate apply and re-runs the affected-commitment check inside its own transaction, and this input shape gains **no** member for it — the engine forms §1.3's `CandidateDeclaration` from that diff's own rule refs, expected revisions (`new` for a rule the diff creates) and the proposed rules' declared scope. No blocker, exemption, grandfathering flag, resolution or `effective_scope` crosses here, so the widening noticed at §7.2 is `check_consistency`'s alone and `commit`'s parameters are untouched.
- **`proposal_ref`** — the third accepted input applies a whole `resolve` Proposal (§1.5) atomically: every move lands or **nothing does**. The harness never unpacks the proposal to commit moves one by one; it passes the reference back. Required by `SCENARIOS.md` P1 step 6, and specified engine-side at `../engine/SPEC.md §6`.
- `alternatives?` is an optional field on a conflict — the engine may offer other placements. The harness may narrate them from the handle but never authors one.
- **Every write carries a caller-supplied write id, and `commit` is idempotent per id** *(2026-08-21)*: re-committing the same id returns the **original result** rather than applying twice — the `../security/SPEC.md §3` hold-idempotency precedent, generalized. This is what makes a lost response recoverable: check-work's one retry re-commits the same id and cannot duplicate a create (K4). The same id is the external surface's continuation handle (`SPEC.md §5.3`, X3–X4) — one mechanism, supplied by the caller *before* the first byte of response, so an interruption that eats the response never orphans the turn. **That allocation point is per entry point, and the recovery obligation is the caller's** *(2026-09-12; the law's home is `../engine/SPEC.md §6` item 6)*: every entry point on this side that can reach a write — a console request, a form save, a guest submission, a resumed candidate apply — allocates **its own** id before its first response byte, so an interrupted one is decidable rather than orphaned. A caller holding an **unknown** outcome recovers it by that existing id before offering a retry or a discard: a discard presented over an unresolved id is refused engine-side, and this seam gives the harness no way to report the unknown as nothing-happened. `unavailable`/`timeout` are **not** definitive refusals — the original id stays the only legal continuation, and minting a second one is how one act becomes two records.

### 1.3 Consistency & coverage
```
check_consistency(rule | ruleset, candidate?: CandidateDeclaration)
  -> { conflicts:[…], latent:[…], compatibility: Compatibility | null }   // optional second argument + third member, both added 2026-09-12 (notice §7.2)
check_coverage(query: {kind:'board-structural', board} | {kind:'covering-grant', act:{tool, canonicalized_args, action_class, operation, scope_ref}, principal_ref})
  -> {kind:'board-structural', missing_required:[…]} | {kind:'covering-grant', covering: grant_ref | null}   // per-kind bound below (FD-97)
```
- `conflicts` distinguishes **governing** conflicts (hard stop), **own-rule** conflicts (override-with-reason), and **unsatisfiable** pairs (`../engine/SPEC.md §8` item 4 — hard stop *regardless of authority*, because no override could make them satisfiable). **Unsatisfiable added no member**: it is a class inside `conflicts`, not a new field *(re-scoped 2026-09-12 — this sentence read "the return shape is unchanged" and was overtaken by the `compatibility` member below; it was only ever a claim about the unsatisfiable class)*. **The harness must not offer the override path on an unsatisfiable conflict** — doing so would let an owner store an unsailable boat that still looks bookable.
- **`check_consistency` additionally returns the affected-commitment compatibility result, as the printed third member `compatibility`** *(2026-09-12; the shape and its law are `../engine/SPEC.md §8`, restated nowhere here — FR13)*: it rides **this same return** beside `conflicts`/`latent`, as its own named member — not a fifth conflict class, not a new verb and not an extra call before a write. It answers what a candidate rule revision does to records that already exist, which the conflict classification cannot reach because it reads stored rules only. The member is `Compatibility | null`, and **which one is decided by the call's optional second argument**, printed above: a `Compatibility` when the harness passes a `CandidateDeclaration` — the proposed rules' `rule_ref`s with their expected `revision`s, under one `effective_scope`, the proposed rule *content* still riding the first argument (a rule the submission **creates** is declared `revision: new` at its proposed ref; a create is never declared by omitting the member, and a narrowing made by **adding** a rule is gated exactly as an edit is) — and `null` when it passes none, which is the legacy noncandidate call every consumer written before this entry was already making. **A present but incomplete declaration is not a noncandidate call**: a missing or empty `rules`, a member without its `rule_ref` or expected `revision`, a missing `effective_scope`, an unrecognized member, or a declaration disagreeing with the first argument about which rules are proposed refuses the whole call as `invalid` with `schema-mismatch` (§7.1) — the harness surfaces that refusal and never narrates it as *not asked* or as clear. And **`null` is not clear** — clear is an empty `blockers[]`. A candidate that changes several rules at once (S13c's combined capacity, price and format submission) travels as **one** call — one `ruleset` first argument and one declaration whose `rules` carries all three changed refs and revisions under one `effective_scope` — returning **one** `Compatibility` whose echoed `candidate.rules` carries every changed rule, and every blocker names one of them; that binding is the engine's, asserted here only as the thing the harness may not re-author. **What the harness passes in is the declaration and nothing else, and it authors nothing out of the result**: no blocker list, no exemption, no grandfathering flag, no additional resolution, and — as with `unsatisfiable` above — **no override path is offered on a compatibility blocker**. An empty blocker set is true only as of the `store_version` the engine stamped on it; carrying an earlier one into an apply is refused at `../engine/SPEC.md §6`, not tolerated here. The **retained** blocked candidate is not read back over §1.1 and is not engine-stored: it stays on the app account-document adapter's operation record (`../marketplace/SPEC.md §3`), and resuming re-calls this verb over what that record retains. **The typed seam is behind this contract, and the step that closes it is named:** `harness/src/seams.ts`'s `check_consistency` takes one argument and types its return as `conflicts`/`latent` only — the optional `candidate` parameter, the `compatibility` member, its `null` arm, the incomplete-declaration refusal and the stub's blocker fixtures are `BUILD.md`'s blocked-candidate carrier obligation at Steps 1/2, with the engine-side computation at `../engine/BUILD.md` Steps 3/5, exactly as the `CoverageQuery` scaffold sentence below distinguishes an owed checker change from implemented behaviour.

## 2. Model seam (the LLM)

The harness wraps the model; these are the calls the harness makes INTO the model. (In the harness build these can be a scripted/mock model that returns fixed structured outputs per scenario.)

**There are exactly four call types** — `normalize` (§2.1), `narrate` (§2.2), judgment (§2.3), and `summarize` (§2.4) — one of which, judgment, **rides inside `normalize`/`narrate` rather than being separately bound** (`../model/INTERFACES.md §2.2`; it is listed so a future split stays representable). **The seam is pinned at four from here forward**, under the same discipline the engine and app seams carry: a fifth call is a harness change, and the swap law is zero harness changes once the harness is built. (The model seam was never interview-locked the way `../engine/INTERFACES.md §1` and `../app/INTERFACES.md §1` are, but it has the same swap property, so it takes the same pin.)

**The seam is per-call selectable.** Nothing may assume a single model: `normalize`, `narrate`, and judgment may each bind to a different model/tier, chosen per call (build-with-frontier, run-with-cheap is an ops decision the seam must keep open — do not narrow it to a one-model assumption in Engine/App phases). `summarize` is per-call selectable in the same way with **one confinement**: never a `byo-*` provider (§2.4).

**Accounting crosses with execution, not model prose.** `SPEC.md §4a` owns routed-step count and effect allowance; `../model/INTERFACES.md §2.2` owns provider-attempt correlation, charge aggregation and enforcement. The adapter reports accounting for failed as well as successful attempts to the firing's bookkeeping and, when applicable, the originating credential's daily accounting (`../security/SPEC.md §10`). The four model return shapes remain unchanged: a missing or malformed return is not an absent charge, and a valid return is not an effect basis. `SPEC.md §3.4`'s typed budget cause identifies the exhausted measure; provider failures retain `../model/INTERFACES.md §2.1`'s closed error union and `../model/SPEC.md §8`'s bounded ladder.

## 3. App seam

The App renders surfaces and moves data in/out. The harness produces typed payloads and consumes typed events; it does not render or deliver.

### 3.1 Surfaces (render targets — harness emits, app renders)

- **The tool contract has a stated compatibility policy (RQ-13).** A published policy states what constitutes a breaking change to a verb, what notice a credential holder gets, and how long a superseded shape remains callable; a change that breaks a caller cannot land without satisfying it; and it is forward-only in the corpus's sense — a change never alters what an existing call already meant. It is spec-class markdown at **§7** below *(authored 2026-08-22 as `harness/COMPAT.md`, whose INDEX row and count bump landed with it that day and were **folded** away with it 2026-08-29)*, on the `../deployment/egress-allowlist.md` precedent: the permission lands first, alone, where it is the only thing to read — and it enumerates the closed reason set per refusal kind (§1's envelope), which is what makes its own widening rule checkable.

- **What constitutes a breaking change:** removing or renaming a tool; changing a parameter's or return field's type or meaning; making an optional parameter required; **and widening any closed enum or return shape** — a new status value, a new refusal reason (§7.1), a new `labels[]` member — because clients branch on closed enums (`SPEC.md §5`'s declines are designed to be branched on). Additive optional fields with declared defaults are non-breaking, on `../engine/SPEC.md §1.10`'s additive-only precedent.
- **Read-result notice:** the declared `ReadSnapshot` arm and its named stored-shape/projection discriminants are part of the calculate return contract. A new snapshot shape, projection, or field that changes a closed member is a breaking change and must be noticed here before it lands; snapshot/display data remains output-only and cannot widen a correctness-critical write position.
- **Forward-only:** a change never alters what an existing call already meant (`../PRD.md` RQ-13's own words). A superseded shape is superseded, never reinterpreted.
- **Notice:** a breaking change lands in this section **before** the change lands anywhere else — the spec-first half of `../deployment/SPEC.md §1`'s boundary law is the notice mechanism. While the only credential class admitted is the owner's own agents (`../PRD.md §1.2`, refusal two), that entry is the whole notice.
- **Supersession window:** a superseded shape remains callable until every issued credential has been exercised against the successor — with no third-party holders this window may be zero. **Before any credential is issued beyond the owner's own agents, this policy must first state a numbered notice period and window** — issuing without them is X7's refusal. (A readiness condition, not a schedule — FR2.)
