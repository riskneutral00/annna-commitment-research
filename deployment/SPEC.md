# annnä Deployment — SPEC (the discipline of the build)

*"Deployment" here is the whole discipline that gets code from a builder's keyboard to production: repos, environments, what may land on main, concurrency. **This file governs the build in this repo** — ruled in place 2026-08-07, and §1 is now written to that ruling (one repo, no vendored snapshot). The repo keeps its **direct-to-main flow** (founder rulings 2026-08-06/07), and the re-scope pass that discharges it has run: fourteen scenarios and the machinery they described — split bot identities, PR scope law, worktree law, the waves ledger, the swap lockfile, CODEOWNERS floor approvals — are **deleted, not deferred**, because they specified a team of bots that does not exist. Two properties survive by name and are what remain worth mechanizing: **author ≠ approver** (§4) and **no spec edit to make a red test green** (§1). Everything below binds the build from its first code commit. Tech-neutral throughout: "the host", "the CI service", "the model provider" — substrates are named at the seams (`INTERFACES.md §3`) and ordered in `BUILD.md`. Hardened by adversarial review round one, 2026-08-06 (`NOTES.md` holds the record).*

---

## §0. What deployment is

- **Scope: the build phase** — from the first code commit to the marketplace's Z1 integration gate. Post-launch operations (monitoring, on-call, incidents) are a later package, not this one.
- **The process is specced falsifiably, like everything else.** Every `[MUST]` below is enforced by a named mechanism — a required CI check, a script — never by prose alone. A rule no mechanism can refuse is not a rule here (`SCENARIOS.md` is the proof obligation). What only a runtime or a human can enforce is tagged honestly as a `[DRILL]`, not dressed as a `[MUST]`.
- The bookend: `marketplace/` builds last of all; **deployment builds first of all** — its own `BUILD.md` completes before `../harness/BUILD.md` Step 0 begins (one deliberate exception: the Z1/Z2 ladder drills run at app Step 0, the first moment production has content — §4). **The order above is law and has already been departed from once:** the engine's Step-0 scaffold landed before any deployment step did. That is a recorded deviation (DR-5, §8), not a changed order — a reader who finds engine code and no CI configuration is looking at work that ran ahead of its gates.

## §1. One repo, and the spec/code boundary

**One repo, ruled in place** (the header line above records the ruling; `README.md` records the separate-repo posture it reverses): the build happens **here**, in the repo that already holds the specs. There is no second code repo, no vendored snapshot, no import manifest — specs and code are siblings in one tree, and one history carries both.

What the two-repo split was buying is one property, and only one: **a builder cannot quietly edit a spec to make a red test green.** A copy that CI refused to let anyone write was one way to buy it. In a single repo it is bought by a boundary *inside* the tree:

- **Spec files are floor paths** (§7) — read by the human before they land, which with one operator is the whole of what CODEOWNERS used to buy (§4).
- **Spec and code never move in the same commit** — a path-class check refuses a commit whose changed paths span a layer's spec files and that layer's code (S2). The spec change lands first; the code then builds to a spec someone already read.
- **The gate reads the commit under test, and nothing else.** No workflow, submodule, remote, or code path pulls spec content from outside the checked-out commit (S3) — so the text a reviewer read and the text the checker enforced are provably the same text.
- **Stub-lies batch.** During a swap pass, do not land a spec change per lie: complete the pass, collect every stub-lie it surfaces, land the set as **one** spec commit, then replay from the top of the swap. The authority law holds; the per-lie serialization does not.

**Authority law: a red test is never fixed by editing the spec beside it.** When a swap turns red because a stub lied (`../TDD/integration.md §When a swap turns red`), the fix is a design decision — made on the floor, in its own commit, then built to. DR-3 (patching the spec in the same change the spec is blocking) stays *no* (§8).

## §2. Vocabulary

The harness owns **agent · loop · trigger · parallel · unattended** for the product's runtime (`../harness/SPEC.md`), and owns bare **session** (T2 interview sessions). Deployment never uses those words **unqualified** in the development sense; its own terms are always compound. Normative:

| Term | Meaning | Never confused with |
|---|---|---|
| **builder** | A development-time AI session authoring code (inherited — `../harness/SPEC.md` read-order line, "a fresh builder") | The product's runtime agent |
| **builder session** | One builder's run of work on one layer (always the compound form — never bare "session") | A harness/interview session (T2) |
| **wave** | A set of **concurrent** builder sessions the dependency order permits | Harness "parallel" (a runtime word) |
| **rung** | One environment on the promotion ladder (§3) | — |
| **lane** | A CI job class (suite lane, qualification lane) | The marketplace money lane |

Deployment says **"concurrent"**, never "parallel".

## §3. The rungs (environments)

**Three rungs: local · per-change preview · production.** No standing staging rung (DR-1). **The ladder grows with the repo:** the production rung *activates at app Step 0* — the first moment a deployable surface exists. Before that, main's terminal rung is **CI-green**; harness and engine are not web deploys and pretending otherwise would make "the deploy is the exam" an exam with no answers.

- **Data law: production data never descends.** Lower rungs seed from **suite fixtures only**, through **one named seed entrypoint** whose module imports nothing but the fixtures bundle — statically checked (R4). **The name is `seed.<ext>`, and the check is on the name rather than the location:** exactly one file in the tree may be called that, wherever it lives, and its module may import only from a `fixtures` path. A location rule would have to guess which layer owns seeding before the layer exists; a name rule does not, and "exactly one" is the property R4 actually states. Zero exist today — the check asserts *at most* one and says the import half is unexercised until the first one lands. Poka-yoke on credentials: a lower rung's env store holds **no production-tagged secret** — asserted by enumerating each rung's env store and diffing against the manifest (R1), plus a token-scope assertion: the preview-creation credential cannot read the production deployment.
- **Secret law — composed with `../security/SPEC.md §7`.** Deployment owns *where each rung stores*; security §7 owns *what code may load and how*. Hosted rungs: the host's env store, injected as environment. Local rung: exactly the one untracked secrets file security §7 prescribes. Every secret on every rung is enumerated in the **env manifest** (name · rung · owner · rotation note) — including the security-package vault keys; an unmanifested secret fails CI (R5; the production half of that check runs only inside the protected deploy environment, the one place a production-scoped read credential is sanctioned). Each rung's secrets are rotated once as a drill (R10).
- **The mock law, promoted to environment law.** Below production, the paid and closed world is mocked — enforced statically, not hoped:
  - **Closed marketplace service** — no closed-service credential and no real base URL exists anywhere below production: a static check over code and config, so there is no path to reach it (R2).
  - **Model provider** — the model key lives in exactly one place: a **protected qualification environment**, manually fired. A required lint over the CI workflows fails if that secret or environment is referenced by any other lane (R3) — key absence is proven statically, not by a job grepping its own env. The qualification key carries a **provider-side hard spend cap**, and the lane fires only from a **human-held trigger** (a protected environment whose required reviewer is the human identity) (R8).
  - **Mail** — sandboxed below production. **Clock and travel** — scripted, per `../engine/BUILD.md` Step 0.
- **Exposure law.** Production, once active, refuses anonymous access — deployment protection, attempted and observed (R7); "dark" is a mechanism, not a habit of not sharing the URL. Non-production rungs are non-indexable and carry no reachable debug or auth-bypass flag — config/grep-checked, the security X1 pattern (R9).
- **Builder credential floor.** No deploy or production secret is present in any CI job that executes agent-authored code (R6). A builder session holds a repo-scoped write token and nothing else (§5) — a prompt-injected builder must have nothing worth exfiltrating. *Branch-limited went with the branch law: under direct-to-main a token that cannot write main cannot land anything.*

## §4. Landing law

- **Trunk-based, direct to main.** No git-flow, no release branches, and — per the ruling — no mandatory PR: nothing here has releases yet, and a long-lived branch breaks the stub-swap discipline, which assumes main is always the integrated truth. What must be true of main is enforced at the commit.
- **Author ≠ approver, restated for who actually exists.** The **author** is the agent session; the **approver** is the human. A change an agent authored and no human read cannot be the final state of main, and what the human casts is a **structured verdict** — named findings, or an explicit *attempted to falsify; nothing found*; a bare "looks fine" is not one. This is a `[DRILL]` (B4), not a `[MUST]`, and the honesty matters: with one human and no bot identities there is no second identity for a check to compare against.
- **Where the verdict is recorded: `git notes --ref=verdict`, on the commit it judges.** B4 has said "recorded per landed change" since it was written and never said *where*; the only home ever specified (`NOTES.md` E7 — a required check reading the latest non-author review body) died with PRs under FD-4 and FD-6. **Not a tracked file, and the reason is a regress:** recording a verdict for commit N in the tree *is* commit N+1, which needs its own verdict, forever. A note attaches to a commit that already landed, is written by a different actor at a different time, and never changes the SHA. **A verdict covers its own commit and every commit back to the previous verdict** — which is how a reviewer signing off on a run actually works, and the only reading under which a batch sign-off is representable at all. Per-commit is still available: cast one on each and each covers only itself. `scripts/b4-verdict-check.mjs` reports the covered range and lists what is beyond it. **It reports and never refuses** — a gate that blocked committing until the previous commit was reviewed would deadlock the first commit and every solo session after it. What this buys is that *whether* a verdict was cast is now checkable; *who* cast it still is not, and no mechanism here can change that.
- **Why the CODEOWNERS floor is gone rather than reworded.** The deleted S1 scenario enforced "a human must approve this" through CODEOWNERS against *bot identities*. With one human operator and no bot identities, human-cast is **true by construction** — the illegal state is unconstructable rather than checked, which is this corpus's preferred shape (M2). A check that could only ever pass is worse than no check: it reads as protection. The property is not abandoned; it is no longer purchasable by a mechanism, and §7 says so where the floor is defined.
- **Checkpoints.** A **checkpoint** is a declared subset of a BUILD step's gate IDs that can go green on its own; the step *closes* when its full gate set is green. Whole-surface steps (app Step 1, harness Step 5) land in checkpoints rather than in one thousand-line change. This survived the re-scope while the PR scope law around it did not: the reviewable-unit property is real and the layers depend on it (`../harness/BUILD.md` Step 4's I5 sub-gate and Step 5's checkpoint block both cite this definition); what died with it was the claim that a checkpoint is a *PR*.
- **Landing gates** (`SCENARIOS.md` B-family) — mechanical except where marked:
  - The declared gate IDs green, and the layer suite green on stubs — **detected, not refused** (B1, a `[MUST]` since FD-7). Direct-to-main lands the commit before anything runs, and FD-4 deleted the ruleset that could have refused it, so nothing here makes red *unable* to be main; what the aggregator (`npm run check`) buys is that red cannot be main *unnoticed*. It carries **no path filters**, because a skipped required check reads as success on the substrate (B1's footgun clause). `.github/workflows/check.yml` declares the job and it fires for real since FD-10 reversed the push refusal — but it fires **after** a landing, which is a report, not a refusal. **The mechanism that can refuse is `.githooks/pre-commit`** (FD-7): it execs the aggregator before every commit, which is the pre-landing form B1 named in advance as sufficient to return it to `[MUST]`. CI is the second reader, catching what a bypassed or unconfigured hook let through. **`--no-verify` defeats it, and that is the accepted ceiling** — recorded here rather than closed, because with direct-to-main and no push there is nothing stronger to buy. A ceiling that is written down is a known bound; an unwritten one is a false floor. The hook is per-checkout (`git config core.hooksPath .githooks`), so a fresh clone has no gate until that line is run — `../AGENTS.md` says so where an agent will meet it.
  - Spec and code never move in one commit (S2, §1).
  - **Gate-coverage: every `[MUST]`/`[ENGINE]` scenario names a BUILD step, and every BUILD-named gate ID is a real scenario.** A required check runs `scripts/gate-coverage.mjs` over each layer's `SCENARIOS.md × BUILD.md`; an orphan (scenario with no BUILD home) or a phantom (gated ID no scenario defines) fails it (B8). This mechanizes the standing rule that a `[MUST]` enforced only by prose is not a rule — the checker is the machine that refuses a stale gate list, run in CI against the spec files of the commit under test (S3).
  - **Determinism: the suite replays byte-identical.** The full layer suite runs **twice** and its transcripts are byte-compared; divergence fails the build — the harness's L2 determinism (`../harness/SCENARIOS.md L2`) lifted to a process gate (B9). **A transcript is a file a layer's suite writes to `.tmp/transcripts/<layer>.txt`** — untracked, rebuilt per run, and the only thing the byte-compare reads. Declaring the path is what lets the runner exist before any suite writes one: it runs the suite twice, compares whatever landed there, and **fails on divergence, on a vanished file, and on a suite that wrote none while claiming to** — but reports an explicit *nothing to compare* line while no layer produces one, the same shape as the reactive-push skip. The comparison is exercised at harness-build time, when transcripts first exist.
- **Land → deploy: continuous; dark once live.** From app Step 0 onward, landing on main deploys production, behind R7's access gate, until a launch ruling (DR-2). A deploy pipeline exercised from the first deployable commit cannot rot — "the swap is the exam" generalizes to **the deploy is the exam** (Z1, run at app Step 0).

## §5. Builder sessions

- **One builder session works one layer at a time.** Steps within a layer are sequential by construction, so a second session in a layer is a **handoff at a step boundary, never concurrent work** — and never a file-level split.
- **Credential floor:** per §3 — a builder session holds a repo-scoped write token; deploy and production secrets are structurally out of its reach (R6).

## §6. Concurrency and the wave plan

The dependency order is **the per-layer BUILD preambles, not the root README's linear prose**: the engine builds after the harness ("its seams are the requirements", `../engine/BUILD.md`); **the app states no harness dependency before its swap step** — it builds against its own spies (`../app/BUILD.md`, `../app/INTERFACES.md §4`); model Steps 1–5 want the **built** harness only ("not an invitation to start early", `../model/BUILD.md`); the marketplace is gated on all four (`../marketplace/BUILD.md`). The swaps serialize per `../TDD/integration.md §The swap sequence`.

| Wave | Concurrent builder sessions | Barrier to the next wave |
|---|---|---|
| **0** | Harness · **app Steps 0–7** (against its spies — no harness dependency until the swap) · model Step 0 (scaffold *code* in CI; its live Verify — "runs the N-set against any one OpenRouter model" — fires in the qualification lane, never ordinary CI) | Harness suite green on stubs — gates the **engine and model tracks only** |
| **1** | Engine · model Steps 1–5 (**built harness only**) · app continues | Each layer's own suite green |
| **2** | The swaps, **serialized on main**: engine swap → app swap (app Step 8) → model qualification | Each swap green before the next opens |
| **3** | Marketplace | Its preconditions green: app Z2 · harness B1/B2 + the D family · engine rule menu + Shared projection (`../marketplace/BUILD.md` preamble) |

- **The swap order is `engine → app → model`, serialized on main.** A stated build-order fact, not a ledger entry: the barriers above are read from the layers' own BUILD preambles, which is where they are already normative. Nothing arbitrates them but the human running the build.
- **The diff gate is the one mechanism the swap order keeps.** `git diff harness/` non-empty in a swap commit fails the check (Q3) — a job, not a reviewer's eyeball. It survives a re-scope that deleted the rest of this section's machinery because it is the **only mechanical guard on the zero-harness-changes swap law**, the property the whole four-layer bet rests on.
- **A swap commit declares itself: the `Swap: <layer>` trailer.** The gate above had no mechanism for two days for a plain reason — nothing said what *makes* a commit a swap, and a check cannot fire on a category no file defines. It is a **git trailer on the commit message** (`Swap: engine`), which git already parses, no reviewer has to remember, and no heuristic has to guess. **The declaration is the swapper's, and that is the honest bound:** an unlabelled swap is not caught, exactly as an `--no-verify` commit is not caught (FD-7's ceiling, §4). What the trailer buys is that a swap which *says* it is one cannot also edit the harness — and since the swap sequence (`../TDD/integration.md`) is a deliberate serialized act, not an accident, the person writing it is the person who knows. Enforced by `.githooks/commit-msg`, because the message does not exist yet at pre-commit time.
- **Stub-lie adjudication is the human's.** A green-on-stub/red-on-real dispute is a design decision that leaves the code lane entirely: it lands as a spec change on the floor, batched per swap pass (§1).

## §7. The process floor

M1 — the reversibility line (`../harness/SPEC.md §7`) — mapped onto the process. **The mechanism is gone and the floor is not:** CODEOWNERS bought "human-cast" by making bot approvals insufficient, and with no bot identities every approval is already the human's — the state the check refused is unconstructable (§4). What remains is a **named list of paths a human reads before they land**, and the honesty that this is discipline, not a ruleset.

**On the floor:** every layer's spec files (`SPEC.md` · `SCENARIOS.md` · `BUILD.md`) · deploy configuration · the env manifest · **the CI workflow definitions** (`.github/workflows/**` — a workflow edit can weaken every other gate) · **the egress allowlist** (outbound network calls in product code are confined to an allowlisted module set, lint-asserted; adding egress is a floor act — the path a prompt-injected builder would need). **It lives at `egress-allowlist.md`, and it is markdown deliberately:** that makes it spec-class, so S2 refuses to let a widened allowlist ride in the same commit as the code that widens it. The permission has to land first, alone, where it is the only thing to read · deleting or weakening any layer's suite · production secret changes · history rewrites — **force-push: never**.

Everything else is reversible-by-revert and needs no ceremony (Z2 proves the revert path).

## §8. Open rulings (DR series)

- **DR-1 — standing staging rung.** Absent by decision (§3). Re-open if launch or a multi-operator phase demands soak time.
- **DR-2 — production exposure.** When dark production opens, and to whom. A launch question, not a build-phase question.
- **DR-3 — spec-change fast path.** May a build-blocking spec defect be patched inside the change it is blocking, instead of in its own commit on the floor? **No**, on record — and the pressure that motivated a fast path is relieved by §1's batching: one spec commit per swap pass, not per lie.
- **DR-4 — cross-host builder-session registry. Moot 2026-08-08 (FD-4).** It deferred branch-uniqueness across build hosts; the worktree/branch identity law it deferred is deleted, so there is nothing to register. Kept in the series rather than renumbered — DR numbers are cited elsewhere.
- **DR-5 — the engine scaffold ran ahead of the gates.** §0 states deployment builds first of all; the engine's Step-0 scaffold exists while deployment Steps 0–3 do not, so it was built under none of the mechanisms this file specifies (no required checks, no path-class check, no floor discipline). **Open:** whether the scaffold waits for Steps 0–3 to close before the engine takes another step, or is retro-covered when the gates land. Recorded rather than absorbed: nothing mechanical catches step ordering — `gate-coverage.mjs` checks scenario↔BUILD pairing, not sequence — so an unrecorded deviation is invisible. The mirror of this note belongs at `../engine/BUILD.md`'s preamble, which states the engine builds after the harness.
- **DR-6 — the CI floor landed before this package's own BUILD steps.** A root `package.json` (`npm run check`) and `.github/workflows/check.yml` now exist and run: gate-coverage, the engine suite, the reactive-push probe *where a deployment exists*, a binary-size guard, and a doc-count assertion. That is deliberately **smaller than §4 describes** — no path-class check, no canary red test, no twice-run byte-compare — and it was built out of order, before deployment Steps 0–3. Recorded rather than absorbed, in DR-5's register and for DR-5's reason: nothing mechanical catches step ordering. **Two live consequences.** (1) The §4 declarations this floor does not yet satisfy remain declarations — reading them as implemented is the error this entry exists to prevent. (2) The reactive-push probe needs a live Convex deployment and CI has none, so it reports an explicit *skipped* line there instead of passing quietly; `../AGENTS.md` states the same thing where an agent will meet it. **Closes** when deployment Steps 0–3 either absorb this floor or supersede it. *(§4's re-scope has since landed — FD-4 — and the required check it names is this floor's `check` job.)*

  **Partly absorbed 2026-08-08, and still open.** The floor grew the gates it was missing: `s2-path-class.mjs`, `s3-no-outside-spec.mjs`, `r3-workflow-lint.mjs`, `r9-noindex-nodebug.mjs` and `x1-secret-grep.mjs`, plus `.githooks/pre-commit` firing the aggregator before every commit, `gate-coverage.mjs --selfcheck` running ahead of the real walk, and `b9-twice-run.mjs` — wired, canaried twice, and exercised the day harness Step 0 gave it transcripts to compare. **Step 0 closed on that** (`BUILD.md` Step 0) and the canary red test has been fired three times and recorded, which is what consequence (1) above was waiting for on B1. **What is still declaration, not implementation:** B4's structured verdict is the human's and cannot be self-cast; security X2–X5 have nothing to assert against yet. **This entry stays open** until Step 2 lands — the rung ladder is untouched.
- **DR-8 — harness Step 0 begins with deployment Step 2 open.** `§0` and `BUILD.md`'s preamble say deployment Steps 0–3 complete first. Steps 0, 1 and 3 are closed; **Step 2 is not, and cannot be**, because five of its gates work by enumerating a live env store or configuring a hosted environment, and no rung exists below CI-green until app Step 0 gives one something to serve. Waiting would stall every piece of work that does not touch a rung, on accounts that no code can create. **What remains a declaration, not an implementation:** R1, R5, R11 (no store to diff the manifest against), R8 (a protected environment with a human reviewer and a provider spend cap), R9's noindex half (no rung config), R6's env-dump canary (CI fires since FD-10, but no rung issues a deploy secret for a job to dump), R4's import half (no seed door). Recorded in DR-5's register and for DR-5's reason: nothing mechanical catches step ordering — `gate-coverage.mjs` checks scenario↔BUILD pairing, not sequence — so an unrecorded deviation is invisible. **Closes** when the first hosted rung stands up and those gates are built against it, or when a later ruling re-scopes them. *The mitigation is that the manifest they diff against was written first (`env-manifest.md`), so what is missing is the store, not the specification of what the store may hold.*
- **DR-7 — the model spike was built outside the wave order, deliberately.** `../model/spike/` runs the eight N-set seeds against one OpenRouter model and prints one number. The wave order puts model qualification last, after the built harness; this deviates from it on purpose, because the risk it prices is asymmetric — if no affordable model clears the bar, three layers are being built to a contract nothing satisfies, and that is worth knowing before they are finished rather than after. Recorded in DR-5's register, not absorbed: the order is law and this is a departure from it, not a change to it. **The runner exists and has not been run** — it needs a provider key and spends money on each execution, so it fails closed without one (`../model/spike/README.md`). **Closes** when the number exists and is recorded, or when the eval scaffold (`../model/BUILD.md` Step 0) subsumes the spike and it is deleted. The spike's number is never a qualification record (`../model/EVALS.md §3`).
