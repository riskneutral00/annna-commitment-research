## T — Tokens *(SPEC §3; B-derived)*
- **T1 [no oracle]** Probing token routes with bad, revoked, and never-issued tokens: responses are indistinguishable and constant-time on miss; no route confirms whether a token, owner, or booking exists. Repeat without a credential and with expired flow/single-visitor credentials on page, bookability, return and replay routes under SPEC §3; no supplied request id turns failure into an existence oracle.
- **T2 [expired reuse]** A lapsed hold link or revoked recipient link presents the honest dead end (app G5) — no availability, no stale view, no data. *(Composes with the engine's no-un-expire: engine B1.)* Under SPEC §3, revoke one request link while a form is open and again while confirmation is pending: its next read/apply/replay fails generically. Sibling links and the booking remain unchanged. Reissue only with fresh owner-authorized scope, assert a different digest and the old digest permanently dead; stale arrangement/report/acceptance cannot resume through the replacement. Contact correction, contact removal and Shared content edit do not revoke, transfer or widen the binding. Unpublish an invitation and assert admission stops while an independently valid booking-bound read retains its lifecycle. Cancel a separate booking with valid own-cancel authority and assert the same scoped link reads its retained confirmation/cancellation; move/re-confirm refuses. These are independent fixtures, not promises that expired credentials can read history.
- **T3 [digests only]** Inspecting the store (and logs) after issuing tokens finds SHA-256 digests only — the plaintext appears nowhere at rest. For request and confirmation-time manage issuance, inspect the persisted recipient, bound request, read/operation scope, revision and any arrangement binding. Delay/fail persistence and lose its acknowledgement: no usable unpersisted credential is exposed, and recovery yields the existing persisted outcome, not duplicate issuance or booking. Repeat with a shared reader to ensure manage issuance cannot upgrade its rights.
- **T4 [transport hygiene]** Every token page response carries `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; no token appears in a query string after load.
- **T5 [attribution can't cross]** Recipient X's token can never read or return as recipient Y — the H6 guarantee, exercised as an attack. *(B: two renters, one bike listing.)* **And the forwarded-link face** *(added 2026-08-22)*: a booking made on recipient X's link by **whoever holds it** attributes to X — forwarding a named link hands over your standing, never a way in of your own. Asserted as the same guarantee from the other side; the story consequence is Situation-D's Nathan beat (the front-door link, not Priya's own, is the shareable one). **Request/operation matrix (SPEC §3; Matt S10/S11/S13d/S14b, MT-13/62/79/83, CRUD-18, XR-04):** use two independent requests for the same party, a different party with a similar name, and four links to one group request. An authorized individual fills only permitted use fields, checks bookability and confirms the exact request; its original link and confirmation manage link resolve the same booking. Retry after lost success, with the original and another write id/link, yields no second booking or quota draw. Try the other request id, forged recipient, owner-rule/definition/contact edit, another participant's attendance/payment mark and a wrong-target diff labelled as a permitted move: every attempt refuses with no domain mutation or private read. A reader can read the confirmed scope and ask bookability but direct proposal/report-agreement/report-objection/confirm/participant-change/move/cancel calls all refuse. A coordinator performs only explicitly authorized arrangement operations with current report/terms/confirmation; stale, expired, revoked, suspended or superseded arrangement/report controls refuse. Forward a valid individual and a reader link: the holder has exactly the recorded recipient's existing rights, never a verified-human claim or a change of actor from text. No hidden board reason, contact directory, other standing/calendar or credential internals appears on any read/context wire. Edit the contact channel and repeat: authority and quota identity stay unchanged. Later account creation alone adds no read/write power; verified conversion remains N6, not this fixture.
- **T6 [limits bite]** Hammering a token route trips the per-IP and per-token limits; the guest sees the plain "try again shortly" page, never an error dump.
- **T7 [the entry link is not a capability — the token is]** *(SPEC §3, fourth token class; re-cut FD-45, 2026-08-22 — the mint moved from pull-time to open-time so the Situation-B browse-then-pull probe holds.)* A **public entry link** (Situation B's counter QR) answers nothing on its own: probing the bare URL yields no availability, no board, no offering detail — the response is a rate-limited **single-visitor token mint** carrying only FD-53's **unfurl-safe static preview** in its metadata, **and assert the preview's ceiling**: name and photo render, and no availability, price, or offering datum appears in it *(re-cut 2026-08-22 — the row's "and nothing else" predated FD-53's ruled preview and contradicted the home)* — and it is the **minted token's** page that renders the published offering surface (the live fleet with photos and prices — `../app/SCENARIOS.md` G8's content half). Assert the mint limit bites: hammering the entry URL from one IP trips the per-mint rate limit (§10) — the scraping bound lives at the mint, not in a hidden catalog. With the configured per-IP seed L in an injected window W, the last allowed mint succeeds; the next mint refuses without creating a pass; advancing the injected window admits a valid mint, and a different declared key has an independent counter. These controls establish neither device nor human identity. Two visitors scanning the same QR get **different** tokens; each token's hold cap is counted independently, so it limits that token key, not a person, shop, or whole fleet. The IP mint counter is also a shared-network limit: unrelated visitors can share it, and neither an IP nor a token establishes a human identity. A photographed QR posted publicly mints rate-limited singles, never a shared credential. Revoking the entry link stops future mints and leaves already-minted tokens to expire on their own clock. **And FD-53's age-out and atomic cleanup bite:** with an injected clock, an otherwise-valid unused pass is accepted immediately before `issued_at + 24 hours` and refused at the boundary and after it, even if cleanup is delayed. The stored `unused` predicate is explicit; repeated cleanup physically removes only expired unused pass records, while a first session activity, hold creation or booking atomically withdraws that predicate and preserves the required access. Race cleanup against those activities and booking, including a duplicate submission: each outcome is atomic, no orphan or duplicate booking is created, and replay returns the original outcome. Active holds, needed continuations, completed bookings/history and booking-bound manage access retain their own lifecycles; no access at 30 hours is promised. After an unused pass expires, revisiting the still-published entry URL mints a fresh authorized single-visitor token under the existing limits. Expired, revoked and unknown tokens all fail through the same generic response, as G5 asserts. Keep this unused-pass matrix separate from the per-recipient/manage lifecycle controls in T2/T3/T5: passing its injected clock or cleanup controls grants no expiry or deletion authority over those records.
- **T8 [held credential never leaks, never authorizes]** *(SPEC §3.1.)* An owner's calendar **refresh token** appears in no seam payload, no log, no error report, and no engine object — asserted as absence on the wire and at rest. Assert further that **no code path treats a live connection as a basis** for an across-the-line act, and that provider rejection surfaces as a visible disconnected state with **no background retry** anywhere in the tree. **Run the same assertions against a bound BYO provider API key** (§3.1 member 2, `../model/SPEC.md §7`): it is vault-resident, absent from the routing config's stored form, and absent from every seam payload and log. **And against an ICS secret-feed URL** (§3.1 member 3, FD-37): the URL is vault-resident, appears in no log or seam payload, and its rotation-at-the-provider surfaces as the visible disconnected state exactly as member 1's revocation does. Three members, one test — a class with an untested member is a class in name only, and the key is the member a builder is most likely to leave in a config table as a plain string.
- **T9 [the fifth class, minted not held]** *(SPEC §3, fifth token class — FD-17, admitted to §2's models by FD-18.)* Run **T1, T3, T4, T6 unchanged against an `external-client` credential**: no oracle on a bad or revoked one, digests only at rest, transport hygiene on every route it reaches, limits that bite. Then the two assertions unique to it, because it is the only class attributing to a principal on the *inside*: **(a) attribution is never permission** — a credential whose owner never authorized an act cannot perform it, so possession alone reaches nothing the owner has not granted (`../PRD.md` RQ-7), and the act records *both* the attributed principal and the client that made the call; **(b) withdrawal is the same act as issuance, reversed** — a withdrawn credential stops authorizing at the next call, with no grace window and no cached capability, asserted against a mutation it could reach a moment earlier. **This is the suite `SPEC.md §3` requires green before any such credential is issued**; before FD-18 that sentence named a test the T-family did not contain, which is the defect class FD-13 fixed by writing G9. **And the runaway case** *(2026-08-22; current accounting home: `SPEC.md §10`)*: a client's successful and failed provider attempts, including attempts in parked firings, accumulate provider charges against the daily per-credential cap under `SPEC.md §10`. Use the scripted charged-attempt matrix at `../model/EVALS.md §3` to isolate that cap from unrelated rate/firing stops and assert credential suspension when it is exhausted; a routed-step park with no provider invocation contributes no provider charge.

## N — Tenant isolation *(SPEC §9; C-derived — two shops, one store)*
- **N1 [unconstructable reference]** A write attempting to reference another tenant's board, commitment, or rule is rejected at construction — not filtered at read.
- **N2 [rules don't leak]** Shop A's kind-targeted rule never evaluates on shop B's placements — same kind name, different `owner_org`.
- **N3 [the legal crossing]** The **engine share seam** (`../engine/SPEC.md §7.1`) moves exactly the goal and the counterparty's *exposed availability*, by explicit floor-crossed granting acts, recorded on both boards — and nothing else crosses without a stored higher rung. Terminal states (decline, expiry, conflict) are recorded on both boards with the commitment placed on neither. *(Rewritten 2026-08-06: this scenario previously named Situation C's **referral** as the legal crossing. - **N4 [one crossing class, no second door]** A grant is engine-minted or it does not exist: assert **no caller-reachable entry point** constructs a two-tenant edge, walked against the whole contract. Asserted structurally, not sampled — this is what keeps N1's "unconstructable" literal while grants exist.
- **N5 [a share adds no read power]** Every counterparty value observable to the initiator during a share offer is derivable from the `availability` grant (the published Shared projection); no commitment, rule, party, name, or money mark of the counterparty appears on the wire absent an explicitly granted higher rung — and every read above the floor is asserted to have a stored rung behind it. *(P1's board-blindness, re-asserted across the tenant line; engine I3's security half.)*
- **N6 [conversion adds no read power]** *(FD-46; §2's verified-channel claim.)* A guest with token-attributed bookings across **two** tenants converts to an owner account: after the claim verifies their contact channel, the new principal's board reads exactly the **union of what their booking-bound tokens could read** — their own bookings, attestations, and participation history — and **nothing else of either tenant** (no other party's records, no board complement — asserted on the wire, the G1 leak-test pattern). An unverified or ambiguous claim links **nothing** — asserted as absence of the link and of any read. The records themselves keep their owning tenants: no write moved them, and both source boards are byte-identical before and after the conversion. **And the FD-51 bounds, each asserted as a refusal:** a booking whose token the owner **revoked** is absent from the converted history (the latch survived); an **expired** token's read does not return; and on a **shared channel** that delivered two parties' tokens to one inbox, every presentation of either or both tokens links **nothing** — neither party's bookings are included, asserted as absence, not as a filtered view. **And the claim door's named limit bites** *(added 2026-08-22 with the §10 registration)*: channel-verification attempts beyond the seed rate refuse with the honest try-again — the claim flow offers no contact-probing oracle. **And the FD-76 dormancy bound bites** *(added 2026-08-23)*: a token whose last linked commitment ended more than twelve months before the claim is **absent from the automatic union** — asserted as absence — and surfaces only through the board owner's confirm ask; the owner's yes links it, a no leaves it unlinked, and neither outcome touches the live-slice union or any other party's records. **And the shared-channel counterexample, asserted as the whole outcome** *(added 2026-09-11 with §2's clarification of what a shared channel does not supply)*: both parties' per-recipient tokens are readable in **one verified inbox**; present the first token, then the second, then both in the same run — every attempt **links nothing**, returns no read, and leaves **both source boards byte-identical**, asserted as absence of the link and of any read rather than as a filtered view. Repeat the run with a self-selected name, a similar name and a forwarded token: none narrows the channel to a person, and none widens identity or history access. **The positive fixture names its own evidence:** the one successful conversion here runs on a verified channel whose delivery record maps to **exactly one** party, and what it assembles is still exactly that party's authorized token reads with the revocation latch, the expiry refusal and the FD-76 dormancy absence each re-asserted in that same run. **The ambiguous-success case has no fixture, deliberately:** no authorized evidence contract for distinguishing two people behind one channel is identified, so this suite carries no passing example of it and does not treat its absence as a gate it can close.

## S — Consent & signatures *(SPEC §6; B waiver, C medical)*
- **S1 [no consent, no submit]** Submission without the required consent action is refused client- **and** server-side (the server refusal holds when the client is bypassed). Under SPEC §12, separately refuse optional purpose P while accepting required terms: unrelated service continues without P processing. Refuse required terms: the governed act cannot proceed and no acceptance is recorded. Missing timely notice or required choice refuses affected collection on a direct request as well as the UI.
- **S2 [evidence complete or refused]** A consent record missing any of `{timestamp, IP, user-agent, document-version-hash}` is refused at capture.
- **S3 [version replay]** The audit surface answers: who consented to *which document version*, when, from where — for a version that has since been superseded. Change required terms and an independent purpose separately: old receipts keep their exact meaning, and any required new action precedes changed processing. Withdraw P: further P-dependent processing stops, unrelated allowed service remains, and the readback records withdrawal without fictitious erasure. Replay identifying fields after eligible erasure yields the truthful tombstone, not reconstructed evidence.
- **S4 [guardian consent]** A minor's flow (junior diver) captures guardian consent as the consent record; absent it, the same S1 refusal. Use the legally reviewed entity/market/minor matrix (SPEC §12); missing or unsupported applicable treatment blocks affected collection, and guardian consent alone does not establish legal validity. Test owner-entered guest data under the reviewed indirect-notice/basis rule; never substitute owner acceptance for the guest's required action.

The owner and recipient caps are independent: satisfying one does not bypass the other, and saved contacts confer no send authority. *(Added 2026-08-21 — the cap previously had a number, no reader, no consequence and no test: the FD-12 defect class reproduced. ## D — DR & lawful exits *(SPEC §8)*
- **D1 [restore drill]** Backup → clean deployment → the layer suites run green against the restored store — **and §8's two bounds are measured on the drill: the restored store's newest write is within the stated loss bound of the simulated failure point, and the drill completes inside the stated recovery bound.** A drill that goes green without a clock tests half of what it exists for. Seed erased subject A and unerased control subject B; restore a snapshot predating A's completed erasure inside the backup horizon. Before any affected data is served, reconcile current erasure/key state independently of that snapshot: A stays unreadable/unservable, B restores and required nonpersonal history survives. Missing current state or unestablished key destruction fails closed until reconciled, including a stale snapshot claiming A was not erased. Re-backup the restored store: the original residual expiry never restarts. SPEC §8 owns this fence; Step 7 selects and exercises its recovery mechanism.
- **D2 [takeout is whole and only]** An owner's takeout contains their board whole — commitments, rules, history, money records, attestations — and nothing of any other tenant.
- **D3 [takeout ≠ bundle]** Takeout output fails marketplace install validation — it is a person's data, not an installable artifact. *(The §8 carve's teeth.)*
- **D4 [return-or-delete]** A verified owner initiates account termination through SPEC §12's existing ops request path; verify requester/tenant/subject/basis and resolve the affected field/copy/key inventory and dependencies. Produce the scoped takeout, then eligible erasure on the stated schedule, with V4's five-obligation attestation and truthful tombstone/completion readback. Pair a relayed guest request with its verified subject scope and preserve another subject's values. A forged request, caller-asserted ops identity, ambiguous subject or wrong tenant produces no export, destruction or disclosure. Retry with the **same request identity**, including a lost result: recover the correlated outcome, create no duplicate takeout/erasure effects and expose **no foreign tenant**. Pending backup/provider residuals remain visible; account closure and display/Grant withdrawal cannot claim immediate universal erasure. Gate: Step 8, using Step 7's existing ops authority; no harness destruction tool.
- **D5 [owner-scoped restore]** A two-tenant store loses part of tenant A's board. **Detect:** the live board falls short of the last backup watermark and the console raises a restore card naming what is missing and the copy's timestamp. **Confirm:** until the owner confirms, **the store is byte-identical** — no write of any kind. **Replay:** on confirm, A's lost objects return as **appended writes attributed to the confirming owner**; tenant B's objects are byte-identical before and after; **no latch is un-set**, and no delete occurs anywhere in the run. Asserted negatively too: **no harness tool can initiate this** — the tool registry contains no restore verb. *(§8's restore law; the tenant half is N1's rule applied to a restore.)* In that tenant-scoped replay, include erased subject A1 and unerased A2 from an older snapshot. Owner confirmation cannot resurrect A1: reconcile current erasure/key state before replayed personal data can serve, while A2 and permitted nonpersonal history recover. Unavailable current erasure state fails closed; a backup's old state is insufficient. Fresh backup generations preserve the original residual expiry, never restart it. These are SPEC §8's same fences as D1, not a second restore mechanism.
