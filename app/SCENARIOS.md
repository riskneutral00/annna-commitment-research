# annnä App — SCENARIOS (deterministic acceptance suite)

*Pass/fail, deterministic, replayable. These test **structure and behavior** — payloads, mappings, wire contents, state transitions. Visual/design law lives in `DESIGN.md` and gates `BUILD.md` steps as a checklist, not as scenarios. Run against a stubbed harness (scripted seam calls) and, for the G-family, real HTTP against the guest routes. Sources: `../harness/INTERFACES.md §3`, the user-stories corpus, `.specs/deep-interview-app.md` acceptance list. Every scenario is MUST. Each row also carries a release tag — `[r1]`/`[r2]` — whose vocabulary, gate, and reading of Z2 at the release bar live at `../PRD.md §6.5` (FD-50).*

## C — Canvas & surfaces
- **C1 [board home] [r1]** `render(board, payload)` produces the board state; a fresh sign-in lands there. Blocks show only display projections from the payload's handles — no app-computed values anywhere in the rendered output.
- **C2 [riser = commitment-page, whole] [r1]** `render(commitment-page, payload)` opens that commitment's riser containing **the same form it was created with** pre-filled from stored structure, **and** the commitment's support content — its rules, SOP attachment, stakeholder assembly, availability-sharing — reachable within the same riser. A bare form with the support content elsewhere fails this scenario.
- **C3 [console omnipresent] [r1]** In every canvas state — board, any riser open, settings — the console is present and accepts an utterance. *(Supersession 2 pinned: the prior build's hide-during-edit rule must NOT reappear.)*
- **C4 [riser round-trip] [r1]** Open a riser, make no change, close it: the board returns identical — no state change, no writes emitted.
- **C5 [surface reported] [r1]** An utterance sent with the board risen carries the **view-context** `{surface: board, visible_range, selected_ref?}`; the same utterance with a commitment riser open carries `surface: commitment-page` + that commitment's ref as `selected_ref` (values per `../harness/INTERFACES.md` render/act signatures + `§2.1`). Selecting a board block stamps its ref as `selected_ref`; with nothing selected, `selected_ref` is absent. The app stamps mechanically; no interpretation — resolving a deictic "this" against the stamp is the harness's job (`../harness/SCENARIOS.md L6`).
- **C6 [frontier follows navigation] [r1]** Navigating the date row past the materialized frontier: the app requests extension **through the seam** and, until the store holds the new instances, renders the gap empty — it never invents projected copies to fill it. When the store extends, the instances appear.
- **C7 [self-improvement is opted into, and the card shows both readings] [r1]** With the owner's self-improvement setting absent, `render` produces **no** standing-policy proposal card under any payload — assert the card is **absent**, not merely empty, and that no setting was silently created. With the setting present and on, a standing-policy proposal renders with **two rule lines — current and proposed** — plus Confirm / Dismiss / don't-ask-again. Turning the setting on renders as an approve-card, never as a bare toggle (`../app/DESIGN.md §Proposal cards`).
- **C8 [pending-decision card] [r2]** A trigger card raised by a `PendingDecision` (`../engine/SPEC.md §1.14`) renders its **engine-named choices as the card's actions**, with the cause visible (`SPEC.md §3`). Picking a choice emits it through the seam — assert **no client-side application** and **no app-authored choice text**. A card whose choices the app renamed or reordered fails this scenario.
- **C9 [the wake policy renders as ruled] [r1]** With a `today` scope entry stored (FD-70's closed menu), a block inside the scope rests at the stored value and a block outside it rests at the `presence-floor` token — fill and ink faded, spine, urgency edge, border and micro-mark at full strength either way (`DESIGN.md §Board rendering`); membership derives mechanically from the block's own stored data with zero model calls (U3's discipline); a `keep-awake`-marked block renders fully awake whatever the scope says; **engaging any block reveals it to `max(value, floor)` regardless of scope** — the floor is the `presence-floor` token, so presence 0 never yields an unreadable reveal; attention is senior to the rule, always (`../PRD.md` RQ-11's reveal, asserted as the transition, not the copy). *(Added 2026-08-21 — RQ-10–12 named this file as a landing site and no scenario had landed.)*
- **C10 [the scope menu reads back as itself] [r1]** With a `kinds` scope entry stored (FD-70's one parameterized shape), the console settings pane's scope row reads the entry back **as its plain-language sentence — the picked kinds named in words, never a raw identifier** (`DESIGN.md §Board rendering` — the pane's readout *is* the state); an off-menu scope utterance produces the honest refusal naming the nearest menu shape and **writes nothing**; and operating a preset row the owner backs out of does not silently overwrite the stored entry — assert the entry survives both. *(Re-cut 2026-08-22 twice: from the island form FD-39 retired, then from the open-predicate form FD-70 cut to the closed menu.)*

- **C11 [staleness shows itself] [r1]** *(Situation C's "expired certs show red"; added 2026-08-22.)* A stored qualification attribute whose expiry instant is past renders in its **expired state** on the owner's console — visual treatment per `DESIGN.md`'s urgency law, not asserted here — derived from the stored expiry alone: no model call on the render path (U3's discipline), and the state clears only when a fresh attestation is stored, never by an app-side edit.
- **C12 [board mode is packed unless set] [r1]** *(FD-81.)* With `board_mode` absent or `packed`, the board has no time axis: block position and size do not encode clock. With `board_mode: hour-grid` stored through `display_settings`, the board draws a clock face (Y-axis = hours) and a timed block may be moved by drag; packed mode has no drag-to-move. Off-set values are rejected writes. Wake policy and AA proofs apply to whichever mode is drawn (`DESIGN.md` §Board rendering). **Where undated / all-day / deadline-only work sits on the clock is unruled** — this row does not invent a gutter.

## U — Generative-UI discipline
- **U1 [compose] [r1]** A valid schema of catalog nodes renders the composed view; every node maps to a manifest component.
- **U2 [reject unknown] [r1]** A schema containing one unknown node type: structured error returned to the harness, **nothing rendered for that schema** — no partial view, no guessed widget.
- **U3 [generate-once] [r1]** The same stored schema rendered twice produces identical output with **zero model calls** (asserted by instrumentation: the render path has no model client to call).
- **U4 [data not code] [r1]** A schema attempting executable content (script node, event-handler string) is unrepresentable in the meta-schema — it fails validation before rendering is ever attempted.
- **U5 [unknown prop = rejected render] [r1]** A schema whose node carries a prop outside that type's closed manifest prop list (`SPEC.md §4.1`): structured error, nothing rendered for that schema — U2's poka-yoke, props half. *(Added 2026-08-21 — the props rule was a MUST with no defining artifact and no test; the manifest now carries per-type prop lists.)*

## G — Guest flow (end-to-end, on the wire)
- **G1 [board-blind wire] [r1]** Fetch a guest month view as the guest: the response payload contains open windows only — no commitment titles, party names, reasons, or addresses of anything blocking, and no blocked-time enumeration. *(Leak test on the wire, not the pixels.)*
- **G2 [at-a-glance] [r1]** Month cells carry the day's open windows as ranges ("2–6p"); a day with nothing open is marked closed, indistinguishable from do-not-disturb. *(Sofia's student scanning her rhythm; Debra's link offering the day's place only.)*
- **G3 [pick → form → return] [r1]** Slot pick → the published form renders → submission fires `on_form_return` carrying exactly the link's token attribution; the guest sees a plain confirmation. No account was created; no agent appeared.
- **G4 [token attribution — and per-recipient narrowing, on the wire] [r1]** Two named recipients hold different links to the same Shared artifact; each return attributes to exactly its own recipient. *(Engine S2's app half.)* **And the narrowed page** *(added 2026-08-22 — engine S5's app half)*: with a party-targeted rule narrowing recipient A, A's page renders only the narrowed set and B's response payload carries no trace of A's narrowing — G1's leak-test pattern applied between recipients.
- **G5 [dead token honest] [r1]** An expired/revoked token: the honest dead-end page — no availability shown, no redirect, no stale bookable view.
- **G6 [consent in form] [r1]** A flow requiring signature/payment authorization captures it in the form itself; the return payload carries the consent evidence; without it, submission is refused client- and server-side.
- **G7 [typed shape preserved] [r1]** The guest page is a rendering over a typed payload: the payload backing any guest view validates against the published form's schema, and submission is the same typed shape in reverse. *(This keeps the machine-legible door open — asserted as structure now, not as a machine-caller feature.)*
- **G8 [walk-up entry link mints per visitor, and the token sees the offering] [r1]** *(Re-cut FD-45, 2026-08-22 — the mint moved to open-time.)* A **public entry link** (Situation B's counter QR — `SPEC.md §5`, law at `../security/SPEC.md §3`): the bare URL's response carries **no offering data** — it mints a **single-visitor token** (rate-limited) and hands the visitor to that token's page, which renders the **published offering surface** — the live fleet with photos, prices, and open windows — before any pull, with units in a hold or a buffer absent as unpullable. The ordinary guest flow (pick → checklist → hold) proceeds on that token. Two devices scanning the same link hold **different** tokens and cannot see or affect each other's hold; identity attaches at the checklist, and from that point attribution behaves exactly as G4's named recipient. *(The walk-up half of the guest flow — Situation B's counter; the rate-limit half is `../security/SCENARIOS.md` T7.)*
- **G9 [never served from a snapshot] [r1]** A token route is rendered **per request against live token state**, never from content produced before the request that asked for it. Revoke a token, then fetch its page again with no rebuild and no cache purge: the response is G5's honest dead end, not the last-known-good page. Assert it for a route the build tool would judge static — the whole point is that the guarantee cannot be inherited from a default that happens to be correct today (`SPEC.md §5`). *(FD-11's substrate check owes this row a result: `BUILD.md` Step 0, criterion 4.)*

- **G10 [a bound token manages its own booking] [r1]** A `per-recipient` token's page shows the guest's **own booking with cancel and move** (`SPEC.md §5`): cancel records with the token's attribution, releases the slots, and the owner is informed — no owner-approval step exists on the path (asserted as absence); move re-picks from published free space only and swaps atomically — a failed placement leaves the original booking standing, never a gap. A different recipient's token for the same Shared sees nothing of this booking (T5's line); an entry-link visitor with **no booking** sees no manage state at all. **And where the page shows money or quota standing** *(sentence added 2026-08-22 — FD-54's must-work floor beat had no scenario anywhere)*: it renders the bearer's **own** marks and running quota count from the manage-state projection (`SPEC.md §5`, FD-54; the engine-side fence is `../engine/SCENARIOS.md` S1's money sentence) — another recipient's token sees none of it — and a booking completed through the entry link carries the **manage token minted at its confirmation** (FD-43) and manages exactly as a `per-recipient` booking does. *(The app half of harness H8–H9; added 2026-08-21, FD-43 parity 2026-08-22.)*

- **G11 [guest standing series] [r1]** *(FD-47; `SPEC.md §5`.)* A published shape with the series option enabled renders the one-time/recurring choice; a shape without it renders **no recurring affordance** (asserted as absence). Picking recurring books a pattern on the owner's board whose materialized instances each attribute to the guest's token and latch independently (engine M1/M2's law, exercised from the wire). The manage token's *end series* withdraws **future instances only** — past instances keep their terms and money marks — and the owner's own pattern edit is the same forward-only act (engine M3). A different recipient's token for the same Shared sees nothing of the series (T5's line). **And the base fee exists (FD-52):** where the shape carries a monthly base, enrolling materializes the base's own monthly commitment beside the sessions — assert the monthly entry appears priced under the ordinary `pricing` bind, and that *end series* ends both patterns forward-only with past entries' marks intact. *(Situation A's standing Wednesday lesson and Sofia's NT$1,000 base — the guest half of recurrence, owner-side only until 2026-08-22.)*

- **G12 [guest surfaces render in the stored language set] [r1]** *(FR15/FR32's app half; `SPEC.md §5`; §4.1's per-language label map.)* With the owner's ranked guest-language set stored (FR15, asked once at setup — assert no re-ask) and a published form authored with per-language labels, the guest page and form render in the guest-facing top-ranked language; a node whose label map lacks that language falls down the ranked chain and lands on English last (FR32's fallback rule, read from the same map) — asserted **per node**, so a mixed page is lawful and a blank label is not; and the outward notification carrying the link is composed under the same stored set. *(Both language laws were founder-ruled with zero scenarios in any suite until 2026-08-22 — the FD-15 "prose asserting a test that does not exist" class; the catalog half is `../marketplace/SCENARIOS.md` D6.)*

## D — Delivery
- **D1 [email sends] [r1]** An outward act with a reachable email recipient: the app sends, embeds the per-recipient token link, and emits `sent` on the seam for the harness to store (the app records the raw result and decides nothing — `SPEC.md §6`).
- **D2 [hand-me-the-link] [r1]** A recipient on an unreachable channel: the app composes message + link and surfaces it to the owner to forward; it emits `handed-to-owner` on the seam for the harness to store. The seam call is satisfied either way.
- **D3 [failure and complaint recorded] [r1]** A bounced/failed send emits `delivered-failed` on the seam for the harness to store; a provider-reported spam complaint emits `complaint` **against a send that already succeeded**, as the out-of-band delivery-report event (`SPEC.md §6`; `INTERFACES.md §1`) — the app doesn't retry on its own, doesn't stop sending on its own, and decides nothing about what either one means (the deciding is `../harness/SPEC.md §3.11`'s). A provider `timeout`/`unavailable` emits as its own unknown-fate outcome, never collapsed into `delivered-failed` (`SPEC.md §1.1`).
- **D4 [channel asked once] [r1]** First outward act to a new recipient surfaces the channel question; the answer is stored; the second act to the same recipient asks nothing.
- **D5 [no origination] [r1]** There is no app path that produces an outward message without a floor-gated harness act upstream — tested as absence: no endpoint, no UI affordance.
- **D6 [addressee bound] [r1]** The act names party X: the send goes to **X's stored address for X's stored channel**, carrying **X's** token link — asserted on the outbound message, on a fixture where X and Y are both recipients of the same Shared. A recipient with no stored address for their channel routes to D2 (hand-me-the-link); a name resolving to zero or two parties produces **no send at all**. *(The addressing half: T5/G4 prove a token cannot cross once sent — this proves the right human was sent to.)*

- **D7 [LINE sends behind the same seam] [r1]** *(added 2026-08-22 — FD-61 ruled the channel into the first release while no scenario or build step forced the module to exist; the row executes the ruling as written and is reversible by one counter-ruling.)* An outward act whose recipient's stored `preferred_channel` is LINE: the app sends via the LINE Messaging API **behind the identical seam shape** — the same `send` call, the same immediate-outcome union emitted on the seam for the harness to store, the same delivery events and suppression stops (`SPEC.md §6`) — and the per-recipient token link rides the message exactly as in D1. No LINE-specific verb, payload branch, or event kind exists (asserted as absence).
- **D8 [WhatsApp sends behind the same seam, template-honest] [r1]** *(added 2026-08-23 — FD-74 widened the release roster; the row is D7's pattern applied to the second channel.)* An outward act whose recipient's stored `preferred_channel` is WhatsApp: the app sends via the WhatsApp Business API **behind the identical seam shape** — the same `send` call, the same immediate-outcome union, the same delivery events and suppression stops — with the token link riding as in D1. **And the channel's own constraint is honored honestly:** a business-initiated send rides a **pre-approved utility template** on an on-file recipient opt-in; absent either, the outcome is the honest `handed-to-owner` (Generate-Link path surfaces), never a silent drop and never a reclassification into a marketing send. No WhatsApp-specific verb, payload branch, or event kind exists (asserted as absence).

## I — Import (inbound only; `SPEC.md §9`, FD-49)
- **I1 [connect is the console conversation] [r1]** The connect flow runs as a console conversation — asserted as absence of any settings-wizard route — with copy at the industry-standard minimum; the resulting credential lands vault-resident (`../security/SPEC.md §3.1`) and appears in no seam payload, no store object, and no log (T8's custody assertion, exercised from the connect path).
- **I2 [owner-triggered only, structurally] [r1]** A sync happens only as an `import_fetch` inside a caller-initiated firing: assert **no background poll, watch, timer, or scheduled path** exists to reach the importer (absence over the tree — FR12's law), and that a trigger firing cannot invoke it (the harness half: `../harness/SCENARIOS.md` B10).
- **I3 [imported items are proposals, tagged] [r1]** Fetched items enter the loop `import`-tagged (`../security/SCENARIOS.md` Q3 — `import` grants nothing `guest` lacks) and become **propose→confirm** writes through the ordinary seam: nothing auto-commits, nothing fires outward, and a confirmed import is byte-equivalent in shape to the same commitment authored by hand.
- **I4 [rejection is a visible disconnect] [r1]** Provider rejection — revoked at the provider, a rotated ICS URL — renders the **disconnected state with the reason**; the next "Sync now" says so plainly; assert **no retry loop** anywhere in the tree (T8's no-background-retry, surfaced app-side; `SPEC.md §9`).

## V — App-only views
- **V1 [read-only by construction] [r1]** The audit/management view renders append-only history; no write endpoint is reachable from it (asserted as absence of routes, not as a disabled button).
- **V2 [SOP library routes edits] [r1]** Opening an SOP from the library and editing routes through the normal authoring seam — the library itself never writes.

## O — Onboarding & starters
- **O2 [starters compile to seam writes] [r1]** Tapping a starter template produces ordinary commitment/rule writes through the seam, pre-filled and owner-confirmed — byte-equivalent in shape to what the console path would produce.
- **O3 [saved locations] [r1]** "home" typed in any place field resolves to the stored address; editing the stored address updates resolution everywhere; an unknown name is just a literal, not an error.

## S — Appearance (skins, boring, opacity)
- **S1 [skin applies] [r1]** Selecting a skin re-tints canvas and chrome from that pack's approved palette tokens; the same stored appearance state renders identically twice, with **zero model calls**.
- **S2 [boring round-trip] [r1]** Boring on: photo off, solid content backing. Boring off: **every member of the display-only state set** (`SPEC.md §7`'s enumeration, whole — the duplicate list this parenthetical carried went stale against it twice; the set's one home is §7) restores exactly. The stash survives reload. *(Asserted against the set, not a fixed list: a member added to §7 and not stashed fails this scenario, which is how the second opacity dial and `keep-awake` would have been caught.)*
- **S3 [fave-four FIFO] [r1]** Starring a fifth skin drops the oldest fave; unstarring the last is a no-op; the pop-out never exceeds four rows and never renders a scroll container.
- **S4 [no-flash landing] [r1]** A return visit paints the stored skin in the first frame; a true first visit paints the ambient ground — never a guessed skin later corrected.
- **S5 [gallery = own board] [r1]** Every gallery card renders the owner's own current board re-tinted per that skin — real commitments, display projections only, no app-computed values, zero writes.
- **S6 [degrade to available] [r2]** With the marketplace stub unreachable, the store shelf shows an honest absence — never an error wall or stale store actions. The picker still serves the owner's faves from skins **available on-device** (the shipped four always; installed store skins from their persisted device copies); nothing offers a skin whose pack isn't present. The fave-four law (S3) and Plain's never-a-picker-row rule hold unchanged during the outage.
- **S7 [guests unskinned] [r1]** A guest page fetched while any skin is active carries **zero skin tokens on the wire** — G1's leak-test pattern, applied to appearance.

- **Z2 [the swap] [r1]** The full harness `SCENARIOS.md` suite (including P1, the compaction pass-through, **and P2**, the pending-decision round-trip) runs green with the real app in place of the app stubs — **zero harness changes**. The layer's definition of done. *(FD-80: one list. This row is the full harness `[MUST]` suite, including P1 and P2 — not a tagged subset. Home `../PRD.md` §6.5.)*
- **Z3 [story walkthroughs] [r1]** Two end-to-end renders on the real canvas: **Sofia's link flow** (generate link → student's month view → booking lands → board updates live) and **Debra's compaction morning** (cancellation event → direction question card → proposal card → confirmations → board re-forms → freed-afternoon question). Every screen along both paths renders from stored structure with zero model calls.
