# App — ideas captured from the user stories

*Status: **all five ideas absorbed into the spec package (2026-08-05)** — onboarding & starter templates → `SPEC.md §8`, saved locations → `SPEC.md §8`, guest availability-at-a-glance → `SPEC.md §5`, adaptive link delivery → `SPEC.md §6`. Kept as provenance, not as open input.*

*Raw ideas that surfaced while writing the TDD user stories and belong to the **app** layer — captured here before the app design pass.*

- **Onboarding flow.** A new user lands on an empty board; the app should walk them through the common areas of life — meals, physical activity, work — so the board fills fast instead of staring blank. (Surfaced in Person A: Elena setting up meals/workouts one by one.)
- **Common-domain starter templates.** Most people eat a few times a day and do some exercise; work is "share my availability." These are standard shapes with predictable fields, so ship sensible starter templates rather than making everyone build from zero. (See the matching harness note on template-matching.)
- **Saved locations.** Typed names like "home" or "gym" resolve to a saved address (editable in settings), so the user doesn't re-drop a map pin every time. Person A: Elena types "home" and it just fills in.
- **Guest booking calendar shows availability at a glance.** The off-app booking page's month view displays *when* the owner is open right in each day cell (e.g. "2–6p", "6–9p") — not a greyed-out hour grid, and not blank-until-you-click. A student reads the owner's rhythm before drilling into any day; days with no availability (or do-not-disturb) are the only blacked-out marks. Drilling into a day is for picking the exact start + duration. (Person A: Bobby scanning Sofia's calendar.)
- **Adaptive link delivery.** When the user shares a booking link, the app can **send it for them** through the recipient's channel (email / WeChat / text) — the user picks the method — OR just hand them a link to send themselves through any app annnä can't reach. Solves both "goes to the right person" and "goes by the right method." (Person A: Elena sending links to Bobby/Millie/Brownie.) **Both halves are now absorbed:** the method half → `SPEC.md §6` (channel stored per recipient, asked once); the person half → `SPEC.md §6` (the addressee is resolved, never composed — D6), absorbed 2026-08-07, having sat here unabsorbed while only the method half reached the spec.

## Still open — calendar import (founder ruling 2026-08-06)

*The true history, in order. **Numbering warning:** the `R11` in this paragraph is the **prior-build repo's** numbering, and it is a different thing from this corpus's founder ruling series (now `FR#`, to end exactly this collision). The **prior-build repo** (not this one) ruled its **R11** — "Unseen commitments are handled by rules, never integration": an outside calendar annnä can't see gets a standing rule, never a sync (`~/Desktop/annnä/docs/product-definition.md`, external to this repo). **This corpus** then ruled import differently from the start: `../archive/05-post-critique-decisions.md` Decision 2 (2026-08-03) — **import IN yes, export/sync OUT banned**. A stricter "no calendar integration, ever" line briefly entered the app package citing R11 and was corrected by founder ruling 2026-08-06, which closed the whole question as **"data flows in, never out"** (see OR-39 below). R11's reason survives intact: commitments not brought in are still covered by **standing rules**, never a background sync. Consistent with `../harness/SPEC.md §0` ("import IN is allowed") and the Situation-C instructor story (`../user-stories/Situations/Situation-C/resource-instructor.md`). The non-goal at `SPEC.md §9` records the current law. One thing stays open (the mechanism); the sync/write-back question below is closed:*

- **Import mechanism — open design item.** *That* annnä imports calendars is ruled, and so is the trigger: the owner connects an account once, then asks for updates — annnä never pulls on its own. **The credential half is now ruled** (`../security/SPEC.md §3.1`, 2026-08-06): the stored OAuth refresh token is a **held credential**, filed apart from the token table (which stays closed at four) precisely because annnä *holds* it rather than *mints* it — vault-resident, **read scopes only** (a write scope would turn "never out" from an impossibility into a promise), revocable from either side, expiry surfaced visibly with **no background retry**, and never a basis for crossing the floor. What remains *not* ruled is which calendar providers, the connect **UX** itself, and the format on the wire; none is invented here. Belongs to the app's move-data-in role (`README.md`) and the harness/security import seam (source-tagging at `../security/SPEC.md §5`). Awaits a design pass.
- **OR-39 — calendar sync & write-back: CLOSED (founder ruling 2026-08-06).** *The ruling, stated plainly: data flows in, never out.* **Inbound is allowed** — the owner connects an outside calendar once, then brings updates in by asking; **annnä never pulls on its own**, so there is no background poll, no watch and no timer (connect flow and providers still unspecified; see the open item above). **Outbound is banned** — annnä never keeps a live two-way connection and never writes back to an external calendar, carrying `archive/05-post-critique-decisions.md` Decision 2 unchanged: a second writable copy of the board reintroduces exactly the split-truth problem the product exists to remove. This matches the standing posture at `../harness/SPEC.md §0` and `../security/SPEC.md §8`. The legal data-portability minimum is already satisfied by security §8's takeout carve (on-request takeout, not live sync-out); if a jurisdiction ever demands more, that is ruled when it arrives. Outside commitments that are not brought in remain covered by **standing rules**, never a background two-way sync.
