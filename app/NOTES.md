# App — ideas captured from the user stories

*Status: **all five ideas absorbed into the spec package (2026-08-05)** — onboarding & starter templates → `SPEC.md §8`, saved locations → `SPEC.md §8`, guest availability-at-a-glance → `SPEC.md §5`, adaptive link delivery → `SPEC.md §6`. Kept as provenance, not as open input.*

*Raw ideas that surfaced while writing the TDD user stories and belong to the **app** layer — captured here before the app design pass.*

- **Onboarding flow.** A new user lands on an empty board; the app should walk them through the common areas of life — meals, physical activity, work — so the board fills fast instead of staring blank. (Surfaced in Person A: Elena setting up meals/workouts one by one.)
- **Common-domain starter templates.** Most people eat a few times a day and do some exercise; work is "share my availability." These are standard shapes with predictable fields, so ship sensible starter templates rather than making everyone build from zero. (See the matching harness note on template-matching.) *(Provenance, FR38: starters are domain content — founder-built through the app as production defaults, never developer-authored; any dev-time starter is declared throwaway. See `SPEC.md §8`.)*
- **Saved locations.** Typed names like "home" or "gym" resolve to a saved address (editable in settings), so the user doesn't re-drop a map pin every time. Person A: Elena types "home" and it just fills in.
- **Guest booking calendar shows availability at a glance.** The off-app booking page's month view displays *when* the owner is open right in each day cell (e.g. "2–6p", "6–9p") — not a greyed-out hour grid, and not blank-until-you-click. A student reads the owner's rhythm before drilling into any day; days with no availability (or do-not-disturb) are the only blacked-out marks. Drilling into a day is for picking the exact start + duration. (Person A: Bobby scanning Sofia's calendar.)
- **Adaptive link delivery.** When the user shares a booking link, the app can **send it for them** through the recipient's channel (email / WeChat / text) — the user picks the method — OR just hand them a link to send themselves through any app annnä can't reach. Solves both "goes to the right person" and "goes by the right method." (Person A: Elena sending links to Bobby/Millie/Brownie.) **Both halves are now absorbed:** the method half → `SPEC.md §6` (channel stored per recipient, asked once); the person half → `SPEC.md §6` (the addressee is resolved, never composed — D6), absorbed 2026-08-07, having sat here unabsorbed while only the method half reached the spec.

## Generative-UI coverage pressure-test (2026-08-07)

*Validation of the existing design, not new law. Question: can the fixed catalog v1 (`SPEC.md §4.1`) compose every form Situations A–D require? **Situation E was held out** — coverage predicted, not designed to (below). This table records the result; it creates no spec.*

**Verdict: catalog v1 composes every form in Situations A–D. Zero CANNOT-COMPOSE cases, so no `§4.1` primitive is proposed.** Two AWKWARD spots are recorded with their workarounds.

| Situation | Forms tested | Verdict |
|---|---|---|
| **A / A′** (Sofia — teacher) | life-commitment, bookable-teaching template, guest booking, no-show rule, A′ blanked-parameter install | Compose cleanly, except the new-party list (awkward, below) |
| **B** (Sunbird — bike rental + walk-up counter) | shop setup, bike/unit resource, guest pull + checklist, damage-charge consent | Compose cleanly (damage-charge is a correct *refusal*, not a gap) |
| **C / C′** (dive center — multi-resource) | center setup, course design, specialties, ranked preference lists, six resource forms, guest medical/waiver intake, C′ bundle install | Compose cleanly (gear type×size grid is verbose but mechanical over closed axes; group booking rides per-recipient tokens, not an in-schema repeater) |
| **D** (Debra — home-visit + compaction) | life-commitment, places/site, session templates, per-patient constraints, guest home-visit request, compaction/move-confirm, travel override, admin task | Compose cleanly, except the new-party list (awkward) and the service-area declaration (awkward, below) |

**AWKWARD (workaround exists; recorded, not elevated to a proposed primitive):**
1. **Open-ended list of *new* named parties in one authoring pass** — "who is this for?" surfaces in A (`../user-stories/Situations/Situation-A/story-sofia.md`) and D (`../user-stories/Situations/Situation-D/story-debra.md`) independently. `party-picker` references a *known* principal; there is no repeater/list-of-new-records node, and composition nodes have fixed children. **Workaround:** sequential per-name creation turns (the corpus's confirm-per-proposal pattern). Arguably out of the catalog's scope anyway — minting a new principal is a harness *elicitation* act, not a form field. Strongest catalog-revision candidate if one is ever opened (seen twice), but **not a gap that breaks any tested behavior**.
2. **Debra's service-area declaration** — the prose implies an irregular drawn boundary ("this side of the highway"), but the only *tested* behavior (`../user-stories/Situations/Situation-D/situation-3.md`) is a binary feasible/infeasible check at submit, which `threshold` (max drive-time/distance from home) fully covers. Flagged because the prose outruns the test; a geo-region node would be the missing primitive *only if* a future situation ever tests polygon precision.

**Situation E (held out — prediction, not a design target):** E is the ER shift (`../user-stories/Situations/Situation-E`), whose distinctive shapes are an ordering over principals (seniority) and admission-as-type-match — both are *rule/attribute* concerns (harness J2/J4 held-out probes), not new form-field types. **Prediction: E's forms also compose from catalog v1** — seniority is a `ranked-list`/`threshold` over a principal attribute and staffing rules reuse `scope-selector` + `threshold` + `multi-select`, none of which need a new node. To be confirmed against E only after the harness build, per the held-out discipline.

## Still open — the board has no direct-manipulation path for time, and the bet is untested (2026-08-08)

*From the concept-feasibility research pass (provenance: `../RULINGS.md` FD-16). Recorded so it is a decision rather than a discovery. **Not a blocker for any build step**, and **not a proposal to change the board.** The board laws were in fact re-ruled the next day (FD-22, FD-23 — two gravities, and it scrolls); this note did not ask for that and none of it answers this note. The one law this finding rests on — **no time axis** — is the one the re-ruling left untouched.*

`DESIGN.md`: *"No time axis, ever. Time is block data, never position or size."* Blocks are uniform regardless of duration and the date row is the sole navigation. A consequence follows that no file states: **drag a block to move it — the most common gesture in every competing product — is unconstructable here by design.** Every time change routes through the console or a riser form.

*(Quote refreshed 2026-08-09. It formerly read "The board never scrolls and has no time axis" — **the board now scrolls** (`DESIGN.md` §Board rendering, two gravities), and the citation would otherwise point at a phrase no longer in the file. **The finding is unchanged and if anything sharper:** scroll moves a block's position on screen without moving it in time, so scrolling is not a time gesture and the gap this note records — no direct-manipulation path for time — is exactly as open as it was.)*

The external evidence is unflattering and consistent: conversational interfaces lose to direct manipulation on **low-ambiguity visual tasks**, the gap widening as difficulty rises, and what users prefer is the hybrid — pointing *and* speaking, with language reserved for what is hard to point at. *"Move this to 3pm"* is the canonical case where conversation loses.

**What the corpus already answers with:** the console is present in every canvas state (`SPEC.md §1`, Supersession 2 — reversed on purpose so the owner can talk about the open thing), and `selected_ref` in the view-context makes *"push this back an hour"* resolve against the selected block — pointing and speaking combined, which is closer to the hybrid ideal than either alone. The riser is a direct-manipulation surface for the same edit.

**The open part:** the design rests on a bet that the gesture becomes *rare* — if placement is good, nobody drags blocks all day. That bet is the product, and **nothing in `SCENARIOS.md` tests it.** C1–C8 assert the board renders correctly, never that an owner can *correct* it as fast as they could in a grid.

**Suggested resolution, not ruled:** add a **time-to-correct** measurement to the Z3 story walkthroughs rather than a new scenario — Sofia's and Debra's paths already exist, and the number that matters is how long a correction takes on the real canvas versus the grid it replaces. Measure before redesigning anything.

## Still open — perceived latency on the conversational write path (2026-08-08)

*Surfaced by the harness technical research (traceability, outside this repo: `~/Desktop/RiskNeutral/Vaults/annnä/research/technical-annnä-harness-layer-research-2026-08-08.md`). Recorded here, not in `harness/`, because the finding is that **no layer owns it** and this is the layer where a human perceives it.*

An owner utterance traverses `normalize` → engine reads for the relevant slice → tool calls under the floor → check-work read-back → `narrate` before a confirmation appears — at minimum two model round-trips plus engine calls. **No scenario in any layer covers how that feels**, and none of the harness's five responsibilities owns "it must be fast." The one latency bound the corpus does carry is `../engine/SPEC.md`'s travel envelope, capped *"by law, not by hope"* so an external call inside the placement hot path cannot become the product's latency — which is the precedent for how to bound a hot-path cost here, if a bound is wanted. Open questions, none ruled: whether the app shows progressive state (the utterance landed / the engine is checking / here is the proposal) or waits; whether `narrate` may stream; whether a slow firing should ever surface differently from a parked one. **Not a blocker for any build step** — recorded so it is a decision rather than a discovery.

## Still open — calendar import (founder ruling 2026-08-06)

*The true history, in order. **Numbering warning:** the `R11` in this paragraph is the **prior-build repo's** numbering, and it is a different thing from this corpus's founder ruling series (now `FR#`, to end exactly this collision). The **prior-build repo** (not this one) ruled its **R11** — "Unseen commitments are handled by rules, never integration": an outside calendar annnä can't see gets a standing rule, never a sync (`~/Desktop/annnä/docs/product-definition.md`, external to this repo). **This corpus** then ruled import differently from the start: `../archive/05-post-critique-decisions.md` Decision 2 (2026-08-03) — **import IN yes, export/sync OUT banned**. A stricter "no calendar integration, ever" line briefly entered the app package citing R11 and was corrected by founder ruling 2026-08-06, which closed the whole question as **"data flows in, never out"** (see OR-39 below). R11's reason survives intact: commitments not brought in are still covered by **standing rules**, never a background sync. Consistent with `../harness/SPEC.md §0` ("import IN is allowed") and the Situation-C instructor story (`../user-stories/Situations/Situation-C/resource-instructor.md`). The non-goal at `SPEC.md §9` records the current law. One thing stays open (the mechanism); the sync/write-back question below is closed:*

- ~~**Import mechanism — open design item.**~~ **CLOSED 2026-08-07 (wayfinder #10/#11).** The credential half was already ruled (`../security/SPEC.md §3.1`, 2026-08-06). The rest is now ruled and landed at `SPEC.md §9`: providers = Google (`calendar.readonly`), Microsoft Graph (`Calendars.Read`), iCloud (app-specific password over CalDAV) *(since dropped — FD-37: CalDAV under that password is read-write by construction; iCloud owners import via ICS)*, ICS/secret links; connect UX = the console conversation, copy at the industry minimum. Research record: local branch `research/calendar-import-providers`; prototype: local branch `prototype/calendar-connect-ux`.
- **OR-39 — calendar sync & write-back: CLOSED (founder ruling 2026-08-06).** *The ruling, stated plainly: data flows in, never out.* **Inbound is allowed** — the owner connects an outside calendar once, then brings updates in by asking; **annnä never pulls on its own**, so there is no background poll, no watch and no timer (connect flow and providers still unspecified; see the open item above). **Outbound is banned** — annnä never keeps a live two-way connection and never writes back to an external calendar, carrying `archive/05-post-critique-decisions.md` Decision 2 unchanged: a second writable copy of the board reintroduces exactly the split-truth problem the product exists to remove. This matches the standing posture at `../harness/SPEC.md §0` and `../security/SPEC.md §8`. The legal data-portability minimum is already satisfied by security §8's takeout carve (on-request takeout, not live sync-out); if a jurisdiction ever demands more, that is ruled when it arrives. Outside commitments that are not brought in remain covered by **standing rules**, never a background two-way sync.
